# R85：控制面性能优化开发日志

开始日期：2026-09-10。基线提交：`bb25ab9`。当前推进 **HTTPD**。

这份日志按“问题 → 成本定位 → 改动 → 实测 → 功能检查 → 保留或撤回”的顺序记录。

- rpcd 的配置列表 CPU 为 80→130 µs/次，增加 62.5%。
- netifd 的设备状态查询延迟增加 41.7%，CPU 增加 57.2%。

782.63→879.88 µs/次（+12.43%）。单体完成后再评价整机，不能把各项倍率相加。

### 每项的执行与验收规则

1. 定位成本：分开统计函数/阶段耗时、分配次数与字节数、系统调用、复制与等待。
2. 按贡献排序：同时看绝对成本、调用频率、可消除比例和影响范围；猜测不写成已证实根因。
3. 每次改动尽量只处理一个可解释的成本来源，记录源码版本与二进制 SHA-256。
4. 比较原版、R84 Rust、当前候选。剖析器下的时间只用于定位，正式成绩来自无剖析器的发布构建。
5. 保留全部有效重复测量，记录均值、p95/p99、CPU、内存和运行间差异，排除失败尝试时写清原因。
6. 在约定负载矩阵中稳定超过原版，并通过功能与资源门，才标记该组件完成。未达标就继续该组件；
   不把有限测试外推成“所有输入、所有硬件都更快”。

外部接口、鉴权、错误处理和资源上限继续遵守已验证合同；内部算法、数据结构和状态维护方式自主优化。
缓存必须有明确失效条件。镜像、二进制、私有配置和原始测量留在 Git 外。

### H03 · 每次查找复用已取得的 metadata（保留，扩大验收）

- 证据：H01 观察到每请求 2 次 newfstatat；首次查找已拿到成功 metadata 后又读取一次。
- 改动：把该次 metadata 与命中路径一起传递，不再立刻读取第二次。每次 HTTP 请求仍重新查找，
  不引入跨请求的文件或权限缓存；目录索引的 metadata 仍来自索引文件自身。
- 要验证：查找阶段收益、每请求 syscall 数、完整请求结果，以及文件替换/删除/权限变化可见性。

H03 的查找阶段从约 15.4 降到 11.1 µs（5 × 20,000 次），简化全路径约 80 µs。
[逐轮数据](R85_parts/h03_profile.json)。候选 SHA-256：
`9289f856d2e086379fc27339142c4decfe21a22f599d6f05933f58ab054d90eb`。

扩大后的预设矩阵是：512 B `.dat`、16 KiB `.dat` / `.css`、镜像自带 44,042 B CSS、
64 KiB `.dat`、1 MiB `.dat`，分别 c1/c4；CGI、JSON-RPC 同样 c1/c4。
冻结 R84 原生客户端保持不变。四客户端 CPU 只用一个外层区间，计入并计数各 20 次预热。

**失败尝试保留：** 第一轮原版完成；随后冻结 R84 在 c4 CGI 中有一个客户端未读到有效的 200
状态行，整轮中止。这发生在 H03 候选尚未开始之前。原始记录保留于私有的
`h03-comparison`，不将该轮剩余的成功请求拼接为通过结果。失败后的正式栈与恢复门复检通过。
后续单独排查这一连接问题；扩大矩阵不是筛选有利负载。

### H04 · 请求头缓冲与超时系统调用（阶段验证通过）

### H05 · 扩展负载发现的 CGI 连接问题（修复并保留）

- 新的 c4 负载在未改动的 R84 二进制上复现无有效状态行；构建机独立的 4 客户端 CGI
  长循环也已复现。不能把这个失败作为“快”的样本，也不能通过减少并发绕过它。
- 诊断客户端增加状态/EOF 信息；它只用于定位。正式计时仍使用 SHA-256 `0d0dac73…` 的冻结客户端。
- 诊断记录确认：并发 CGI 活动中，请求头的 `fill_buf()` 返回 `Interrupted`（EINTR），
  旧实现直接向上传递并关闭连接。三次记录发生在连接的第 430、433、3559 次请求之后。
- 改动：遇到 EINTR 保留当前半行并重试；每次重试仍检查原来的整体 deadline。
  没有重新计时，也没有忽略其他 I/O 错误。
- 回归先红后绿：新测试在修复前报 `Interrupted`；修复后 24/24 单测通过，
  包含“持续被中断仍须超时”。同一冻结客户端的四连接 CGI 长循环取得 **120,000 次成功 + 80 次预热**，零错误。
- 构建机功能门：静态文件变化/权限/边界 26/26，扩展兼容性 31/31；断开 SSE 后原版遗留
  12 个 fd、候选 0；128 MiB TLS CGI 慢接收时候选 RSS 增长 112 KiB。
  R27 的 133 项保留同样 22 项既有差异，新增差异 0、存活失败 0。
  [派生验证记录](R85_parts/h05_validation.json)。
- 候选 SHA-256：`2ea259c1a4d506c0588784c27677a25087afaa6223c8ba510aeda0cf3a0bb849`。
- 失败尝试保留：`h05-comparison` 在上传前因 LAN4 已断开而停止，没有性能样本。
  用户随后明确授权 Wi-Fi 调试；后续隔离试验使用 `en0` 管理，负载仍运行在路由器的 namespace loopback。
  DHCP、双频 AP、九项进程身份、看门狗、HTTP/HTTPS、IPv4/IPv6、配置与启动身份的检查继续执行。
  这个管理方式没有触发正式栈切换、重启或刷写。

### H07 · 文件查找的路径构造（保留，剩余差距继续处理）

- 排序依据：H06 中每次文件查找仍有 10 次分配、3 次扩容；每次静态/CGI 调度都经过此路径。

### H08 · 连接内复用有上限的输出缓冲（保留，内存代价显式记录）

- 新定位：H07 的构建机追踪，c1 的 10,020 次含预热请求出现 1 次 futex（主线程等待），
  c4 的 10,080 次出现 7,901 次；mmap/munmap 也从 304/296 增至 885/876。
  这是调用次数证据，strace 下的阻塞时间不能当作真机 CPU 占比。
- 当前每个响应新建并释放 Vec，16 KiB 正文使其从 512 B 再扩容；即使连接持续复用，
  这块较大的分配仍每请求重复。先验证消除此成本能否减少并发同步和映射操作。
- 改动：Out 移到连接作用域；每个响应结束后必须彻底排空并结束 relay 状态，才能读下一请求。
  最多保留两个 16 KiB 窗口的容量，超过该容量的异常大响应头会在结束时释放。
  保留的是可覆写的空缓冲，文件内容和元数据不会跨请求缓存。
- 明确代价：keep-alive 空闲期间也保留这块容量，须记录内存开销；不能只展示吞吐收益。

  只有响应和正文处理结束才能回收。按真实 capacity 合计，最多保留 **8 KiB/连接**，超出即释放。

### HTTPD 迭代记录格式

每次实际尝试追加一节，至少包含：

- 假设、定位证据、预计消除的成本。
- 具体改动、源码版本、构建参数、产物哈希。
- 与原版和 R84 的对比，重复次数与统计口径。
- 得到的收益、无收益项、退化与资源代价。
- 功能验证结果、已知限制，最终保留/调整/撤回决定。
