# R69：R68 十八项的分诊

日期：2026-09-08。R68 的审查基线冻结在 **db5afa1**，我在那之后有若干提交，
所以每一条都要对着当前代码核实，不能直接照抄"已修"或"未修"。

## 先说不是 F 编号的那一条

**验收门槛本身失效。** 把两边监管器换成 `/bin/false`，r65 仍报
`r65: ok`、diff 0 字节、退出 0。所以在补上就绪断言之前，
**r65 的绿不能作为任何结论的依据**，包括我此前写下的"1050 行 0 diff"。

R68 列了五处叠加的漏洞：

1. 第 2 例 `call service list` 被包装器塞了个空字符串 JSON，两边都在 CLI
   解析阶段失败——**这一例从来没测过空服务表**，本身就是假绿。
2. 只检查了 ubusd 能往返，没检查监管器起来了：启动后固定 `sleep 2`，
   不看进程还在不在、`/proc/<pid>/exe` 是谁、`service` 对象和方法在不在。
3. 正向调用、预期失败调用、驱动失败没有各自的期望；`|| true` 把整个 drive
   的失败吞掉。
4. 正向效果文件用 `cat … || echo "(no file)"`，**两边都没有文件也算相等**。
5. PID 检查只要求两边结论相同：`differs/differs` 也算过，而"确实换了 PID"
   和"压根没拿到 PID"被混为一谈。

scrub 也有两处实际问题：`"pid": N` 的规则会把 `data` 里的业务字段一起抹掉；
`pid1` 的规则不锚定，会先吃掉 `wdpid1` 的尾巴。

## 修复后的状态（2026-09-08 续）

**验收门槛已经能红了。** `tools/r65_selftest.sh` 做的就是 R68 那次故障注入
（把两边监管器换成 `/bin/false`），并且**要求非零退出**；它还会先确认替换真的
发生了，否则一份没改动的副本会因为最坏的理由"通过"。实测报红，且被五处
互相独立的检查各自抓到：就绪、逐例期望、失败调用计数、PID 存在性、
以及"两边都 missing 不算一致"。

门槛现在包含：

- `ready.sh`：驱动之前先证明被测对象在——pid 活着、`/proc/<pid>/exe` 是个 procd、
  `service` 对象带齐 13 个方法、一次真实的 `service list` 往返返回对象。
- 每一次调用记录它**本来该做什么**，"两边一起失败"不再算一致：
  `call` 在非零状态时判红，11 个故意传坏参数的用例用 `callx` 声明"必须失败"；
  `must_have` 对正向效果文件做同样的事，`gate` 对不能进 diff 的正向结果
  （pid、计数）做同样的事。
  （**这一条我一度写错**：`2fb5600` 之前只有一个 `expect ok` 调用点，
  其余 132 个 `call` 只是把 `rc=` 写进被比较的文本——那不是断言。

- 第 2 例不再传空字符串 JSON——它原来是两次 CLI 解析失败被比成相等。
- `same_pid` 区分 `missing` 和 `differs`；断言两个 PID 相同的用例，
  在压根没有 PID 时会红。
- scrub 锚定到缩进的 `"pid":` 行和完整标记行，不会再吃掉 `data` 里的业务字段，

修复过程中差分自己又抓到四处，其中三处是这一轮引入的：

- 给事件处理器传 `None` pattern 被 ubusd 拒绝（`Invalid argument`），
  等于**根本没有事件处理器**，watch 永远挂不上。改回 `ubus.object.add`，
  对象重建改在 `resubscribe()` 里按 id 变化处理。
- `take_config` 把已武装的 watchdog deadline 丢了——它和 `deadline` 一样属于
  正在跑的子进程，被新配置的 None 覆盖等于**每次 reload 都会解除武装**。
- `crash_looped` 没有任何地方清除，于是崩溃循环之后的实例**删不掉**。
- 两个用例在比时序而不是行为（respawn 计数中途采样、45 秒 watchdog 在
  一次同样长的运行里只在一边触发），已改成确定性断言。

最后一处 `ujail_procs` 的差异是**断言本身不好**：它自己的明细行没有输出，
计数却是 1，两次 `ps` 之间的竞态。换成 F01 真正关心的性质——
被 jail 的命令有没有在沙箱外跑起来。

## 审自己的修复，又查出三处（2026-09-08 续二）

把 R68 的十八项都处理完、r65 连续三次绿之后，我回头审的是**我自己给门槛加的
那些断言**——结果第一条就站不住。

**其一：`expect` 写了却几乎没用。** R68 的第 3 条说"正向调用、预期失败调用
没有各自的期望"。我加了 `expect ok` / `expect err`，然后**只在一个地方用了它**
（第 2 例的空 list），`expect err` 一次都没用；其余 **132 个 `call` 只是把
`rc=` 打进被比较的文本**。那不是断言：drive 脚本里的 bug 会在两边以同样的方式
把调用打坏，diff 依旧是 0，运行照样通过——正是第 2 例当初藏住两次解析失败的
那个形状。我却在给 Astra 的复审请求里写成"三种逐例期望"，等于**把自述的修复
范围说大了**。已当场向 Astra 更正。

修法（`2fb5600`）：`call` 自己在非零状态时判红，11 个故意传坏参数的用例改用
`callx` 声明"必须失败"。两者打印的文本与原来逐字节相同，所以基线不变，
0 diff 仍然是原来那个意思。

**其二：五处"两边都没做出来也算过"。** 顺着同一个念头把门槛通读一遍，
又找到五个只把常量打进 diff、此外什么都不检查的断言：syslog 那两行、
pidfile、rc running hook 的次数、trigger requeue 的次数，以及**最要命的
F06——"换了个新 ubusd 之后监管器有没有回到总线上"**。这五个都在"两边
都没有产出"时通过。`gate`（`d00ed03`）打印和原来完全一样的文本，
但在正向结果没发生时判红。

**其三：`grep -c` 的返回值。** 修其二时发现 hook 计数那行本来就有个潜伏 bug，
而我新写的那行原样继承了它：`grep -c` 在**零匹配时会打印 `0` 并且退出 1**，
所以 `$(grep -c … || echo 0)` 得到的是 `"0\n0"`，随后的算术比较直接报错——
**恰好是在这个断言该响的那条路径上**。两处都改成 `|| true` 加空值兜底。
判决那一侧还有两个同类的（`7d6b991`）：calls 文件不存在时捕获为空，
`[ "" -lt 1 ]` 是**错误**而不是真，`if` 于是走 else，本来要抓
"什么都没跑起来"的检查反而静悄悄地过了。两种情况都对着一个不存在的文件
实测过：旧写法跳过，新写法报红。

这三处的共同点和 R68 第 3 条是同一个：**把"记录下来"当成了"断言"**。
写进合同的教训是——**加一条断言之后，要回头数它到底被调用了几次**。

## 第四处：注释把 harness 整个弄坏了，而 `sh -n` 说没问题

上一节写完"加一条断言之后要回头数它被调用了几次"，我紧接着就犯了同一类错的
另一种形态。

给 scrub 加那条"这条规则我知道太宽"的注释时（`9e8910b`），三行注释被放进了
**用反斜杠续行的 `sed` 里面**。续行到注释就结束了，下一行的 `-e` 于是被当成
命令：`-e: not found`，退出 127，**一行都没比较**。harness 整个不工作了。

`sh -n` 是通过的——文件是合法的 shell，只是跑的东西不对。我就是靠 `sh -n`
加上"上一份拷贝跑绿了"把它提交的：**部署并跑的是旧拷贝，提交的是新拷贝，
引用的是旧拷贝的结果。**

抓住它的不是任何检查，是"提交之后按 md5 重新部署再跑一次"这一步。
run 5 因此报 `EXIT=127`、`compared=0`。修法是把注释移到 `sed` 外面
（`bcfcb49`），并且这次**真的执行 scrub 验证**：对象 id 被抹、缩进的 `"pid"`
被抹、`"pidfile"` 不受影响、`pid1`/`wdpid1` 被抹。

所以这一晚同一个形状出现了三层：
**二进制不是我以为的那个**（`--examples` 不建 bin）、
**断言没在断言**（`expect` 只有一个调用点、五处常量、`grep -c` 的返回值）、
**脚本根本没跑**（注释断了续行）。
共同的解药只有一句：**部署你提交的那一份，跑它，引用它**——
harness 的 md5 要和候选二进制的 md5 并排记下来。
