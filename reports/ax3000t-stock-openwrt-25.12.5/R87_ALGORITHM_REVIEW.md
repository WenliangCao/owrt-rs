# R87：三处残余回退的算法复核与改动

开始日期：2026-09-12。起点 `02ef26f`（R86 收尾），设备仍运行 R86 发布 `f612e30`。
状态：三项代码改动已提交并在构建机 `oracle` 完成单元测试、R86 同名功能门和对照实验；
**尚未生成正式发布产物，也没有部署到路由器**。本文所有数字都是构建机数字或 R86 实机数据的重新分析，
不是新一轮实机验收。

## 1. 复核对象

R86 保留的三处不如原版：

| 现象 | R86 实机数据 |
|---|---|
| HTTPD 64 保持连接 RSS 增量 | 原版 452 KiB，Rust 2096 KiB |
| 整机真实 `service list` | 平均延迟 +1.02%，控制面 CPU/次 298.00→354.50 µs（+18.96%） |
| 少数尾延迟 | ubusd 精确 lookup p99 +13.81%；rpcd `session_access_64` p95 +9.36% 等 |

## 2. 定位

### 2.1 整机 CPU 回退来自 ubusd 事件循环的 O(客户端数) 工作

整机窗口的每条读负载记录了六个守护进程各自的 CPU。按进程拆开（每侧两窗×五轮的中位数，µs/次）：

| 顺序负载 | 原版 procd | 原版 ubusd | Rust procd | Rust ubusd |
|---|---:|---:|---:|---:|
| `service list` | 199.0 / 198.0 | 101.0 / 99.0 | 207.0 / 206.0 | 148.0 / 148.0 |
| `network.interface dump` | — | 97.0 / 94.0 | — | 135.0 / 135.0 |
| `log read` | — | 166.0 / 161.0 | — | 197.0 / 192.0 |
| `uci get`（rpcd 路径） | — | 76.0 / 76.0 | — | 111.0 / 113.0 |
| JSON-RPC over HTTP | — | 253.0 / 253.0 | — | 331.0 / 331.0 |

`service list` 的 +56 µs/次中，procd 本身只贡献 +7.5 µs（+3.8%），其余 +48 µs 全部是 ubusd；
而且每一条经过 ubusd 的负载都多出 36–48 µs/次，与负载内容无关。隔离矩阵里 Rust ubusd 反而更省
（invoke −0.95%、lookup −8.70%），差别在于隔离夹具只有 2 个客户端，实机 ubusd 空闲时有 21 个 fd（约 18 个客户端）。

原因是 `ubusd/src/main.rs` 的事件循环每次迭代都从整张客户端表重建 `poll(2)` 数组并轮询全部客户端，
每转发一条消息要做 2–3 次这样的轮询；C 版 ubusd 通过 uloop 使用 epoll，每次只处理就绪项。
这是算法级别的差异（每消息 O(N) 对 O(就绪数)），不是常数开销。

### 2.2 HTTPD 保持连接内存来自“每连接一线程”

空闲的保持连接各自占用一个线程：已触碰的栈页、8 KiB 读缓冲、解析存储，再加每线程 16 KiB 内核栈和
一页页表（R86 实机 VmPTE 34→294 KiB，Threads 1→66）。R86 把输出缓冲改成共享后仍剩 2096 KiB，
说明每请求缓冲不是主因，连接模型才是。uhttpd 单线程事件循环下每个空闲连接只有一个 `struct client` 与 ustream 缓冲。

### 2.3 尾延迟

- ubusd 精确 lookup p99：候选四轮分别 114.11、114.34、141.19、137.34 µs，原版 109.34–118.49 µs，
  两轮偏高、两轮与原版相同。代码路径（BTreeMap 查路径、ACL 检查对 root 直接放行、单次 sendmsg）没有可归因的算法问题；
  2.1 的循环改动减少了每消息工作量，但不能据此声称 p99 已修复。
- rpcd `session_access_64`：“64”指会话表中有 64 个会话，会话查找是 BTreeMap，O(log n)。
  每次检查对作用域内每条 ACL 执行两次 `fnmatch`，Rust 实现按字节递归；C 使用 libc 的迭代实现。
  这是常数级差别，均值已经领先，p95 的 +10 µs 不能确定归因。
- procd 真实列表 +3.8%：Rust 循环在每条总线消息后都执行一轮维护（日志泵、回收、超时、触发器、rc 队列）并重建 poll 集合，
  C 只在定时器到期时运行。本轮未改：把维护改成“只在非总线唤醒时执行”会让由总线消息排队的触发器最多晚一个 200 ms 节拍启动。

## 3. 改动

### U05 · ubusd：增量维护的就绪集合（`5cb2192`）

新增 `ubusd/src/readiness.rs`：Linux 上用 epoll（与 uloop 相同），其他目标保留一个原地维护的 poll 集合供测试构建。
客户端连接时注册一次、断开时移除一次；只对本轮实际写过的客户端（`Server::touched`）同步输出就绪兴趣，
与 C 版围绕阻塞写增删 `ULOOP_WRITE` 的做法一致。`service_client` 的读写语义未变。

构建机 oracle，ubusd 与客户端各固定一个核，每组 5 次取中位数，ubusd CPU µs/次（旧→新）：

| 空闲客户端 | invoke | 精确 lookup |
|---:|---:|---:|
| 0 | 49.0 → 49.0 | 17.3 → 17.7 |
| 18 | 59.7 → 49.7 | 22.7 → 16.7 |
| 200 | 73.0 → 48.7 | 35.3 → 17.3 |

新循环的成本与客户端数无关；旧循环在 18 个客户端时已多出约 10 µs/次（构建机的 poll 每 fd 成本远低于路由器的 Cortex-A53，
实机差额为 36–48 µs/次）。

### H17 · HTTPD：空闲保持连接不占线程（`c36badb`）

连接线程等待下一请求首字节最多 50 ms；这个等待就是请求头截止时间本来就要设置的套接字读超时，只是更短，
所以请求循环没有增加系统调用。超时未收到任何字节时，套接字交还给接受它的监听线程：监听线程把所有停放的套接字与
监听套接字一起 poll，在原保持连接截止时间（uhttpd `client_timeout`）到期时关闭。停放套接字有输入则重新起线程；
对端已关闭的连接在监听线程内直接释放，不起线程。TLS 连接只在 rustls 没有已解密明文、也不欠对端写入时停放。
主线程自己运行一个监听器，空闲时线程数等于监听器数。

保留的语义：保持连接截止时间仍从上一响应开始计；`max_connections` 仍计入全部打开连接并在上限时停止接受；
流水线字节先服务再停放；线程创建失败仍归还连接槽（R86 F02 门重跑通过）。

构建机 oracle，静态 musl 构建（与路由器相同的分配器），`bench http-resident` 64 连接：

| 指标 | R86 HTTPD | 本轮 |
|---|---:|---:|
| 持有时 RSS 增量 | +1944 / +1932 KiB | +100 / +104 KiB（堆预热后 +0 / +8） |
| 持有时线程数 | 66 | 1 |
| 持有时 VmPTE | 304 KiB | 44–56 KiB |

R86 的正式 `r85_httpd_static.py --memory-connections 64` 在精确 rootfs 中重跑：原版 uhttpd 增量 444 KiB，本轮候选 92 KiB
（R86 最终文件同一夹具为 1936 KiB）。固定核的 c1 每请求 CPU 在噪声内不变：小文件 40.0/40.5 → 39.5/39.5 µs，
16 KiB 46/47 → 47/48 µs。

代价：空闲超过 50 ms 后的第一个请求要重新创建线程（A53 上约数十至一百微秒）并分配 8 KiB 读缓冲；停放的 TLS 连接仍持有 rustls 缓冲；
监听线程的 poll 集合大小等于停放连接数，仅在停放/唤醒事件时轮询，`-N 0` 取消上限时该集合无界。

### H18 · HTTPD：停放集合改用共享就绪集合（`e766e86`、`2ba37c8`）

U05 的就绪集合移入共享 crate `owrt_ubus::readiness`（测试随之迁移），HTTPD 监听线程用它保存停放的套接字：
每个连接注册一次、按令牌唤醒，监听套接字在连接上限时离开集合、有空位时回来。`-N 0` 取消上限时停放/唤醒的成本不再随
空闲连接数增长。六个 HTTPD 门重跑通过；30000 次 CGI 压力在三个夹具并行时失败一次，单独重跑通过。

### P11 · procd：只读方法后跳过维护，空闲时睡到下一个截止时间（`fab7cea`）

每条总线消息后都执行整轮维护（日志泵、回收、超时、触发器、PID 1 工作、rc 队列），且无事可做时仍每 200 ms 醒一次：
R86 空闲 procd CPU 是 C 版的五倍（0.008%→0.042%），真实 `service list` 每次都付这轮维护。现在：只读方法
（`list`、`get_data`、`validate`、`system info/board`）不触发维护；任何时间相关状态待处理时（停止/重启截止、实例看门狗、
触发器、rc/hotplug 任务、inittab 重启、coldplug）保留原 200 ms 节拍，否则睡到下一次看门狗喂狗、上限 5 s；
关机信号与 SIGCHLD 一样写自管道唤醒循环。procd 门重跑：busy 候选 5/5（原版侧 7 次里失败 2 次，是 R86 已记录的原版丢日志问题），
r65、r83、r71、r72 tty、r75 通过；73 项单元测试通过。

### R45 · rpcd：字面量与 `*` 的 ACL 匹配快路径（`f57b716`）

`fnmatch` 对不含通配符的模式直接比较切片，对单独的 `*` 直接返回真；含通配符的模式仍走原匹配器。
新增单元测试覆盖两条快路径与原匹配器的一致性。

### 夹具与构建机清理

`7d72bad` 修正 r36/r42 的对象基线竞争；`caed6ac` 让 r36 沙箱结束时杀掉它启动的 rpcd（沙箱没有 pid namespace）。
构建机上 32 个 `/sbin/ubusd` 和 1 个 `/sbin/rpcd` 残留进程（根目录均已删除，来自 r83_lifecycle_diff 与 r36 的历次运行）已按 pid 清理；
r83_lifecycle_diff 的泄漏路径未改。

### 4.1 三个门的红灯都在夹具，不在被测程序

- **r36 / r42 的对象列表竞争**：两个 inner 脚本在 `ubus list` 出现 `uci` 后立即取对象列表基线，而 rpcd 的插件对象
  （`luci`、`network.rrdns`）晚片刻才注册。基线取早了，最终列表就多两项。首轮 r36 是 C 侧缺、Rust 侧全，重跑三次里两次反过来；
  旧 ubusd 三次里也有一次红。改为“连续两次相隔 1 s 的列表一致且含 `uci`”后再取基线，新旧文件各 3 次全绿。
  这是把 R86 用一次通过掩盖的竞争修掉，不是放宽断言。
- **r41 的 verdict 字串**：构建机 `/tmp/r36-helpers/busprobe`（9 月 6 日）打印 `dropped_during_body`/`too small`，与仓库
  `tools/testsrc/busprobe.c` 和 `audit_checks.py` 期待的 `dropped` 不同，新旧 ubusd 用它都红；用 HEAD 源重建到独立目录后新旧都绿。
- **r26 的 Not found**：首轮 91 个差异全部是原版 rpcd 返回 `Command failed: Not found` 而候选正常应答，形态与上面的注册竞争一致；
  同一命令再跑两次为 0 差异，旧 rpcd 对照也是 0 差异。保留首轮记录，不据此宣称候选与原版逐字节一致的概率。
- 构建机上还残留着 32 个历次门运行留下的 `/sbin/ubusd` 和 1 个 `/sbin/rpcd`（2026-09-10 至 09-12，父进程为 1），
  本轮没有清理别的会话的进程；它们各在已删除的 rootfs 副本里，未见影响，但说明夹具的收尾不完整。
