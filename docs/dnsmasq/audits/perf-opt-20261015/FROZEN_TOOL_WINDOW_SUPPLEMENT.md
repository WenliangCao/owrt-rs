# 冻结协议补充：工具无效窗口的成对补测

用户于 2026-10-15 明确批准本条款，从候选 E 当前轮次开始适用：

> 因测试工具原因无效的窗口，在整轮结束后按原条件、原交替顺序补测同一对；两侧规则相同。补测仍然无效的，如实记为失败。原失败窗口全部保留。

本条款在 E 原始无效窗口出现后、任何补测开始前制定。这不是原始运行前的预注册；原始冻结文件、所有原始结果和退出码保持不变。这里只修改工具无效窗口的处理方式，原有负载、正确性要求、统计规则、噪声与精度门、健康保护及资源要求不变。

## 资格与对称性

同一规则适用于比较的任一侧。E 的旧标签 `c` 是已部署 v0.2.0（`8472be5a…`），`rust` 是 E（`8b8082b9…`）；标签不改变资格规则。

可以补测的工具原因包括：

- 负载工具漏发或跳过计划请求，已发送请求均正确，且没有 dnsmasq 响应超时、错误或崩溃。
- 请求批次与上游时间相位计数不一致，原始计数和轨迹支持工具口径问题；仍保留该窗口的原无效标记。
- 有证据确认的控制器、采集器或传输工具超时/失败；不得将 dnsmasq 响应超时或原因不明的失败改称工具问题。

有 dnsmasq 错误回答、响应超时、崩溃或其他产品正确性失败的窗口不适用本条款。同一窗口同时存在工具和产品错误时，也不得通过本条款补测取得通过。无法确定原因时不自动放行。

每个资格判断必须绑定原始窗口、产物身份、错误计数、相关原始文件哈希及理由。不得根据性能好坏、波动大小或比较方向选择补测。

## 一次完整成对补测

1. 先完成原定整轮 110 窗口，完整归档并核对原始数据。不得在看见某个结果后立即替换它。
2. 按原场景顺序、原轮号建立补测清单。一个原配对中任一侧因工具原因无效，则补测整个配对；两侧都无效也只补同一对一次。
3. 保持原配对内顺序：奇数轮为 `c → rust`，偶数轮为 `rust → c`。两侧使用与原轮相同的精确 ELF、测量二进制、配置、负载、预热、持续时间、客户端数、nice/affinity 和健康门。
4. 每个配对最多补测一次。使用新的独立标签、目录和启动记录，不覆盖或恢复写入原窗口目录。开始前确认没有其他设备测试组，重新核对生产与测量产物身份。
5. 补测两侧都有效，才可将这一整对作为该原轮号的有效比较。不得将原始一侧与补测另一侧拼成一对。
6. 补测任一侧仍无效，该配对最终失败；无论再次无效的原因是什么，都不得继续补测。不得因补测结果回退或不显著而再次运行。

健康失败仍按原保护立即停止拥有的测试实例，不操作生产服务。补测条款不授予绕过健康门或产品错误的权限。

## 派生结果与报告

原始 110 窗口仍保留自己的完整结果，包括所有失败。补测另存原始归档、清单、计数、退出码和健康记录。

用于最终比较的派生视图必须有明确映射：每个场景的五个轮号，各自来自原始有效整对或对应的一次有效补测整对。视图仍为 11 场景 × 五对 × 两侧；统计计算、W、配对方向、CPU tick 精度和生命周期 1 ms 门不变。它不是未注明来源的新一次原始运行。

报告同时列出原始窗口数量和无效项、补测配对及顺序、补测结果、最终使用的映射，以及仍失败的配对。原始无效窗口不能因补测成功而从报告消失。既有正确性门和“多数场景可辨别改善”等性能要求不变。

## 工具修复的版本边界

计数口径和负载工具漏发分别作为工具缺陷修复、分别提交并保留复现与负向控制。它们从下一轮开始使用，不混入 E 正在进行的原始运行或本条款下的 E 补测。

E 补测继续使用原测量工具和原窗口校验逻辑；补测控制器仅增加选择既定场景/轮号所必需的能力，并记录脚本哈希。原统计分析器和 C 期望结果不变。
