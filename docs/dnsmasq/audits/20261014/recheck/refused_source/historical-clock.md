# 原审计压力错误与 conntrack 日志：独立时钟复核

本复核支持“原审计的少量拒答与 conntrack 满表有关”这一解释，但不把历史时间相关性写成
已经取得历史逐包 errno。直接的系统调用因果证据来自总报告中的新 C / Rust 配对诊断；
下面是对原审计保留证据的独立补充。

## 数据和方法

输入为原审计五个正式压力窗口的二进制完成记录、保存下来的错误包，以及复核开始前
保留的内核日志（91 条 `nf_conntrack: table full, dropping packet`）。Rust 的 51 个错误
都有报文，独立核对为 REFUSED、ID / 问题保持不变；C 的 17 个错误只有错误完成记录，
没有原错误包，**仍只能称为 17 次回答校验失败，不能补判为 REFUSED**。

客户端完成时间是 `CLOCK_MONOTONIC` 的发送时间加延迟。不能直接拿这个值减 dmesg 时间，
也不能假定二者只差一个固定开机偏移。使用后来 Rust 诊断窗口的只读 syscall 观察器
**首、末两个时钟样本**建立独立仿射映射：

```text
R(M) = R0 + (M - M0) × (R1 - R0) / (M1 - M0)

M0 = 437358849739650 ns       R0 = 437250441260446 ns
M1 = 437528849848046 ns       R1 = 437420399120764 ns
R / M 速率 = 0.9997514820525786
```

`M` 为 MONOTONIC，`R` 为 MONOTONIC_RAW。校准跨 170.000108396 秒；**没有用任何历史
DNS 错误或内核事件调整斜率、零点或挑选子集**。报告固定使用这个模型，后来完成的 C
诊断仅作外部验证，不用于重新优化旧数据匹配。

校准窗口全部 8 个时钟样本相对首末模型的 RAW 残差为 −0.265 至 0 微秒。
另以相同 8 个新样本做 OLS 敏感性检查，回推历史时刻时与首末模型仅差 1.36–2.33 微秒。
这是当前读数的一致性，**不是 40–68 分钟反向外推的严格误差界**。顺序读取多个 clock
没有用成对读数作时间夹限；也不能排除历史期间的频率调整。

新 Rust 诊断中的 6 个实际上游 `sendto(...127.0.0.1:15354)` `EPERM` 与内核满表警告的
RAW 时间差为 −4.214 至 −3.978 ms，中位 −4.184 ms。它表明 dmesg 时间与 RAW 本身还存在
约 4.2 ms 的经验偏移。**这里不声称 dmesg 就是 CLOCK_MONOTONIC_RAW。**

随后 C 诊断的 17 个时钟样本作为外部验证，距 R 校准起点 182–352 秒，
相对固定 R 模型的 RAW 残差为 +0.059 至 +1.496 微秒；没有更新模型参数。C 的 15 个
实际上游 `EPERM` 也全部可在 ±10 ms 内与 15 条不同满表警告匹配，RAW−kernel 差值
为 −4.252 至 −3.908 ms。这验证当前窗口的钟差关系跨两个实现成立，仍不把它当作
历史数十分钟期间时钟频率不变的证明。

## 历史结果

以下时间差是 `R(客户端完成时间) − 最近内核警告时间`，尚未消去上述约 4.2 ms 偏移。

| 原窗口 | 错误完成数 | 已捕获 REFUSED | 差值范围，ms | ±10 ms 内最大一对一匹配数 |
| --- | ---: | ---: | ---: | ---: |
| main-run/08-busy-C | 17 | 无错误包 | −4.221 至 −2.746 | 17 |
| capture-run/02-busy-R | 13 | 13 | −4.493 至 −1.896 | 13 |
| retention-run/01-busy-R | 1 | 1 | −4.021 | 1 |
| retention-run/02-busy-R | 14 | 14 | −4.416 至 −3.502 | 14 |
| retention-run/03-busy-R | 23 | 23 | −4.389 至 +3.373 | 23 |

所有 68 个错误完成在 ±10 ms 内都有满表警告，可构成 68 项一对一时间匹配；放宽为
25 / 50 / 100 ms 不改变该数量。相同的、完全由新诊断取得的 dmesg−RAW 中位偏移
`+4.1837375 ms` 作为敏感性修正后，历史误差范围为 **−0.310 至 +2.288 ms**，仍全部匹配。
这项修正也没有用旧错误拟合。

一项必须保留的歧义：`retention-run/03-busy-R` 序号 `12884972514` 的 ±10 ms 窗内有两条
内核警告，相隔 7.129 ms。未校正 RAW 偏移时最近的是前一条，应用新诊断的经验偏移后
最近的是后一条。时间数据不能唯一指定哪条警告属于这一请求。因此不能写成
“68 条旧请求均获得唯一逐包内核归因”。内核日志也没有 PID / DNS ID，可能被限频，
其余 23 条警告不应硬分配给某个测试请求。

## 固定平移负控制

保持事件序列形状不变，把全部预测时刻统一平移，再做同样的一对一匹配：

| 平移量 | ±10 ms 内匹配数 | ±50 ms 内匹配数 |
| --- | ---: | ---: |
| −5 s | 0 / 68 | 3 / 68 |
| −1 s | 2 / 68 | 3 / 68 |
| −0.5 s | 0 / 68 | 4 / 68 |
| +0.5 s | 0 / 68 | 4 / 68 |
| +1 s | 1 / 68 | 3 / 68 |
| +5 s | 0 / 68 | 2 / 68 |

这说明关联依赖正确的时间位置，而不是任取一个相邻警告就能得到高匹配率。这是探索性
敏感性检查，不是随机化试验，也不据此计算“偶然概率”、p 值或因果置信区间。

## 可复核结论

原来的 **51 个 Rust REFUSED 全部与 conntrack 满表具有很强的时间关联**；17 个旧 C
回答校验失败也有同样关联。这与新诊断的实际 `EPERM`、EDE23、conntrack 增量，以及
精确 C / 最终 Rust 对同类发送失败返回同字节 REFUSED 的控制实验相互支持。
历史报文没有系统调用观察，因此不能声称已直接记录到原来的 51 次 `sendto EPERM`，
也不能把旧 C 遗失的 17 个错误包重新分类。

[historical-clock.json](historical-clock.json)。
复算工具为 [`recheck_clock_correlation.py`](../../../../../../tools/dnsmasq/recheck_clock_correlation.py)。
Git 中没有复制原始内核日志、设备输出或二进制记录。
