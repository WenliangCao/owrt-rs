## 简单、可维护的构建边界

生产 profile 已使用 opt3、LTO、一个 codegen unit、panic=abort、strip；
配方还固定 no-unwind-tables、static PIE 和 RELRO。应用直接依赖只有
仓库内 owrt-ubus，没有发现遗漏 strip 或可直接去掉的重型第三方依赖。
`.text` 自身已约 1.77 MB，即使不合理地移除其余所有文件部分，也达不到
旧 1 MB 目标。这不是不能优化的数学证明，但足以否定“补一个 strip
开关即可通过旧门”的假设。

本轮保持 profile、allocator、功能和 64 MiB 压力边界。没有用 UPX、
重复压缩 ELF、裁功能、换 allocator、nightly/build-std 或未经新功能及
性能资格的 opt-s/z 去满足陈旧门限。既有 std 回溯/unwind 内容不等于
可安全直接删段；不为最多约百 KiB 的潜在节省引入新的工具链维护成本。

最终构建由 `repo_handoff` 单独负责 SDK/target。F4 的首个 frozen-ELF
包装只用于激活修复验证，不充当最终源码编译资格。最终必须实走精确
SDK 的源码 prepare/compile、strip、APK 生成，核验 SDK、配方、源码、
包 metadata 及包内 ELF 的身份。strip 若改变 SHA，后续关键验证绑定
包内最终 ELF；不把 Oracle ELF 或旧 SDK 包体积转签为新产物。

此前设备只读观察有约 54.6 MiB overlay 余量，说明现有几 MiB 的文件
不能直接被描述为“装不下”；这不是当前重新读取的空间，也不能替代
最终安装/回退的空间检查。文件字节与映射 RSS 不相加。最终决策同时
参考已有故障恢复、64 MiB 资源门及最终产物的相关运行结果。
