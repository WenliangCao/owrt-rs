## F3：映射后的 owner 超过 14-bit，P2，新增阻断

在原驱动基础配置（含 `local-ttl=60`、`no-round-robin`）中添加：


再生成 61 条不同的正常 TXT：

### 边界控制与归属

只缩短最后一条 TXT，另外两组回答均合法；同样四方、同样传输对照：

| 最后 TXT 长度 | 最终 MX target 位置 | C 的 Additional owner | 当前 TCP |
| ---: | ---: | --- | --- |
| 193 | `16375 / 0x3ff7` | `fff7`，解码为 example | 与 C 全语义相同 |
| 201 | **`16383 / 0x3fff`** | `ffff`，解码为 example | 与 C 全语义相同 |
| 220，主反例 | **`16402 / 0x4012`** | `c012`，解码为 example | **EOF** |

保留材料中的直接 `target.example ANY` 控制也已核验：四方正常，TCP 为 16,400 B，scratch MX RDATA 起点 16,373，目标名起点 **16,375**。接入缓存 alias 后净增加 27 B，最终 MX RDATA 起点 16,400，目标名起点 **16,402**。[独立直接终点控制与原始身份](audits/20261014/fix6/build/new-boundary-independent.md)

新代码 [cache_engine.rs:1785](../../components/dnsmasq/src/dns/cache_engine.rs#L1785) 按 span 计算 `16400 + 16375 - 16373 = 16402`。其 [1792 行](../../components/dnsmasq/src/dns/cache_engine.rs#L1792) 仅以 `u16::try_from` 检查 16-bit 范围，成功后调用 `record_at`。未变动的 [wire.rs:684](../../components/dnsmasq/src/dns/wire.rs#L684) 明确拒绝 `name_offset >= 0x4000`，返回 `InvalidName`；调用处只将 `Full` 转为 TC，其余错误向外传播。**内部错误路径由已观察布局和冻结源码推得，实际运行直接观察到的是 EOF，日志未单独打印该错误。**

before 按名称选择 owner 写法，Additional 的 `example` 不等于此前 `target.example`，因此写完整 owner，能给出正确回答。本次新映射把这条记录改走越界压缩指针路径，新增失败属于 `3335a978`，不是 main 或原 `record_at` 校验的问题。

C 的 `rfc1035.c:1532–1535` 将 `nameoffset | 0xc000` 写进两个字节；这里 `0x4012 | 0xc000 = 0xc012`，客户端实际读到的 offset 18 正好是 question 内合法的 **example** 标签起点。其 owner、MX target 和配置地址一致，完整包可解码，没有循环、越界或尾部垃圾。**C 的内部溢出在本例碰巧得到正确答案；本报告据实际有效客户端语义裁定，不把畸形 C 回答作为阻断依据。**

修复应保留 F2 的 opaque RDATA 与 raw owner 布局，同时处理映射后不能用 14-bit 指针表示的 owner；本轮没有实现任何产品修复。该主例只需普通 TXT/MX 配置，但依赖较大回答与特定布局，故标为条件性 P2。
