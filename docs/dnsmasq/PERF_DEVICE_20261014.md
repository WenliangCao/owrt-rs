# AX3000T 性能对比：2026-10-14

**在 AX3000T 真机上，Rust 的 UDP 查询 CPU 成本更高，TCP 未命中与 DHCPv4 续租更快；差异随场景变化，不能用一个“整体加速比”概括。** 最终 SDK 原产物与精确镜像 C 共完成 112 个测试窗口，保留 1 个无效窗口及其异常，没有修改产品代码。

- **DNS：** UDP 命中/混合的 p50 分别增加 0.058/0.057 ms，CPU 增加 70.0%/46.5%；UDP 未命中有效稳态子集 p50 增加 0.072 ms、CPU 增加 30.3%（有下述尾部限制）。TCP 未命中 p50 减少 0.212 ms（−11.1%）、CPU 减少 24.6%。TCP 命中延迟/CPU，以及所有 DNS p95 差异均未超过波动。
- **DHCPv4：** 接近现场数量的 6 租约合成组，续租 p50 低 0.154 ms（−28.3%）、组合 CPU 低 12.9%；150 租约组分别低 2.421 ms（−38.6%）和 34.9%。续租 p95 未超过波动。150 客户端首次 DORA 的 p50/p95 低 19.7%/32.3%；6 客户端首次 DORA 样本少，不排名。
- **启动/重载：** 配置停启 p50 增加 1.883 ms（+35.2%）；1000-host HUP 新代可见 p50 减少 5.633 ms（−24.7%）、整轮 CPU 低 23.3%。启动与现场规模 8-host HUP 的 p50 差异小于 1 ms 探测界限，不排名。
- **资源和需要关注的点：** Rust 常见场景主进程 RSS 约多 1–1.5 MiB，TCP 未命中多约 2.25 MiB；TCP 整树 FD 从 C 的 143/151 降到 20/28。UDP 未命中出现一次 4 次计划漏发及最大 174.267 ms 尾部；6 客户端首次 DORA 的 Rust 最大为 19.795 ms、C 为 2.496 ms，两者原因均未定位，不能被稳态数字掩盖。

在所施加的 200 DNS qps / 100 DHCP 操作每秒下，生产 DNS、LuCI 入口和双栈外网的健康探测均成功。常见稳态延迟差为数十微秒到数毫秒，没有证据表明这会让当前家庭日常上网变慢；但短期隔离测量不证明无尾部风险或高负载容量，**“UDP CPU +70%”也不等于“上网慢 70%”**。本轮发现的性能差异和异常仅记录，是否优化留待用户决定。

## 方法与数据口径

采用测前冻结的 [device-safe v3](audits/device-perf-20261014/protocol-v3.md) 和[场景清单](audits/device-perf-20261014/scenarios-lifecycle.json)。每场景五轮配对，顺序为 C/R、R/C、C/R、R/C、C/R；同组使用完全相同的输入和负载。发生器、受控上游与采样器在本机隔离网络内，计量它们各自的 CPU，**不计入 dnsmasq 服务 CPU**。修订后的采样器每秒最多扫描一次 `/proc` 建立进程关系表，避免旧工具对每个子进程重复扫描；工具身份与校准见 [device-v3-tools.json](audits/device-perf-20261014/device-v3-tools.json)。

- DNS：固定 200 qps，5 秒预热、20 秒正式窗口，800 个热名字，A/AAAA 70/30；cache 1000、TTL 120、受控上游延迟 1 ms。UDP 32 个客户端；TCP 8 条连接，每 100 个答复重连。命中场景先用 UDP 预热父进程缓存；混合场景为 80% 热名字/20% 唯一名字。上游计数用于核验实际命中/未命中。
- DHCPv4：150 个合成客户端增长组，以及另行测前登记的 6 客户端现场规模组，均为 100 次操作/秒；预热先完成全部客户端 DORA，再续租；正式 20 秒只测 2000 次 REQUEST/ACK。独立 namespace 内的静态映射和 `no-ping` 排除了真实网络、冲突探测、动态地址搜索以及 helper/ubus 开销。
- 启动/重载：每轮 20 次、至少间隔 1 秒。小规模为 8 个合成 hosts 名字和 6 条租约；扩展 HUP 为 1000 个名字和 150 条租约。小规模匹配现场数量，不冒充真实地址族/别名拓扑。每次改变 marker，确认新一代答复可见。配置修改按停启实例测量，**不是宣称 SIGHUP 会重读主配置**。

表中数值为五轮中位数 **[最小值, 最大值]**。比较相对中位差与两版相对全距的最大值 `W`，只有差异绝对值大于 `W` 且至少 4/5 配对同向才判快慢；CPU 另要求每轮至少 10 ticks、中位差超过 8 ticks。否则明确为“未超过波动/计量精度”。每窗不足 10,000 条，不报 p99。200 qps/100 次操作每秒是施加的负载，**不是最大吞吐或容量结论**。

DNS 延迟从实际发送至正确答复计时，另保留计划发送至完成延迟与发送滞后，避免隐藏发生器调度成本。CPU 取 PID/starttime 一致且 TCP 子进程已回收后的端点差，包含父进程与已回收子进程；跨越预热和 drain 时分母同样覆盖全部正确操作。资源表只取正式窗口每秒采样。设备无 smaps 接口，**PSS/USS 不可测**；RSS 包含共享映射，整树 RSS 还可能重复计算共享页，RssAnon 也不是 USS。

## 生产健康与方法修正

v3 用生产服务健康决定停测。测前实际 125 秒基线取得 48 次 DNS 答复（p95 0.543 ms、最大 0.715 ms）和 23 次 HTTP 检查（p95 70.548 ms、最大 99.122 ms）。运行中已有本地 DNS 约每 2 秒查询，错误/700 ms 超时立即停止测试，连续三次高于测前冻结的 200 ms 也停止；LuCI 无认证入口每 5 秒检查、700 ms 期限（已核对的 HTTP 403 是预期状态，不代表验证了登录后全部功能）；Mac 每 30 秒检查 IPv4/IPv6 HTTPS。另核对生产 PID/starttime、WAN 路由，MemAvailable 64 MiB 是防耗尽底线。整机 CPU 仅记录，不能作为被测服务 CPU 或产品性能结论。

旧 v1/v2 的两次整机 CPU 门中止和旧 C 校准均保留，不计入 v3 五轮配对。用户明确指出生产 DNS/LuCI/外网当时正常，要求以服务健康为准继续；因此在正式 C/R 配对前冻结 v3，降低采样器开销并取消自行设定的 35% 整机门。旧窗口不能定位全部工具开销，不用新数据倒推其精确根因，也不把旧停止写成产品故障。

两个守卫阶段共 3978 个状态样本；在无测试组的窗口间更新守卫期限。实测结果如下，健康检查通过不等于延迟完全不变。
