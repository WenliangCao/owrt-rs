# fix/audit-20261011 独立合并审计

审计日期：2026-10-11。产品提交：`6b8eee96eda8aaa4cc47580530e5f287baeaaaa4`；
比较基线：`main=be531cee49e366bb5044443d473944dbea45b87e`。

## 结论

**当前不能合入 main。** 已复现两个明确的新增阻断：正常 SDK 源码打包无法链接（F01），
以及 TCP 缓存优先级改变后返回错误记录（F02）。多 MAC 租约交接虽然已能 ACK，
但 DHCP 脚本回调合约仍未完整修复（F03）。这些不是仅凭源码猜测的问题。

原修复有实质价值：信号不再杀死服务，ALRM 确实恢复失败的租约持久化；Rapid Commit
采用最终地址池标签和 hosts 权威名；大 hosts 文件不再按文件长度临时分配；异常 TCP
问题恢复 REFUSED。不能据此把整个分支判为通过，或把大量通过的普通用例用于抵销反例。

合并前至少应修复 F01、F02，修正 F03 的 helper 策略并补齐实际脚本回归，再对修正后的最终产物复核。
即使完成这些修改，本报告也不授予物理路由器替代资格；实际 RELRO、体积预算及目标设备
资源验收仍有边界。仓库目前没有把 dnsmasq-rs 纳入默认镜像替换清单，这也不能成为
将已确认新增回归合入 main 的理由。

本轮没有改产品代码、没有接触物理路由器、没有推送 GitHub；保留了原工作区的未提交文档。

### F01 — 实际 SDK 源码构建失败，包测试漏掉 eval 层

位置：[Makefile:84](../../packaging/openwrt/owrt-dnsmasq/Makefile#L84)。
`DNSMASQ_STATIC_PIE_CC="$$(command -v "$(TARGET_CC_NOCACHE)")"`
在 `$(eval $(call BuildPackage,dnsmasq))` 中先展开一次，运行 recipe 时再次展开；
`$(command -v …)` 被当成 Make 变量，而没有送给 shell。

实际 `compile.log:114` 出现 `DNSMASQ_STATIC_PIE_CC=""`，随后 linker helper 报
`DNSMASQ_STATIC_PIE_CC must name the actual SDK compiler`；make 退出 2，未产生 ELF/APK。
这不是 SDK 缺编译器：同一个复制 SDK 上，main 成功编译、链接、strip 并生成 APK。
main 的**整个审计工具**最终因打包 ELF 与传入的 oracle_build ELF SHA 不同而失败，
该身份门失败原样保留，不能把 main 控制写成全流程通过。
[实际命令、SDK 身份、日志摘录及原日志哈希](audits/20261011/independent/build_package.json)。

本地无需 SDK 的秒级复现：

```sh
python3 docs/dnsmasq/audits/20261011/independent/build_eval_repro.py
```

同一配方直接展开 `Build/Compile` 得到绝对路径，通过 `BuildPackage-eval` 则得到空串。
[复现结果](audits/20261011/independent/build_eval_repro.json)与真实 SDK 一致。
新测试 [test_build_package.py:288](../../tools/dnsmasq/test_build_package.py#L288)
把 `package.mk` 留空，直接调用 `Build/Compile`，所以 20/20 通过没有验证这条真实路径。

影响准确限定为默认 **compile-and-package**。`oracle_build.sh` 不经过这个 Make eval，
能构建本轮实验 ELF；`--frozen-elf` 打包旁路也能工作。后者本轮生成并提取了正确 SHA
的 APK payload，通过 ELF、metadata 和身份检查，最终仅在 F05 的预算门失败。
修正应针对实际 SDK 展开语义，并保留一项经过 `BuildPackage` 的回归；单测或旁路成功
不能关闭此发现。

### F02 — 修复负缓存遮蔽时，将旧 UDP 优先级错误扩展到 TCP

位置：[main.rs:2790](../../components/dnsmasq/src/main.rs#L2790)（debug）及
[main.rs:2811](../../components/dnsmasq/src/main.rs#L2811)（通常路径）。
本次把 `local_tcp_answer/tcp_view_local_answer` 提到动态 cache 之前。
对于已有的动态 CNAME，本地 TXT 能提前返回，绕过缓存中应遵循的别名链。

最小配置的关键项：

```ini
cache-size=32
cache-rr=TXT
txt-record=alias.test,alias-local
server=127.0.0.1#15354
```

1. UDP 查询 `A alias.test`，隔离 stub 返回 `alias.test CNAME target.test` 和 target 的 A。
2. UDP 查询 `TXT target.test`，stub 返回 `target-upstream`，将其缓存。
3. TCP 查询 `TXT alias.test`。

| 实现 | 实际 TCP 回答 |
| --- | --- |
| 精确镜像 C | `alias.test CNAME target.test` + `target.test TXT target-upstream`；2 answers，flags `0x8180` |
| main | 与 C 完全相同的报文字节 |
| 修复分支 | `alias.test TXT alias-local`；1 answer，flags `0x8580`（AA=1） |

`-k` 和 `-d` 均复现，三个实现预热回答一致，直接查询 target 的 TXT 一致，均只发生两次
上游查询，进程健康。因而不是网络抖动、上游不同、未填缓存或仅 DNS 压缩编码差异。
[完整报文](audits/20261011/independent/dns_hosts_cname.json)、
[解码与三方断言](audits/20261011/independent/dns_hosts_cname_summary.json)、
[复现脚本](audits/20261011/independent/dns_hosts_cname.py)。

旧 main 的 UDP 已有同样错误，这不能消除本分支新增的 TCP 回归。修复应同时保留 DHCP
新发布 A 优先于旧 NXDOMAIN 的需求，以及 CNAME／具体 RR 的正确查询顺序；简单恢复
全部 cache-first 会重新引入本次试图解决的问题。

### F03 — ACK 正确，但 DHCP 脚本的外部合约仍不正确

位置：[daemon.rs:2391](../../components/dnsmasq/src/dhcp/daemon.rs#L2391)、
[daemon.rs:2537](../../components/dnsmasq/src/dhcp/daemon.rs#L2537)。
state 修复后能复用另一 MAC 占用的同一静态租约，但 `helper_new_lease` 仍按状态转换前
“当前客户端无租约”计算；`do_classes` 还把所有报文的 option 50 当成更新理由，未限定
DHCPREQUEST。matching C 只在实际新分配，或 REQUEST 含 option 50 时刷新这些数据。

配置 `dhcp-host=02:00:00:00:00:01,02:00:00:00:00:02,127.0.0.30,dual`
及捕获 `dhcp-script`，固定租约名 `dual`，排除客户端更名合法触发脚本的解释。
MAC 01 先 REQUEST，携 vendor=`original`、hostname=`first`；等待首个 `add` 完整执行。
MAC 02 再 Rapid Commit（option 50 有／无）或无 option 50 的 RENEW：两边均 ACK、
租约均交接、均触发 `old`，但 C 带 `DNSMASQ_DATA_MISSING=1`，不再带一次性 vendor/name；
Rust 却带 vendor=`replacement`、supplied-name=`second` 等新数据，没有 DATA_MISSING。
SELECTING REQUEST 含 option 50 的控制组完全一致。

另一个同源策略错误：MAC 01 自身再次 Rapid Commit、带 option 50，C 不再调脚本，
Rust 多一次携新数据的 `old`，即使没有 `script-on-renewal`。此子情形在 main 已复现，
**不是本分支新增**。四种跨 MAC 交接在 main 则根本无第二个 ACK；修复后的错误 helper
数据属于成功路径打通后的集成遗漏。
[修复分支完整事件](audits/20261011/independent/dhcp_helper_fix.json)、
[main 控制](audits/20261011/independent/dhcp_helper_main.json)。

影响不是推测内部状态：脚本实际收到的环境及调用次数不同，argv 也一并保留。镜像附带的
[dhcp-script.sh](../../packaging/openwrt/owrt-dnsmasq/files/dhcp-script.sh)会把 `old` 作为
hotplug `ACTION=update`，并转发 DNSMASQ 环境；自定义 hook 可依这些字段选择分支。
本轮未运行真实 hotplug 消费者，不声称已证明防火墙或真实业务配置被破坏。

[复现脚本](audits/20261011/independent/dhcp_handoff_helper.py)显式等待异步 helper 完成并
在 daemon 存活时捕获事件，完整记录每包输入、回复、租约与 DNS。初次完整环境捕获曾因
过早停止进程而漏读回调，该尝试被判无效；最终证据已加等待门并重跑，不能使用早期
不完整结果。源码依据、复现命令及正常 130 场景清单见
[DHCP 审阅记录](audits/20261011/independent/dhcp_review.md)。

### F04 — ASLR 恢复，但 GNU_RELRO 仍没有实际保护

本轮三次独立启动最终 static PIE，装载基址不同，实际 `/proc/PID/exe` SHA 正确，
没有映射共享库；stack 不可执行，没有 WX 映射。但是 GNU_RELRO 覆盖页三次均为 `rw-p`；
同环境精确 C 的对应页三次均只读。
[ELF 与实际映射证据](audits/20261011/independent/build_protections.json)、
[Rust 映射](audits/20261011/independent/build_rust_mapping.txt)、
[C 映射](audits/20261011/independent/build_c_mapping.txt)。

这是已披露、相对镜像 C 仍存在的防护差距。
[上一轮 static baseline 映射](audits/20261011/fixes/static_pie/build_protection.json)也可写，
因此不列为新退化；本次没有重新测量 main 的运行时 RELRO。
A07 的“恢复主映像随机化”目标已实现；不能据 ELF 的 GNU_RELRO header 或 `-z relro/now`
宣称与 C 等价的完整运行时保护。本轮未做漏洞利用实验，没有远程执行漏洞结论。

### F05 — 文件成本继续增加，最终 APK 仍不符合已有预算

新 ELF 比本次 main 增加 **82,360 B（4.18%）**，是镜像 C ELF 的 **7.62 倍**。
真实 `--frozen-elf` SDK 包为 **1,113,791 B**，payload SHA 与本次实验 ELF 完全一致。
[实测打包证据](audits/20261011/independent/build_package.json)。
现有 [m5_final_budget.json](../../tools/dnsmasq/m5_final_budget.json)规定 ELF ≤1,000,000 B、
APK ≤700,000 B，没有这份 ELF 的例外；工具实际以两项超预算失败。

预算缺口早已存在，不能都归因于 static PIE；此次也没有新增资源预算授权。
上述为 ELF／APK 文件长度，不能当作 squashfs、整个 flash 或 RAM 的倍数。
main SDK 产物经过 strip，候选 frozen 路径保持原 ELF，所以不将两次 APK 的差额当成
精确的同工艺链接成本。运行期 CPU、延迟和 PSS 使用下面的独立窗口判断。

### F07 — 普通 addn-hosts 非法名称缺少错误诊断

普通 `addn-hosts` 文件第6行有100,000字节非法名称时，C 输出 `bad name` 及行号，
Rust 仅报 accepted names 总数；相同文件经 `hostsdir` 两者均报错。合法记录仍可解析。
当前 [hosts.rs:312](../../components/dnsmasq/src/hosts.rs#L312)丢弃 invalid 回调；main 的
普通读取同样只累计 bad_names，没有日志输出。这是操作员难以定位被忽略记录的既有
诊断遗漏，不是此次流式解析新增的数据丢失。
[结果](audits/20261011/independent/dns_hosts_probe.json)、
[复现工具](audits/20261011/independent/dns_hosts_probe.py)。

### 已观察、没有判为缺陷的 EDE 差异

`neg-ttl=1,use-stale-cache=30` 下，先缓存 `client AAAA NXDOMAIN`，等待2.1秒，
DHCP ACK 发布 `client A 127.0.0.30`，再带 EDNS 做 TCP A 查询。C 和 fix 都返回正确的新
DHCP A；C 附 EDE 3（stale answer），fix 没有，`-k/-d` 均复现。
[报文](audits/20261011/independent/dns_hosts_stale.json)、
[复现工具](audits/20261011/independent/dns_hosts_stale.py)。

匹配 C 的 `rfc1035.c:1754` 先读旧 NXDOMAIN 并设置 stale 位，随后改用新 DHCP A，
`forward.c` 又依残留位追加 EDE；本例答案并没有使用过期 RR。没有证据要求 Rust 复制
这个可能误导的提示，也未证明消费者受损，因此撤销初审的P3候选，不计入缺陷清单。
该探针上游只有UDP，没有验证TCP stale-refresh及最终缓存状态，不能扩大通过范围。

## 性能和资源复核

预先冻结的主计划为5场景×3轮×2实现，共30窗：UDP hit、TCP hit、TCP miss、DHCP周期、
并发reload。为覆盖新增每次UDP上游发送／应答时的统计热路径，另在执行前冻结3轮UDP miss
共6窗。补充计划不替换原窗口。每窗预热10秒、测量30秒，无饱和段，daemon／上游／
生成器／控制分别固定CPU 0／1／2／3；全部顺序执行，三轮顺序为 main→fix、fix→main、
main→fix，同轮同seed。基础daemon均feature-off，使用本报告开头的最终ELF。

[30窗计划](audits/20261011/independent/performance_plan.json)、
[UDP miss补充计划](audits/20261011/independent/performance_udp_miss_plan.json)以及各自的
[运行工具](audits/20261011/independent/performance_run.py)、
[补充工具](audits/20261011/independent/performance_udp_miss_run.py)绑定输入SHA与每窗命令。
负载窗口期间持有共享构建锁，开始前检查其他实验负载。没有覆盖失败窗、丢弃较差结果或重跑至通过。

超过两组W且三个配对均变差，才触发成本筛查标记。额外检查所有已发请求错误、实际吞吐、
生成器限制与scheduled_skipped；预定零skipped门槛不通过时不能宣布性能通过。这个规则
