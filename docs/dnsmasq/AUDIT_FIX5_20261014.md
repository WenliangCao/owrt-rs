## 结论

**目前仍不能合入 main。** FIX4 的 F1 原始 `c00c` / `c02b` 反例确已修复，含旧 Local anchor 的 **16/16** 个控制均与精确镜像 C 的完整响应语义相同。但 `5b914d32` 引入了一个新的 **P2 条件性阻断 F2**：多个 raw CNAME 后的压缩指针会落到错误的最终报文位置，返回无法解码的 CNAME。精确 C、main、修复前 d956 均给出相同的合法客户端答案，当前 HEAD 则在普通/debug、UDP/TCP 全部失败。

这是实际新增的坏回答，不是 main 原有问题，也不是仅凭静态疑似否决。原 F1 可按原复现关闭，不能据此宣称 raw 终点修复已完整或分支可合并。其余本轮定向回归、构建和普通单测没有发现另一个新增阻断。

合并标准与 [FIX4](AUDIT_FIX4_20261014.md) 一致：**同一传输的精确镜像 C 是语义标准；main 用于归属判定；main 原有问题不阻止本次差分合并。** 本轮没有沿用旧 main-only 性能否决标准，也没有把旧审计/修复者的通过声明当作本轮运行结果。

## F2：raw CNAME 游标使后续 opaque 指针失效，P2，新增阻断

### 可独立复现的主例

先通过上游预热 `alias.example A → CNAME target.example + A`，再查询 `alias.example ANY`。额外配置如下，**不加 host anchor**：

```text
dns-rr=target.example,5,c062
dns-rr=target.example,5,056f74686572076578616d706c6500
dns-rr=target.example,5,056f74686572076578616d706c6500
dns-rr=target.example,5,056f74686572076578616d706c6500
```

三个未压缩 RDATA 都是 `other.example`。C 按反向配置顺序写 raw 记录，所以指针记录排最后。这里四条 target CNAME **都指向同一个名字**，主阻断没有依赖 CNAME+NS/A 同 owner 混用。为了区分 main 既有额外转发和真正客户端回归，上游对 ANY 提供与 C 相同的 AA CNAME 链/重复 RR，TTL 为 300/60；全部流量保留在证据中。

| 角色 | 客户端最终应答 | 长度 | final 上游请求数 |
| --- | --- | ---: | ---: |
| 精确 C | 合法：alias→target，四条 target→other | 154 B | 0 |
| main | 与 C 完整语义相同，含 TTL | 223 B | 1 |
| d956，旧 SDK / 本轮同配置 release | 与 C 完整语义相同，含 TTL | 209 B | 0 |
| 当前 HEAD | 第五条 CNAME 无法解码，其余字段相同 | 196 B | 0 |

前三轮采用旧 SDK before，每轮四个 fresh normal/debug × UDP/TCP 案例，**12/12** 重现；再用本轮同构建方式编译的 d956 重跑，**4/4** 结果相同，排除了 strip/构建配置差异。64 次主例 daemon 运行均存活、退出 0，TCP 关闭后健康查询正常。这是条件性的坏客户端答案，**不是 daemon 崩溃或所有 DNS 查询故障**。

独立审查者另外用新写的 decoder 从第一组 raw hex 复算四方全部 header、question、完整各节、RR 顺序、名称、类型/class、TTL 和 RDATA，没有使用驱动的 canonical 比较字段。C/main/before 全部相等；当前第5条的 `c062` 在 offset 98 读到 **`0x70`（ASCII `p`）**，既不是合法标签长度也不是压缩指针。C 同一位置是完整的 `other.example`。TTL 严格为 `[300,60,60,60,60]`，没有按时间差豁免。[完整独立报文、解析布局和校验](audits/20261014/fix5/dns/independent-cname-result.json)、[独立说明](audits/20261014/fix5/dns/independent-review.md)、[两次重复](audits/20261014/fix5/dns/extended-recheck.json)、[同构建方式重跑](audits/20261014/fix5/dns/same-profile-recheck.json)

### 原因与归属

[cache_engine.rs:1780](../../components/dnsmasq/src/dns/cache_engine.rs#L1780) 开始原样复制 RDATA，但 [1808–1814](../../components/dnsmasq/src/dns/cache_engine.rs#L1808) 仍把可独立解码的 **raw TYPE5** 当成正常 CNAME 遍历，更新 `previous_name/previous_offset`。之后仍属于 `target.example` 的 raw RR 在 [1781–1796](../../components/dnsmasq/src/dns/cache_engine.rs#L1781) 改为写完整 owner，导致报文偏移变化；最后的不透明绝对指针仍是 `c062`，于是指向 owner 中间。

精确匹配 C 的 `rfc1035.c:1862–1872` raw loop 始终传入 `offset=NULL`，`1610–1617` 的 `"t"` 分支仅复制 bytes；**raw TYPE5 不移动 C 的 owner 游标**。只有实际遍历 CNAME 的路径传入 `&nameoffset`。对应参考文件 SHA 和源码行已独立核验。

必须拆开旧因与新增影响：raw TYPE5 游标偏差原来就有，但旧 helper 会在 scratch packet 中把该 `c062` 展开为正确的 `other.example`，客户端仍与 C 相同。本次改成最终包内原样复制后，旧布局偏差变成了实际坏指针。因此这是 **`d9565f46..5b914d32` 新引入的回答回归**，不能作为 main 既有问题豁免。

另有含 NS/CNAME 和 host anchor 的 Local 路径控制，最终驱动复跑 4/4 同样 main=before=C、HEAD malformed；只作机制/路径补充，不作为主例的配置合规性依据。[控制配置](audits/20261014/fix5/dns/candidate-profiles.json)、[结果](audits/20261014/fix5/dns/extended-recheck.json)

修复需要同时保持 opaque RDATA 和 C 对 raw TYPE5 的游标语义，并保留真正配置 CNAME、SOA、反向合成的现有次序。本轮没有实现修复。完整可复制 argv、profile、原始 private 路径和 SHA 见 [DNS 复现说明](audits/20261014/fix5/dns/README.md)；其中 [同配置主例命令](audits/20261014/fix5/dns/same-profile-invocations.json) 可直接选择新输出目录重跑。

## 范围限制与收尾

- 这是当前单提交增量及其调用交互的独立复核；没有重跑 FIX4 的所有 DHCP/helper/TFTP/hosts/配置族，也没有证明完整 DNS 行为等价。main 原有 O1/O2、体积预算问题按既定标准不否决本次差分合并。
- 本轮运行的是当前源码 fresh Cargo release，经固定 SDK linker 构建；**未 fresh 完整 SDK prepare/strip/APK 打包**。当前和同配置 before ELF 都为 2,056,672 B，但不能用它与旧 strip SDK 直接推导产品体积变化，也不声称已生成包含本次修复的 APK。
- 未重跑三方性能窗口、长期 fuzz/soak、23 个 ignored、OOM/allocator/mprotect fault、全部 TTL/stale/时钟与并发 reload 交错。FIX4 性能数据只属于其旧 SHA，本轮不把它冒充当前数据，也不凭实现推测宣称零开销。
- F2 需要显式手写 raw 指针和重复 CNAME 配置，属于窄条件边界；主例 C 输出可完整解码且重复 target CNAME 同值。没有以 C 自己输出的 `c0ff` 畸形报文作为阻断依据。
- 未修改产品代码、未操作物理路由器、未部署/刷机、未合并、未推送。用户原有未提交提示文档保持原样。镜像、ELF、rootfs overlay、完整运行日志留在 private；Git 仅存工具、无秘密身份清单及派生报告。
