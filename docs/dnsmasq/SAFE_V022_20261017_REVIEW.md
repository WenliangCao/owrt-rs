# v0.2.2 安全边界审阅

**1 处 FD 隔离缺口已关闭，复核到 `b8617f57` 未发现新的阻断问题。**
本记录覆盖 `79849777` 的 platform 公共 API、残余 unsafe 及调用方，再核对
`7deed209` 修复和 `b8617f57` 四文件窄改；仅复核源码和已有证据，没有重跑验收。
结论限于固定 OpenWrt AArch64 musl 与已检查的 Linux64 调用路径，不是形式化安全证明。

## 已关闭的问题与编译约束

原 `close_range(CLOEXEC)` 失败分支只遍历当前 `RLIMIT_NOFILE` 软上限，可能遗漏
在降低上限前已打开的高位 FD。`7deed209` 删除该 fallback，任何错误都阻止 exec，
不会带着未隔离的描述符继续启动。固定目标内核须支持此操作。

`b8617f57` 的三个边界调整符合既有约束：

- `close_file` 将 `File::into_raw_fd()` 的唯一关闭责任交给 rustix `try_close`；
  调用后无论成功失败都不再拥有该 FD，不重试 Linux 的 EINTR。
- libc variadic `syscall` 明确提供六个 native `c_long` 参数槽，未用槽置零；
  `close_range` 的范围和 CLOEXEC 标志不变。
- 移除未使用的 rustix `runtime` feature；不依赖版本哈希命名的实验模块或其私有
  `runtime` alias。固定 `_exit` 仍使用 libc 的 async-signal-safe 接口。

业务 `src/lib.rs`、`src/main.rs` 两个根均设置 `#![forbid(unsafe_code)]`，结合主代理
已完成的 `aarch64-unknown-linux-musl --all-targets` 零警告检查，验证这些根覆盖的业务
代码及其已编译测试没有 unsafe。该约束不能证明 platform、依赖库或内核没有缺陷，
也不把未编译的其他平台 cfg 算作已验收。

## 保留边界及理由

| 边界 | 保留原因与核对的约束 |
| --- | --- |
| datagram / socket options | rustix 1.1.5 未覆盖所需 pktinfo ancillary 和少数选项。保留单 iovec、32/40 字节 align-8 存储及固定选项；长度有界，FD 借用，不复制 payload。LP64 MsgHdr 的 musl 小计数字段及零高位与原 ABI 一致。静态 IPv4 仍跳过 pktinfo；TRUNC/CTRUNC、零端口和 send-once/EINTR 策略由业务层保留。 |
| interfaces | getifaddrs、特定 ifreq/ARP ioctl 和任意字节接口名不能直接用 rustix 的 UTF-8 名称 API 替换。列表由 RAII 释放，visitor 的借用名字不逃逸；固定布局/长度与借用 FD 留在边界内，包路径不新增临时 control socket。 |
| process / self-exec | NSS 使用 reentrant 查询后复制值；libc credential 操作保留进程级语义。固定 pre-exec hook 只执行信号/FD 系统调用，保留 std 的 exec-error pipe，其他 FD 在 exec 时关闭。inherited_pipe 先创建新 duplicate 再建立 OwnedFd，并核验 FIFO/读写方向；没有对任意原始 FD 冒认所有权。 |
| daemon startup | 仅专用启动路径保留 libc fork。检查单线程及无共享可写映射，父进程和中间进程只报告后 `_exit`，不会返回并析构服务的复制状态。此论证仍依赖当前调用图没有第三方 atfork 回调或执行任意 Rust 的信号处理器，不能推广为任意上下文的通用 fork API。 |
| signals / poll | 固定 handler 只使用目标上的锁自由原子、一次非阻塞 pipe write 或 `_exit`；write 前后保存 errno。poll 的负数/已关闭 FD 快照及 POLLNVAL 必须接受普通整数，不能伪造活跃 BorrowedFd。pollfd 数量、存储和生命周期有界。 |
| libc text / resolver / limits / RELRO | 保留镜像 libc 的名称解析、格式和 sysconf 语义；输出由调用方拥有或在 libc 结果存活期间复制。静态 PIE 的 phdr callback 和 mprotect 仅处理检查过的主镜像 RELRO 完整页；未把任意地址保护操作暴露给业务代码。 |

## 现有证据与尚待裁决

原 `79849777` 的四个 main test-harness self-exec 失败仍保留，不能改签通过。
`7deed209` 同时修复测试入口与启动帧写失败后的 `startup_pending` 清理；原命令 pipe
仍打开时注入 EBADF 的回归确认子进程能终止并回收。已有 Oracle 窄门为 **40/40、
0 警告**，只覆盖这次修复，不等于最终完整 native、44 组/67 项正确性或真机验收。
对应 private 结果为 `private/oracle-v022/native-7deed209/result.json`，SHA256
`4ee2577fa3a86852cf81f0c9fae68fb78050343fa9d1aabc52052abd5d4c3d17`。

helper/resolver 的改动有实际成本：helper 多一次 exec、child 保留两个额外 duplicate FD；
resolver 多一次 exec，child 增加三个 pipe FD，parent 在发送请求期间持有临时 writer。
因此不能把整轮迁移描述成纯包装等价。最终 native/正确性、新源码 PGO、体积，以及
K 对照真机 CPU/FD/启动与 helper/resolver 场景仍须独立验收；本审阅不提前接受这些结果。
