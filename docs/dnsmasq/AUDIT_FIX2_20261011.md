## 结论

**暂不建议合入 main。** 原 SDK 构建、缓存优先级、helper 元数据、运行时 RELRO 和普通 hosts 诊断等修复有实质效果；本轮另外确认了 **P2 新增启动峰值内存回退 R5**：10,000 条合法 host-record 下，三轮峰值 RSS 中位数 10,832 → 14,200 KiB，增加 3,368 KiB（31.09%）。源码显示新增初始 cache reload 重建／深拷贝配置 hosts 索引时，旧索引尚未释放，与实测峰值增长一致。基于避免这项可消除、随配置规模增长的重复初始化成本，我建议先修 R5 再合并。

这是审计者的工程判断，**没有触发预先约定的启动 RAM 硬门限**；本轮未证明当前部署配置达到该规模、目标设备 RAM 不足或服务启动失败。绝对增量约 3.29 MiB，稳定 RSS 仅增加 192 KiB，影响边界在 R5 中展开。

固定的 54 个普通业务窗口没有触发预设的 main 回退判据，但 UDP miss、TCP hit、DHCP 的 CPU 中位数分别上升 15.06%、18.04%、13.58%，受配对方向或波动影响，只能标为疑似，不能据此宣称“性能没有退步”。ELF 另增 4.39%，原 ELF/APK 预算仍失败。

R1/R2 的功能缺口和 R3 的原预算越界在 main 已存在，不把它们冒称为本分支新增阻断；R4 是低影响诊断差异。本次暂缓合并的明确新增依据是 R5。合并前应消除重复初始化的峰值成本，并复核普通 hosts、恢复租约、helper 与 DHCP 启动门控，保留本轮已经验证正确的行为。

合并修复代码与通过替换验收分别判断。此次没有合并 main、推送 GitHub、修改产品代码或访问物理路由器；原工作区未提交文档保持不变。

### R5 — 新初始化流程增加配置规模相关的峰值内存

位置：[main.rs:884](../../components/dnsmasq/src/main.rs#L884)、[main.rs:935](../../components/dnsmasq/src/main.rs#L935)、[main.rs:3193](../../components/dnsmasq/src/main.rs#L3193)、[main.rs:3203](../../components/dnsmasq/src/main.rs#L3203)、[main.rs:3572](../../components/dnsmasq/src/main.rs#L3572)、[Hosts 的 Clone](../../components/dnsmasq/src/hosts.rs#L61)。

最终分支先创建 configured hosts，并克隆给 daemon；新的 `initial_cache_reload` 又调用 `reload_hosts_data()`，重新构建配置索引并 `hosts.clone()`。`Hosts` 的 entries、forward 键／值和 non-terminals 都深拷贝。新两份就绪后才依次赋值释放旧 daemon/local 索引；main 的初始事件只发送读入通知，没有这次重建。这支持新增暂态分配的因果解释；本轮没有做 allocator 调用栈归因。

在固定性能窗口及补充检查结束后，另行冻结 0/1,000/10,000 条正常 `host-record=nNNNNN.test,192.0.2.1` 配置，三种实现、三轮轮转，共 27 次启动。10,000 条配置文本仅 340,165 B。等待初始 cache reload 日志后发送一次普通 UDP 查询，再取五次空闲 status/smaps；没有持续流量、资源限额或 OOM 注入。每次回答正确，同配置报文逐字一致，全部正常退出，五次空闲读数均稳定。

| host-record 数 | C 峰值 RSS KiB | main 峰值 RSS KiB | 最终分支峰值 RSS KiB | 最终分支 − main |
| ---: | ---: | ---: | ---: | ---: |
| 0 | 1,116 | 1,924 | 1,988 | +64 KiB |
| 1,000 | 1,328 | 2,836 | 3,132 | +296 KiB（10.44%） |
| 10,000 | 3,120 | 10,832 | 14,200 | +3,368 KiB（31.09%） |

以上为三轮内核累计 `VmHWM` 中位数；10,000 条时 main 三轮为 `[10832,10828,10832]`，最终分支 `[14200,14200,14220]` KiB。相同配置下稳定 RSS 仅 10,340 → 10,532 KiB，稳定 PSS 10,332 → 10,524 KiB，因此**确认的是启动暂态峰值回退**，不是新增长期泄漏。没有复现 OOM，也不外推目标设备必然无法启动。

对资源受限的目标，这是明确新增的启动内存需求；0 条基线只有 +64 KiB，而增量随记录数扩大，不能由 static PIE 的固定映像成本解释全部差额。建议避免初始配置索引重复构建／同时保留深拷贝，并重新验证配置记录和普通 hosts 的初始化先后关系。

证据：[分组数组及中位数](audits/20261011/fix2/build/startup-resources-summary.json)、[27 次结果](audits/20261011/fix2/build/startup-resources.json)、[预冻结计划](audits/20261011/fix2/build/startup-resource-queue.json)、[探针](audits/20261011/fix2/build/startup_resources.py)、[324 份原始文件摘要](audits/20261011/fix2/build/startup-raw-index.json)。它是独立的追加假设验证，没有替换原 54 个性能窗口。

### R1 — cached CNAME 的动态终点漏查配置记录

位置：[local.rs:258](../../components/dnsmasq/src/dns/local.rs#L258)、[cache_engine.rs:564](../../components/dnsmasq/src/dns/cache_engine.rs#L564)、[cache_engine.rs:595](../../components/dnsmasq/src/dns/cache_engine.rs#L595)。

正常配置 `txt-record=target.test,local-target`，上游对 `alias.test A` 返回 `alias.test CNAME target.test` 和 target 的 A。先查询 A 建立动态别名及终点缓存，再查询 `alias.test TXT`。精确 C 跟随别名后返回本地 `local-target`，不再转发；Rust 再访问上游，返回 `upstream-value!`。MX/SRV 的本地终点也有同类遗漏，可能得到错误的邮件／服务目标。不存在异常报文或进程崩溃。

`CnameTarget::Local` 分支调用 `append_local_terminal`；动态终点分支重新按 qtype 查缓存并处理 interface/synthetic 情形，却未查终点的配置 TXT/MX/SRV。[仅配置这些 RR 的名称](../../components/dnsmasq/src/dns/cache_engine.rs#L1832)不会把动态 A 终点分类为 `Local`。匹配 C 则在跟随 CNAME 改名后继续执行本地 RR 处理。

**归属已经用 main 实测。** target-only 的 TXT/MX/SRV × UDP/TCP × 普通/debug，共 12 场景，main 与最终分支都有遗漏；另 4 个 alias/target 同时配置 TXT 的场景中，main 错答 alias-local，最终分支错答 upstream，两者均不等于 C。这不是 main 正确而 HEAD 变错的证据。

原 F02 的“终点 TXT 已在动态缓存，alias 配置 TXT”控制 4/4 通过；额外 RD=0/1、DO=0/1 × UDP/TCP × 普通/debug 16/16 也与 C 一致。因此原 F02 修复有效，R1 是此次扩大边界后发现的既有缺口。

证据：[三方逐场景回答、上游请求数与健康状态](audits/20261011/fix2/dns/cname-summary.json)、[RD/DO 控制](audits/20261011/fix2/dns/cname-flags-01.json)、[正常功能探针](audits/20261011/fix2/dns/cname_compat.py)。Oracle 原始 wire、argv、日志在 `private/dns-hosts/cname-compat-01/result.json`。修复方向应是补齐动态别名终点的配置 RR 解析，保留已修好的 alias 优先级。

### R2 — startup gate 没有覆盖初始 hostsdir

位置：[files_runtime.rs:671](../../components/dnsmasq/src/dns/files_runtime.rs#L671)、[main.rs:3335](../../components/dnsmasq/src/main.rs#L3335)、[main.rs:3572](../../components/dnsmasq/src/main.rs#L3572)。

普通 resolver polling 模式下，`DnsFiles` 同一 turn 可同时置 `initial_cache_reload=true`、`initializing=false`；随后 main 才排队异步读取初始 hostsdir。DHCP 新门控查询 `files_initializing()`，没有覆盖 `hosts_work_pending()`，所以 hostsdir 中的权威名称尚未发布时，DHCP 已可处理请求。

独立正常会话测试：hostsdir 文件含 8 MiB 合法注释和一条 `127.0.0.30 authoritative.test`，配置 `domain=test`、恢复该地址的租约；观察到 daemon 初次打开此文件后，只发送一个正常 DHCPREQUEST，请求名称 `supplied-wrong`。注释用于扩大初读观察窗口，没有持续流量或特殊报文。

两轮最终分支均在初读 fd 仍打开时 ACK，option 12 为 `supplied-wrong`；C 都在读完后 ACK `authoritative`。最终分支请求到 ACK 为 2.912/4.274 ms，C 为 29.657/29.505 ms；这里只用作先后关系证据，不是性能比较。文件读完后两边 lease/DNS 都成为正确名称，但已经交给客户端的 ACK 不能追回。本探针确认的影响是该启动窗口的 hostname option 错误；未观察到持久租约损坏，不排除未测的其他影响。

main 在 poll/no-poll/no-resolv 三种模式都提前回复错误名；在本探针中，最终分支的后两种模式已正确等待。普通 addn-hosts／resolver FIFO 的原修复场景也通过。因此这是**部分改善后仍遗留的模式**。独立 hostsdir helper 控制两边均为 5 次正确回调，没有确认 helper 提前交付，不能由 DHCP 结果外推。

证据：[两次最终分支、main 控制及完整选项/最终状态](audits/20261011/fix2/dhcp/summary.json)、[正常 DHCP 探针](audits/20261011/fix2/dhcp/hostsdir_startup.py)。建议把初始 hostsdir 发布纳入同一启动就绪条件，并保持门控期间调度不空转。

### R3 — 体积预算仍失败，分支增加了确定的文件成本

相同 Oracle release 构建方式下，main 1,970,216 B → 最终分支 2,056,672 B：**增加 86,456 B（4.388%）**。新增 `.rela.dyn` 为 51,840 B，`.text` 增加 29,168 B，解释了大部分增量；不能把全部差额只归因于某一个修复。[main section](audits/20261011/fix2/build/main-release-sections.txt)、[最终分支 section](audits/20261011/fix2/build/release-sections.txt)。

真实 SDK 产物 ELF 2,054,939 B、APK 1,115,173 B，分别超过 [原预算](../../tools/dnsmasq/m5_final_budget.json)的 1,000,000 B／700,000 B。两次源码构建 prepare/compile 均退出 0，校验驱动均按原预算拒绝、退出 1，`failure_boundary=size-target`。没有调宽门限、使用预算豁免或将包生成成功写成完整验收通过。

证据：[第一次源码构建](audits/20261011/fix2/build/sdk-acquire.json)、[固定 SHA 的 clean 重建](audits/20261011/fix2/build/sdk-verify.json)。main 原本也超预算；R3 是仍存在的替换验收障碍，新增 4.39% 是需要接受和追踪的修复成本。

### R4 — SIGUSR1 debug 表的来源表示有差异

位置：[daemon_dump.rs:58](../../components/dnsmasq/src/dns/daemon_dump.rs#L58)、[daemon_dump.rs:70](../../components/dnsmasq/src/dns/daemon_dump.rs#L70)。

## 构建方式与保护边界

Make 中的 shell compiler lookup 现可穿过 `BuildPackage` 的二次展开；linker wrapper 将固定 Rust self-contained startup 对象换为 rcrt1/crtbeginS/crtendS，并保持静态链接。固定的三类 startup 对象缺失、重复、来源目录不符，或出现 response file、独立的 `-pie`/`-static-pie`/`-shared` 参数时会明确拒绝；这不是对任意链接参数的完备分析。当前版本／目标上的正常源码构建已实测。

SDK 两次同路径 clean 源码构建使用固定的 177 个产品／构建输入摘要 `58a8a4fd459806d1029bf891af0ad48b49070701431fcf3a0566d60fcf779f10`，第二次先归档旧 build tree/stamps，再固定第一次的 ELF SHA；ELF/APK 逐字一致。没有设置 `OWRT_DNSMASQ_FROZEN_ELF` 绕过编译。[输入身份](audits/20261011/fix2/build/source-identity.json)、[实际构建驱动](audits/20261011/fix2/build/sdk_source_build.py)。

`startup_relro::protect()` 在 main 开始处运行，经 `dl_iterate_phdr` 获取主映像，检查 RELRO 唯一且非空、地址加法溢出及末端页对齐后 `mprotect(PROT_READ)`；异常明确退出 5。独立探针对实际 `/proc/PID/exe` SHA、inode/device、全部 PT_LOAD 基址与每一页 RELRO 权限做核对；两个 Rust 产物各 3 个不同 ASLR 基址，RELRO 11 页全 `r--p`，无共享库映射、WX 映射或可执行栈，映射快照前后的正常 UDP/TCP A 查询均匹配 C 且退出 0；两次查询都在启动保护完成后。[release 映射](audits/20261011/fix2/build/relro-release.json)、[SDK payload 映射](audits/20261011/fix2/build/relro-sdk.json)。

维护边界明确：依赖固定 Rust 1.98.1 的 startup-object 布局，当前验证为 AArch64/4 KiB 页；没有证明不同 Rust/linker、16/64 KiB kernel 或其他架构可用。使用的是 Rust 随附静态 musl，不能说成与 SDK libc 字节相同。保护发生在 main，未证明 constructors 阶段与 C loader 的保护时序等价。包 ELF header gate 仍明确写 `runtime_protections_verified=false`，运行映射证明由独立门提供。[0018](../decisions/0018-canonical-build-host-ci.md) 的 canonical CI 发布边界没有因此改变。

## 性能与资源

固定计划为三种实现 × 六个场景 × 三轮，轮转执行顺序；5 秒预热、15 秒测量，随后等待退出负载后的 barrier，再在 0/1/5 秒取样。服务、上游、生成器、控制器分别绑 CPU 0/1/2/3，所有窗口顺序运行、无饱和段。普通 UDP hit/miss 各 2,000 query/s，TCP hit/miss 各 500 query/s，DHCP 20 cycle/s；reload 场景 500 query/s，5 秒一次单行 hosts 重载，同时 10 次/秒 TFTP 传输，是混合业务成本。

这使用现有工具的 `--preflight` 短窗口，只复用 `analyze_window()` 核验原始记录；没有冒充正式 M6 30/120 秒协议或使用其五轮分类器。事前规则为：中位数增加超过 10%，同时超过双方 `(max-min)/median` 波动，且三个配对均变差，才标记成本回退信号。未触发不等于等价证明。[预冻结计划](audits/20261011/fix2/performance-plan.json)、[实际驱动](audits/20261011/fix2/performance.py)。

**54/54 个窗口完成并通过计量核验**，已发送请求全部正确，warmup/measurement 均零 timeout、wrong、transport error、scheduled skipped；测量期无生成器受限记录。每个实现完成测量期 247,500 次 DNS 查询和 900 个完整 DHCP 周期，DHCP 最终 leasefile 均为空；混合窗口的 reload/TFTP 行为检查均通过。全部原始窗口保留，没有重试、剔除或选最好一轮。[完整结果与原始输入摘要](audits/20261011/fix2/performance.json)、[运行记录](audits/20261011/fix2/performance-run.json)。

以下为三轮中位数；CPU 单位为 µs/正确 DNS 查询，DHCP 行为 µs/完整周期，混合行的 CPU 包含重载/TFTP 工作；PSS 为每窗 1 Hz 采样的进程树峰值，再取三轮中位数。

| 场景 | main CPU | 最终 CPU | CPU 增量 | main → 最终 p95（µs） | main → 最终 PSS（KiB） |
| --- | ---: | ---: | ---: | ---: | ---: |
| UDP hit | 13.85 | 13.89 | +0.28% | 24.24 → 24.24 | 3,356 → 3,420 |
| UDP miss | 75.33 | 86.68 | +15.06% | 98.64 → 129.80 | 3,928 → 3,928 |
| TCP hit | 35.49 | 41.89 | +18.04% | 88.44 → 97.64 | 4,940 → 5,016 |
| TCP miss | 143.00 | 145.64 | +1.84% | 282.08 → 276.00 | 11,584 → 11,520 |
| DHCP | 525.38 | 596.73 | +13.58% | 3,197.31 → 3,218.59 | 2,368 → 2,512 |
| reload + TFTP | 36.21 | 34.77 | −3.96% | 118.24 → 125.20 | 2,444 → 2,516 |

**O1：CPU 成本增长疑似，影响等级暂不确认。** TCP hit CPU 三对均增加，但最终分支自身波动 W=35.32%，大于 18.04% 的中位数差；UDP miss、DHCP 的中位数增幅虽超过各自双方 W，却只有两对增加。UDP miss p95 的 31.59% 增幅也小于双方最大 W=41.36%。因此这些观测没有达到冻结的确认条件，不能把它们列为已证明的新 CPU 回退，也不能写成“性能没有退步”。进一步确证需要更长窗口／归因，本轮没有完成这一点；R5 的独立内存证据已经给出明确的新回退。

负载期小幅内存增长则有直接证据：UDP hit PSS +64 KiB（1.91%），DHCP +144 KiB（6.08%），均三个配对更高且超过双方采样波动。未达 10% 标记并不意味着没有成本。各场景 FD 采样峰值中位数与 main 相同（UDP hit/miss 12、TCP hit 32、TCP miss 52、DHCP 58、混合 14）。

相对精确 C 的当前产物观察如下，不能使用上一轮其他 ELF 的历史数字替代：

| 场景 | C CPU（µs/正确单位） | 最终分支 CPU 相对 C | C → 最终 PSS（KiB） |
| --- | ---: | ---: | ---: |
| UDP hit | 12.85 | +8.08% | 1,660 → 3,420 |
| UDP miss | 111.74 | −22.43% | 1,652 → 3,928 |
| TCP hit | 50.77 | −17.49% | 8,046 → 5,016 |
| TCP miss | 341.34 | −57.33% | 7,519 → 11,520 |
| DHCP | 448.81 | +32.96% | 1,652 → 2,512 |
| reload + TFTP | 25.53 | +36.22% | 1,660 → 2,516 |

DHCP 和混合场景相对 C 的 CPU 增加达到上述成本信号条件；混合 p95 88.92 → 125.20 µs（+40.80%）也达到条件。UDP hit/miss、TCP miss、DHCP、混合 PSS 高于 C；TCP hit PSS 低于 C。此处报告特定普通负载的现象，不把短窗口优势写成普遍提速，也不把跨 C 实现的差额都归罪于本次修复。

CPU 主计量是 cgroup `usage_usec`，包含 TCP 子进程；没有将易受回收时序影响的 `/proc` 尾部 CPU 字段作为主证据。PSS 用于减小 C fork 共享页重复计算，RSS/FD 进程树求和则可能重复计算共享映射／继承引用。C 的 drain 检查实际只要求无子进程，没有证明 FD 返回初始值；Rust 另外检查 FD 返回空闲计数。0/1/5 秒相对 barrier 完成，不是负载结束的绝对时点。短窗口和 1 Hz 采样不能证明长期无泄漏或覆盖所有瞬时峰值。
