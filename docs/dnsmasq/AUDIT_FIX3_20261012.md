## 结论

**当前不能合入 main。** 有两个独立阻断依据：新增 DNS 回答语义退步 N1，以及配置规模相关的 TCP 缓存命中性能回退 N4。`filterwin2k` 与缓存 CNAME、TCP SOA/SRV 查询组合时，main 返回 NOERROR，分支返回 NXDOMAIN；底层缺陷虽在 main 已有，本分支扩大了触发范围。加入 100/1,000 条无关 `dns-rr` 后，TCP 缓存命中 CPU 明显增加，而相同配置的 UDP 对照基本不变。

另有普通 hosts 文件读取移到降权后造成的启动兼容性收缩 N2；它与目标 C 的权限边界一致，但仍不满足此次严格的 main 比较标准。修复本身有实质效果，然而单测全部通过、旧审计附录中的通过记录和普通 A 查询的小配置基准，不能代替这些组合路径与配置规模的验证。即使接受 N2 作为有意的 C 对齐取舍，N1/N4 仍足以否决当前合并。

### N1 — CNAME 优先级修复让既有 TCP NXDOMAIN 缺陷进入新的查询路径

新增入口：[local.rs:276](../../components/dnsmasq/src/dns/local.rs#L276)。既有缺陷：[tcp_service.rs:621](../../components/dnsmasq/src/dns/tcp_service.rs#L621)。

复现设置 `filterwin2k`、正常缓存及可控上游。先对 `alias.example A` 查询，上游返回合法的 `NXDOMAIN + alias.example CNAME target.example + example SOA`，使别名和负终点进入缓存；随后用 TCP 查询同一别名的 SOA 或 SRV，并设置 DO=1。结果：

| 实现 | TCP 结果 | 是否再次访问上游 |
| --- | --- | --- |
| 精确 C | NOERROR，保留 CNAME + SOA | 是 |
| main | NOERROR，空 answer/authority | 否 |
| 修复分支 | **NXDOMAIN**，CNAME + SOA | 是 |

上游自身返回的是 NXDOMAIN；C 因缓存已知此名称存在而修正响应。main 的空回答也不完全符合 C，但它对这组查询未返回 NXDOMAIN。本分支补回转发和 CNAME 的同时引入了 RCODE 0→3 的语义退步。此处证明的是相对精确 C 与 main 的新增 RCODE 行为退步，**未实测具体客户端行为、整域负缓存或普遍解析失败**。

原因链：新的 `has_cname` 提前返回让查询不再走原来的 `filterwin2k` 本地 NOERROR；DO/RD 条件使动态缓存回答不可用，查询随后转发。TCP `apply_known_local_nxdomain` 的判断只有配置、hosts、lease 等，缺少动态缓存中的已知名称；这个底层遗漏在 main 已有，但过去不覆盖这组 `filterwin2k` 请求。去掉 `filterwin2k` 的 warm 控制中，main/fix 都错回 NXDOMAIN；冷缓存 `filterwin2k` 控制三者都返回 NOERROR、不转发。这些对照把旧根因与新增触发面区分开。

新探针以普通 `-k` / debug `-d`、UDP 预热 / 同一持久 TCP 连接预热、SOA / SRV 做三轮复现：相关 24 组均为 C/main RCODE 0、fix RCODE 3；另保留冷缓存和去 filter 控制。广矩阵还覆盖 RD=0 的同类变化。[定向结果与完整报文代表](audits/20261012/fix3/dns/filter-cname-summary.json)、[定向脚本](audits/20261012/fix3/dns/filter_cname_tcp.py)、[广矩阵](audits/20261012/fix3/dns/summary.json)。

应补齐本次新到达的 TCP known-name 语义，并保留 CNAME 终点、DO/RD、普通/debug、同连接快照的回归覆盖；不能简单删掉 CNAME 优先级修复。本次未修改实现。

### N2 — 普通 hosts 延后读取改变 main 已有的启动权限边界

位置：[main.rs:880](../../components/dnsmasq/src/main.rs#L880)、[降权点](../../components/dnsmasq/src/main.rs#L1343)、[EVENT_INIT](../../components/dnsmasq/src/main.rs#L3558)、[实际读取](../../components/dnsmasq/src/main.rs#L3175)。

以 root 启动 `-k --user=nobody --group=nogroup --addn-hosts=FILE`，FILE 是 root:root、0600，只有 `192.0.2.7 secret.test`。main 在降权前读入；本分支初始只建立配置记录，实际文件留到降权后的 EVENT_INIT，记录 Permission denied 后继续运行。

| 条件 | main 启动 A 查询 | 分支启动 A 查询 | 精确 C |
| --- | --- | --- | --- |
| 0600，`-k`，实际 UID 65534 | `192.0.2.7` | **REFUSED，无 A** | REFUSED，无 A |
| 0644，`-k` | 正确 | 正确 | 正确 |
| 0600，`-d`，实际 UID 0 | 正确 | 正确 | 正确 |

该变化**对齐 C 而非偏离 C**；但按用户此次明确的 main 标准，原来启动后可用的名称现在不可用，必须记录为新增兼容性收缩。不能笼统称为 daemon 启动失败，也不能声称所有 OpenWrt hosts 都受影响。main 在 0600 文件的 SIGHUP 后原本就丢失记录，那个 reload 问题仍归 main 已有。`chmod 0644` 后 SIGHUP，三者都恢复。

[全部 UID、argv、wire 和日志](audits/20261012/fix3/dhcp/hosts-permissions.json)、[独立探针](audits/20261012/fix3/dhcp/hosts_permissions.py)。这是合并兼容性与 C 行为对齐之间的明确取舍；当前分支没有迁移处理。解决时不应为了恢复能力而放弃整个服务的降权。

### N3 — 峰值内存修复保留了配置 hosts 的重复构建成本

| 记录数 | main 初始 reload 日志观测 | 分支 | main ready CPU | 分支 ready CPU | main / 分支 VmHWM |
| ---: | ---: | ---: | ---: | ---: | ---: |
| 10,000 | 26.18 ms | 36.44 ms | 0.01 s | 0.03 s | 10,696 / 10,756 KiB |
| 50,000 | 127.97 ms | 179.03 ms | 0.11 s | 0.17 s | 45,632 / 45,620 KiB |

### O1 — 旧体积预算失败与新增固定成本分开判断

两侧真实源码 SDK 构建均能 prepare/compile/strip/package，审核驱动都因原 `ELF ≤ 1,000,000 B / APK ≤ 700,000 B` 预算失败而退出 1，边界为 `size-target`。这是 main 已有替换验收障碍，不能把生成 APK 写成完整验收通过，也不能用旧预算失败否决本次差分合并。

新增成本：Oracle release 增加 86,456 B（4.388%）；SDK payload 增加 86,024 B（4.369%），APK 增加 29,526 B（2.716%）。新增 `.rela.dyn` 51,840 B、`.text` 增加 30,656 B，解释了大部分 ELF 增量。static PIE/RELRO 确实带来保护改善；这里明确记录其固定文件成本，未证明目标设备因此耗尽 flash/RAM。它与 N3 的配置相关 CPU 成本、后述持续查询成本分别判断。[构建及预算证据](audits/20261012/fix3/build/summary.json)、[main sections](audits/20261012/fix3/build/main-release-sections.txt)、[分支 sections](audits/20261012/fix3/build/fix-release-sections.txt)。

### O2 — main 已有的 TCP CNAME 兼容性缺口

独立 DNS 矩阵中，无 `filterwin2k` 的 cached alias→负终点，TCP 查询设置 DO=1 或 RD=0，C 对已知名称修正 NOERROR，main/fix 都保留 NXDOMAIN。这是 N1 的旧根因控制，只有本分支新增的 filterwin2k 触发面算 N1，不能重复计数。

此外，部分 `local=/target.example/` 或 literal-address 规则与缓存 CNAME 终点的 TCP 组合仍与 C 不同，main/fix 未变化。例如 `target-local-positive / 16-rd-tcp` 中 C 不转发、main/fix 却访问上游；`target-literal-positive / 255-rd-tcp` 中 C 返回配置地址，main/fix 继续转发。具体配置、完整三方解码响应及 case ID 保存在 [DNS summary](audits/20261012/fix3/dns/summary.json)；它们不是本分支新增阻断。

### O3 — main 已有的语法及拒绝连接表示差异

43 个 inactive/integer 探针中，分支仍有 14 个 `--test` 返回值不匹配 C，main 对这些项目也不匹配：`auth-zone`、`dnssec`、`conntrack`、`enable-dbus` 的语法检查，以及超过 C int 范围的 cache-size/local-ttl/max-tcp-connections/fast-dns-retry 参数。前四项的正常 daemon 启动两侧都拒绝，区别在语法检查阶段；整数项没有在本轮用极端值运行资源负载。故限定为 P3 兼容性差异，不外推运行失效。

54 个 auth/ACL 服务组合中，分支保留 8 项 TCP 拒绝的 EOF/RST 表示不同；没有 main 正确而分支新答错的 case。96 个 TFTP IPv4/IPv6 接口组合，分支全部匹配 C，main 78 项不同。日志、响应和三方归属见 [config/summary.json](audits/20261012/fix3/config/summary.json)，完整命令和私有原始结果 SHA 同时保留。

## 构建方式与保护边界

本轮使用复制的隔离 SDK，真实执行源码 prepare/compile，没有 `OWRT_DNSMASQ_FROZEN_ELF` 捷径。分支第二次先归档 build tree/stamps，再以第一次 ELF SHA 为期望 clean 重建；ELF 和 APK 逐字一致，strip、包名/架构/依赖、源码摘要、SDK 输入和配方恢复检查均通过。原 Make eval/compiler 路径故障没有复现。三次构建驱动退出 1 都是 O1 原预算拒绝，编译阶段退出 0。

实际 `/proc/PID/exe` 身份和每页 maps 证明：新 release 和 SDK payload 各三次启动，11 页 GNU_RELRO 全只读、三个 ASLR 基址不同，无动态共享库、WX 映射或可执行栈，映射前后 UDP/TCP 查询健康。main 基址固定，11 页 RELRO 可写；C 为 3 页只读。不能把 ELF header 的 GNU_RELRO 标志当成运行时保护已生效的证据。[release maps](audits/20261012/fix3/build/relro-release-fix.json)、[SDK maps](audits/20261012/fix3/build/relro-sdk-fix.json)、[main 控制](audits/20261012/fix3/build/relro-release-main.json)。

## 性能复核

先固定 36 个 main/fix 窗口：6 个场景 × 3 对，顺序 AB/BA/AB。服务/上游/生成器/控制器分别绑定 CPU 0/1/2/3；预热 3 秒，普通 DNS 测量 10 秒、CNAME 20 秒。UDP hit/CNAME 4,000 query/s，UDP miss 2,000，TCP hit/CNAME 3,000，TCP miss 2,000；20 个客户端。普通 hit 使用 4,096 个缓存名称，CNAME 使用 2,048 个别名与一个共享 A 终点；逐项验证缓存后禁用上游应答，并检查命中阶段没有上游请求，不能把 miss 当 hit。TCP 负载每连接满 100 次查询重连，因此 CPU 包含正常接入和连接状态成本，不是孤立的 lookup 微基准。

36 窗全部完成，正确性检查通过，warmup/measurement 无 wrong、timeout、transport error 或 scheduled skip。下表是三个窗口的中位数，不是一个跨场景通用倍率：

| --- | ---: | ---: | ---: | ---: |
| udp-hit | 12.881 → 13.149 | +2.07% | 38.32 → 22.92 | 3292 → 3372 |
| udp-miss | 78.125 → 80.122 | +2.56% | 102.48 → 117.60 | 3828 → 3952 |
| tcp-hit | 19.531 → 20.686 | +5.91% | 30.84 → 32.20 | 4880 → 4848 |

**S1，P3、疑似本分支新增的小幅普通 TCP CPU 成本：** TCP CNAME 三对 CPU 都更高，中位数 +8.29%；TCP hit +5.91%，TCP miss +9.17%（两对更高）。UDP miss p95 +14.75% 但波动大。预先冻结的筛选规则是“中位数增加 >10%、超过双方相对 range 且三对同向”；本组未触发。这个 10% 是审计筛选方法，**不是用户批准的性能容差**；未触发不能证明等价、零回退或把差额确定归为噪声。上述小增量保留为疑似，不单独作为已确认明显退步。

纯 CNAME UDP 的新增临时本地查询没有在这组数据中形成明显回退；不能只根据代码看起来多做一次工作就写成实测性能缺陷。短窗不足以排除较小成本或 Oracle 虚拟化环境噪声，也不能将其它 UDP p95 的下降宣称为普遍提速。[固定计划](audits/20261012/fix3/performance/dns-plan.json)、[完整统计及每窗原始输入 SHA](audits/20261012/fix3/performance/dns-summary.json)、[执行记录](audits/20261012/fix3/performance/dns-run.json)。

### N4 — TCP 缓存命中现在每次扫描全部无关通用记录

位置：[daemon.rs:1846](../../components/dnsmasq/src/dns/daemon.rs#L1846)、[local.rs:1284](../../components/dnsmasq/src/dns/local.rs#L1284)。main 的 TCP 缓存命中先返回缓存；本分支先执行本地解析，再查动态缓存。本地 `add_raw` 对配置的全部 `dns-rr` 逐项计算、分配 `dotted_key`，比较名称后才检查 RR 类型。结果是原来不需要扫描的普通 TCP A 缓存命中，新付出随无关配置条数增长的开销。

审计只追加合法配置 `dns-rr=unused{i}.audit.test,65401,abcd`，与实际查询的名称及 A 类型都无关。两侧使用完全相同配置、工具、种子、速率和 CPU 分配；产品代码不改。正常填充并逐项证明 4,096 条 A 缓存，禁用上游应答，固定 1,000 query/s、20 客户端、预热 3 秒、测量 15 秒；100/1,000 条的 TCP 与 1,000 条 UDP 控制各 AB/BA/AB 三对，共 18 窗：

| 配置/传输 | main CPU µs/正确响应 | 分支 CPU | CPU 增幅 | main → 分支 p95 µs |
| --- | ---: | ---: | ---: | ---: |
| 100 条 / TCP | 30.524 | 49.993 | **+63.78%** | 78.20 → 105.72 |
| 1,000 条 / TCP | 33.335 | 119.547 | **+258.62%** | 85.92 → 219.96 |
| 1,000 条 / UDP | 103.354 | 101.705 | −1.60% | 201.36 → 200.04 |

TCP 的三对均变差，增幅远大于双方窗口波动；UDP 控制说明原本已有的扫描与本分支新增 TCP 成本应分别归属。100 条就已能复现，不能把它仅解释为极端大文件启动问题。所有回答正确、每窗完成 15,000 次，没有 timeout/transport error/错误回答或跳过计划负载。采样峰值 PSS 中位数变化小于 1%、FD 峰值相同。该固定负载下未出现额外 FD 峰值或请求失败；没有测量连接容量上限，也不能用短窗口排除长期泄漏。

另外冻结五对新窗口，AB/BA/AB/BA/AB；1,000 条配置、1,000 QPS，预热 5 秒、测量 30 秒。每窗 30,000 次正确响应，结果持续重现：

| 对次 | 顺序 | main CPU µs/正确响应 | 分支 CPU |
| ---: | --- | ---: | ---: |
| 1 | main → 分支 | 32.599 | 115.744 |
| 2 | 分支 → main | 31.596 | 118.756 |
| 3 | main → 分支 | 34.710 | 120.402 |
| 4 | 分支 → main | 32.174 | 115.380 |
| 5 | main → 分支 | 33.304 | 115.903 |

CPU 窗口中位数 **32.599 → 115.903 µs，增加 255.54%（3.555 倍）**；p95 中位数 **80.201 → 213.962 µs，增加 166.78%**。5/5 对同向；两侧 CPU `(max-min)/median` 分别 9.55% / 4.33%，远小于效应。PSS 中位数仅 +0.91%，FD 峰值都是 32。这不是依据单个首轮窗口下结论。[确认计划](audits/20261012/fix3/performance/confirm-plan.json)、[五对完整数值](audits/20261012/fix3/performance/confirm-summary.json)、[运行记录](audits/20261012/fix3/performance/confirm-run.json)。

该成本是在支持的配置下持续发生的真实 daemon CPU 和客户端延迟增长，符合本次“无明显性能退步”的阻断标准；不是产品崩溃、饱和吞吐上限或 Cortex-A53 实机数值。普通 TCP hit 组是 3,000 QPS，这组是 1,000 QPS，不能跨组把绝对 CPU 差直接解释成配置成本；本发现使用同一组内 main/fix 配对及 UDP 对照。源码机制与测量一致，未做逐提交 CPU profile 因果拆分。

修复需要在保留正确本地优先级的同时，避免每次缓存命中遍历和分配所有无关记录；不应简单恢复曾导致旧正确性问题的 cache-first 顺序。[18 窗计划](audits/20261012/fix3/performance/raw-plan.json)、[逐窗统计](audits/20261012/fix3/performance/raw-summary.json)、[运行记录](audits/20261012/fix3/performance/raw-run.json)、[仅改变测试配置的 wrapper](audits/20261012/fix3/performance/raw_records_window.py)。

## 没有覆盖的范围

- 不包含物理路由器、真实 Wi-Fi/广播多客户端、多接口 relay、Cortex-A53 实机性能或完整 OpenWrt 开机过程。
- 不包含安装/升级/卸载、procd 生命周期整合、掉电、flash 耐久、部署健康门与回滚；合并判断不是部署授权。

- 功能/性能主体使用 fresh Oracle release；SDK payload 做构建及运行保护/查询控制，没有把完整矩阵重跑到 SDK payload，也没有证明两种构建路径字节相同。
