## 方法和读表规则

通用DNS配置为cache-size4096、cache-rr=TXT、dns-forward-max1024、TTL/local-ttl3600、no-resolv/no-poll/no-0x20-encode，query logging关闭；C/R3/Rs配置相同。20个逻辑客户端、每socket最多1个在途。每个正式窗口先全新独立2秒预热＋10秒pilot，再重建初态，30秒预热＋120秒正式测量；pilot、预填、验证、尾排空和清理均不计吞吐。

每profile5轮，round为外层、profile依冻结顺序执行；三组顺序为`C→R3→Rs`、`R3→Rs→C`、`Rs→C→R3`、`C→Rs→R3`、`Rs→R3→C`。不挑最快attempt。方法失败保留原轮、修环境或工具后fresh重跑；真实错答、timeout、DHCP末态或reload发布错误仍是有效坏产品观测，单列错误并排除出正确吞吐。

正确吞吐按阶段内真实完成数除以固定monotonic阶段秒数。正确latency来自该阶段实际首send的全部正确请求，包括后续阶段或窗口后才完成的请求；这些跨界完成另列，不能算进前一阶段吞吐。p50/p95为nearest-rank，阶段正确样本至少10,000才报p99。不得用平均延迟遮蔽尾部。steady还报告scheduled→send lag、scheduled未发与在途限制；closed-loop只表示20并发完成量，不是开放式daemon绝对最大容量。

CPU主数为独立daemon cgroup的`cpu.stat usage_usec`阶段首尾差，含已回收TCP child CPU；CPU/请求的分母为该阶段内正确完成请求。DHCP分母为完整DORA→renew→release发送的cycle，单位µs/cycle和cycle/s；release没有ACK，另检查负载结束后租约文件收敛为空，不能把release send计成独立应答。`/proc`树own＋已waited子CPU以及退出`wait4`只作交叉核对，不替代cgroup，也不重复加活跃child CPU。

边界capture lag必须≤250 ms，120秒至少118个1 Hz有效资源样本。RSS/PSS峰是采样峰，不是瞬时绝对上界；分别保留parent和完整process family的RSS/PSS/FD/thread/child及四分位趋势。C fork的RSS树合计重复包含共享页，PSS树用于总内存比较；VmHWM单列。负载器CPU≥90%单核，或steady p95 send-lag>1 ms时，标记generator-limited，数据照留，吞吐差不能宣称daemon容量收益。

TCP三profile均按精确C/R的每连接100-query上限复用并重连。CPU包含fork/cache view/回收和重复连接成本；延迟从真实首send计算，connect前等待由scheduled lag和吞吐反映。结果不能称20条永久连接，也不能当纯握手吞吐。reload发布探针为10 ms，controller循环约5 ms且资源读取会延迟观察；publication latency是观测上界，必须结合实际探测间隔，低于分辨率的差异不判收益。

收益/回退规则不随结果改变：组内波动`W=(max−min)/median`，差异须超过两组W较大者且至少4/5同轮方向一致。正确吞吐提高≥10%，CPU/正确请求或p95降低≥10%，才满足对应收益门；吞吐降低≥5%，CPU/请求或p95增加≥10%，才满足对应变差门。RSS/PSS变化须≥10%且绝对≥64 KiB。新增错答/额外普通失败直接列绝对数量及变差。p50/p99、FD/thread/child保留完整描述值，不补造协议未设的收益门。

### UDP 主循环瓶颈（M6b 第一优先级）

用户在正式测量进行中定位了一个应优先修复、再重测的产品瓶颈。冻结源码的主循环在 [`main.rs:3282–3289`](../../components/dnsmasq/src/main.rs#L3282) 对每个监听器每轮只调用一次 `step_udp(index)`；`step_udp` 的实现位于 [`main.rs:3469–3498`](../../components/dnsmasq/src/main.rs#L3469)。已静态确认每次接收只调用一次 `recvmsg`，并新建 `vec![0; 65,535]` 缓冲。`wait_for_files()` 的公共 poll 路径位于 [`main.rs:1794`](../../components/dnsmasq/src/main.rs#L1794)，网络 fd 由 [`main.rs:4260–4377`](../../components/dnsmasq/src/main.rs#L4260) 的 `append_poll_fds` 统一加入；非 Linux 路径才明确使用 `park_timeout(Duration::from_millis(2))`（[`main.rs:3202–3203`](../../components/dnsmasq/src/main.rs#L3202)）。因此 Linux 下“没有网络 fd”或固定2 ms上限尚未被静态代码证明。

首轮正式 R3 udp-hit 的独立分析给出了可复核的数量级：steady 正确完成 41,869／90s = **465.211 QPS**，saturation 为 13,988／30s = **466.267 QPS**；R3 p50 分别 41.909 ms／42.841 ms，Rs 对应 41.979 ms／42.889 ms。实测 R3 udp-hit steady 为465.211 QPS、p50 41.909 ms；这与“每轮一次 `step_udp`、单次 recvmsg”的批处理假设一致，但不是Linux轮次或等待原因的直接计数。当前冻结 ELF没有主循环轮次、每轮收包数或wait原因计数；M6b诊断必须先加入不改变调度语义的观测，区分Linux poll唤醒、单包处理和其他来源。

该单包处理路径同时存在于 opt3 和 s；首轮两者都约465 QPS／42 ms，但Linux等待来源仍需诊断。因此在修复或确认该瓶颈前，udp-hit／udp-miss 的 opt3 对 s CPU、延迟和吞吐对比不具备切换意义。本报告保留首轮数值作为“瓶颈下观察”，不把它们分类为 s 有收益或变差。M6b 第一优先级是：在保持 C/Rs 配置、负载、计时和判定阈值不变的前提下，先用Linux poll轮次、每轮收包数和wait原因计数确认瓶颈，再评估让一次处理排空多个UDP包、复用接收缓冲或调整等待路径；修复后必须重新冻结产品、完成受影响的 UDP profile 全部五轮，再恢复 opt3／s 比较。M6a不实施该修复。

## Rs 相对 opt3：数据结论

Rs ELF 比 R3 小315,392 B（16.35%）。协议切换门要求正常 profile 的 median CPU/正确请求和 p95 代价均≤5%、吞吐回退≤5%、无新增错误，至少4/5配对方向满足，且关键边界不受 generator 限制。完整比较CSV逐指标给出绝对 delta。当前冻结 UDP hit/miss 的 Rs/R3 机械结果不能作为切换依据：两者均在相同单包路径下首轮约465 QPS、约42 ms p50，Linux等待来源尚未计数；必须完成诊断或修复后重冻结并重测。

在未受该UDP瓶颈直接限制的 profile 上，仍应按每项门逐条查看：不能把一个有利 CPU 指标抵消另一个变差 p95，也不能以 ELF 变小推断性能收益。Rs 没有做功能或APK资格验收，本报告不建议在M6a直接切换交付构建。

## DHCP, listener, logging and helper conditional accounting

The five DHCP windows all completed 2,400 correct DORA/renew transactions per group per round. Peak process resources across rounds were C RSS/PSS 1,592–1,680/1,584–1,672 KiB, R3 2,440/2,432 KiB, and Rs 2,124/2,116 KiB; all had one thread, no child and 53/56/56 FDs respectively. The same config uses 20 fixed MAC/CLID hosts, `no-ping`, a 150-lease maximum and a 3,600-second lease; no helper script is configured, so helper allocation is zero in this scenario. These observations do not measure a full DHCP-max or helper backlog.

The reload-concurrent windows configure `addn-hosts`, TFTP and the same cache. Across five rounds C peak RSS/PSS was 1,660–1,676/1,652–1,668 KiB with 15 FDs; R3 2,404/2,396 KiB with 14 FDs; Rs 2,148–2,152/2,144 KiB with 14 FDs. All use one thread and no helper. The logger is configured as `log-facility=-`; its `Logger`/queue structure is therefore present, but no queued log payload was separately attributed by the process snapshots. Listener file descriptors include DNS/TFTP and reload file descriptors; kernel socket buffers are outside the user-space object budget.

The source-size table remains the correct conditional bound: C `dhcp_lease` 160 B versus Rust `Lease` 232 B plus variable Vec payloads; C `log_entry` 1,048 B versus Rust `Logger` 176 B and 40 B queue records plus payload Vec; C listener 64 B versus Rust socket/owner metadata; C helper `script_data` 104 B versus Rust Helper/LeaseDelivery/ExtraData only when a helper is configured. No formal profile here enables a script helper or an unbounded logging queue, so those rows must not be charged to the observed UDP/TCP RSS.

## Final residual and M6b boundary

The UDP formal five-round plateau confirms the major anonymous delta is present after cache fill, but it does not identify individual allocation owners. Full smaps distinguish C's preallocated 548 KiB cache mapping from Rust's multiple anonymous mappings; they cannot identify a Rust mapping as a particular `HashMap`, `Vec`, or allocator arena without heap instrumentation. The remaining candidates are: cache/index requested bytes (measured static accounting), allocator size-class retention and page rounding, the 65,535-byte UDP receive Vec, persistent upstream receive state, forwarding maps, stack, and logging/TFTP/DHCP scratch depending on profile.

Final analysis identifies the single-packet-per-step path and 65,535-byte receive allocation as measurement-backed candidates; the Linux wait source remains unmeasured. The non-Linux 2 ms park is a separate static fact, not a Linux attribution. They are recorded here as measurement-backed candidates only. This M6a work does not change the buffer, loop, allocator, cache representation, fork policy or logging behavior. Any M6b change needs a new freeze and the full 135-window qualification.
