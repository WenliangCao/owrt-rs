## 结论

**目前不能合入 main。** 本轮确认一个 **P2 新增功能阻断 F1**：缓存的动态 CNAME 终点含带压缩指针的 `dns-rr` 时，精确 C 和 main 的客户端 NS 答案相同，最终分支却返回错误 NS 名称，或 UDP 超时 / TCP EOF。普通和 debug 模式、UDP 和 TCP 都复现。

阻断依据是这个新增回答/可用性错误，不是旧 N4 性能结论、root-only hosts 权限变化或 main 原有体积预算。原有多数修复确实生效；最终 SDK 的 63 个三方性能窗口没有形成性能否决依据，构建与运行保护也未发现新增阻断。应先修 F1 并用原反例复核后再合并；本次没有修改产品代码。

本报告按本次要求判断：同一传输的精确镜像 C 是回答语义标准；main 只用于判定新增影响。向 C 对齐的变化不算回归；main 原有问题记录但不否决差分合并。性能数据必须同时包含 C、main 和最终分支；补上语义检查后慢于 main、仍不慢于 C 的场景只列优化建议。没有沿用旧审计的 main-only 性能否决标准，也没有使用旧记录中的用户接受意见替代本轮判断。

### F1：动态 CNAME 的 raw 终点新增错答/查询失败

配置的关键行是 `dns-rr=target.example,2,c00c` 或 `dns-rr=target.example,2,c02b`（TYPE 2 为 NS）。先用上游的 `alias.example CNAME target.example` 加目标 A 预热，再查询 `alias.example NS`。每个 case 都重启 daemon，TCP 使用同一条已预热连接。

为排除“main 原来忽略配置、因此本来就错”的混淆，补充对照让上游对 NS 返回真正的 AA CNAME+NS，TTL 分别为 300/60：`c00c` 组的 NS 指向 `alias.example`，`c02b` 组指向 `target.example`。精确 C 无需再转发；main 虽然有既有的额外转发，但客户端得到与 C 相同的答案。分支新失败如下：

| 配置 / 传输 | 精确 C | main | 最终 SDK |
| --- | --- | --- | --- |
| `c02b`，UDP | 合法 NS=`target.example` | 同 C | **timeout** |
| `c02b`，TCP | 合法 NS=`target.example` | 同 C | **EOF** |
| `c00c`，UDP / TCP，游标控制 | NS=`alias.example` | NS=`alias.example` | **NS=`target.example`** |

两组各覆盖 `-k` / `-d` × UDP / TCP，**8/8 个 case 都是 C/main 客户端答案相同、分支新增错误**。比较保留 header、全部节、名称、类型/class、RDATA 和 TTL（CNAME 300、NS 60），只规范化名称压缩布局。主审另用独立解码器从 hex 复算全部八组，结果相同。daemon 仍存活；这是条件性的请求失败，而非进程崩溃。[全部三方原报文与配置](audits/20261014/fix4/dns/raw-pointer-controls.json)、[独立字节复算](audits/20261014/fix4/root/raw-pointer-independent.json)

**独立阻断以 `c02b` 为主例**：C 的 NS 目标 `target.example` 有 A 记录，输出是完整有效的 DNS 应答。`c00c` 仅作 C 指针游标兼容性对照，其 NS 目标 alias 本身是 CNAME，不将它泛称为常见合规的 NS 部署配置。两种情况都要求手写 raw 指针和特定缓存 CNAME 组合，未观察到普通无此配置的 DNS 查询受影响。

原因是 [cache_engine.rs:675](../../components/dnsmasq/src/dns/cache_engine.rs#L675) 新增 Dynamic 终点的 `append_local_terminal` 调用。helper 在 [1736](../../components/dnsmasq/src/dns/cache_engine.rs#L1736) 以 **target** 构造临时问题，再在 [1776](../../components/dnsmasq/src/dns/cache_engine.rs#L1776) 对 raw RDATA 调用 `canonical_rdata()`。精确匹配源码 `rfc1035.c:1862–1872` 的 raw 循环（调用在 1868–1870）则把 `dns-rr` 数据作为不透明字节写入最终响应。

`c00c` 指向 offset 12：最终 C 报文那里是 alias，Rust 临时包那里却是 target，故悄悄改写名称。`c02b` 在 C 最终报文中指向 offset 43 的完整 target 名称，形成有效 NS RDATA；临时包同一偏移却落在 RR 长度字段，解码失败沿 `?` 返回，UDP 无响应、TCP 关闭。这一反例使用 **C 合法应答**，不以 C 自身输出畸形报文的 `c0ff` 控制作为阻断依据。

归属必须拆开：临时包/canonicalization helper 在 main 的 Local CNAME 分支就存在；额外的 host-record anchor 对照证明旧路径 main/分支共同出错。**本分支将它用于 Dynamic 终点，才使上述 main 原可正确回答的查询错答/失败。** 不能因底层 helper 较旧就免除新增调用造成的实际影响；也不把 main 已有的额外转发重复计算成新增缺陷。

复现使用 [terminal_boundaries.py](audits/20261014/fix4/dns/terminal_boundaries.py)，在 `run_isolated.sh` 中传入本文三份实际 ELF/镜像路径，选择 `--only raw-ns-target-pointer --qtype 2 --upstream-ns --upstream-ns-target target`。该命令生成四个主反例；另加 `--host-anchor` 是旧路径归属控制。选择 `--only raw-ns-pointer --qtype 2 --upstream-ns --upstream-ns-target query` 生成四个错答对照。完整可复制 argv、输出目录和新旧驱动身份见 [DNS 复现说明](audits/20261014/fix4/dns/NOTES.md)。

修复方向是保持 raw RDATA 在最终报文中的不透明输出语义，同时保留已补齐的本地终点优先级、SOA 和反向合成顺序。至少重跑两个指针反例、旧 Local anchor、普通非压缩 NS/未知类型、UDP/TCP 与 normal/debug 控制。本轮只报告问题，未实现修复。

### O1：既有 TCP 终点路由差异，P2，main 已有

先缓存 `alias.example A -> CNAME target.example + A`，然后在同一 TCP 连接查别名。配置 `local=/target.example/` 时，SOA/PTR/MX/TXT/AAAA/SRV/ANY/CAA 八种查询；配置 `address=/target.example/192.0.2.4` 时，ANY 查询。每个 case 都重新启动 daemon，分别测普通/debug 模式：**18 个 TCP 案例均与 C 不同，但 main=分支；对应 18 个 UDP 案例三方一致**。

例如 `local=/target.example/` 的 TCP TXT：C 本地返回空 NOERROR，不再访问上游；两个 Rust 版本都转发。实际影响包含本应由本地规则截住的查询仍发送上游。C 的 TCP `answer_request` 改写名字游标后用终点查路由，UDP 则恢复原问题名；Rust 没有保持这一区别。

这是明确的旧兼容性缺口，不是允许将 C UDP 当 C TCP 的理由。此前矩阵对九类组合的豁免不能解释为“全部等于 C TCP”，本轮亦不以它们阻止合并。[完整三方 fresh 对照、实际报文和复现命令](audits/20261014/fix4/dns/NOTES.md)

### O2：既有 parser/选项/拒绝表示差异，P3，main 已有

本轮 368-case 探针中，forward-pointer UDP/TCP 两例再次复现：C 解析指向后方的完整名字并回答，Rust UDP 丢包、TCP REFUSED；main/最终分支逐字相同。复现：运行原探针加 `--local-only --cases forward-pointer`，分别选择 main 与最终 ELF。[请求和响应](audits/20261014/fix4/root/boundary-summary.json)

另外保留、但本轮没有全部重跑的旧边界：部分 `auth-zone`/`dnssec`/`conntrack`/`enable-dbus` 的 `--test` 返回值、超过 C int 范围的整数参数、八个 TCP ACL EOF/RST 表示，以及 stale 回答的 EDE 提示缺口。它们在此前 main 对照中已有；不能将本轮 39 个新增配置探针通过误写成消除了全部选项差异。[旧三方语法/ACL证据](audits/20261012/fix3/config/summary.json)、[同一最终 SDK 的保留功能记录](audits/20261013/fix4_repairs/functional/validation.json)

现有门限 `ELF ≤ 1,000,000 B / APK ≤ 700,000 B` 在 main 就失败；本分支最终 ELF 2,054,939 B、APK 1,117,789 B 仍失败。它是完整替换资格的既有障碍，不是本次差分合并新增阻断。文件实际大小与确定 SHA 见本报告身份/构建部分；本轮未证明实际设备因此耗尽存储，也未放宽预算。[main 的原 SDK 预算证据](audits/20261012/fix3/build/summary.json)、[最终 SDK 现场核验](audits/20261014/fix4/build/result.json)

### 补充：raw CNAME 不移动名字游标（FIX5 复核发现的回归）

`5b914d32` 只在 raw TYPE 5 能完整解码为名字时才移动游标，但 C（`rfc1035.c:1862–1872` 传 `NULL`）对所有 raw 记录都不移动游标。FIX5 复核用多条未压缩 raw CNAME 加一条 `c062` 指针复现：游标被移走后，后续 owner 改为完整名字，报文布局与 C 不同，原样复制的指针落到错误字节，回答无法解码。

修复：不再维护启发式游标，改为按临时报文的实际 owner 指针翻译。指向临时问题（offset 12）的 owner 映射到最终报文里的 CNAME 目标；指向已复制 RDATA 或完整 owner 的指针按已复制区间换算；无法映射时写完整名字。raw 记录的 owner 在临时报文里都指向问题，因此在最终报文里始终是指向终点的 2 字节指针，与 C 布局一致；配置 CNAME 的目标仍按其 RDATA 位置压缩。

验证（release `6e619ce5…`，raw 结果在 Oracle `/home/ubuntu/dnsmasq-f1-fix2-20261014/private/`）：FIX5 复核者的全部 DNS 调用按原 argv 只替换 ELF 重跑——`cname-dynamic-02/03`（本回归）、`candidate-anchor-02`、`extended-controls` 80 例、四组 F1 指针复现，全部与精确 C 一致；完整 terminal 88 例中仅 O1 的 18 例不同且全部 main == 分支；N1 72/72；DHCP 负缓存 24/24、SOA 64/64、游标 12/12 零差异。单测 lib 779、bin 77 通过。新增 `cached_cname_raw_cname_terminals_keep_c_owner_layout` 直接断言四条 raw CNAME 的 owner 都是同一个 2 字节指针，已在 `5b914d32` 代码上确认失败。
