# 公网 DNS TCP 上游故障对照

2026-10-14。**在相同的“四上游、IPv4 UDP 正常但 TCP 不可用、IPv6 UDP/TCP 正常”条件下，Rust 与精确镜像 C 的上游选择、失败转移、连接复用及恢复策略一致。指定条件下的超时来自运营商 IPv4 DNS 的 TCP 不可用及客户端等待期限，没有发现 dnsmasq-rs 新增的此类缺陷；产品代码未修改。** 实际耗时有小幅差异，详见下文，未宣称逐毫秒等价。

## 如何核验

路由器仅两次只读查看，没有替换或重启 dnsmasq。现场为 `resolv-file` 提供 **IPv4、IPv4、IPv6、IPv6** 四个上游，未启用 `strict-order`、`all-servers`，没有显式 `server=`，缓存为 1000。收尾确认磁盘、ROM、实际运行进程仍为原 C。

在 Oracle 独立 network/mount/PID namespace 中，C/Rust 顺序执行相同配置、问题和故障日程；上游全部为虚拟 loopback 服务，未访问真实运营商 DNS。使用 `--keep-in-foreground`，保留 C 正常部署时的 TCP fork 行为，未用改变该语义的 debug 模式。C 在私有 chroot 使用镜像原库，核验实际 `/proc/<pid>/exe` 和库映射。

固定新问题名和 TTL=0，先以缓存 0 隔离选路，再以现场的缓存大小 1000 复验未命中路径。分别注入 **RST 立即拒绝**与 **INPUT 丢弃 TCP 包形成 SYN 黑洞**；捕获 SYN/RST、上游请求/响应、nft 丢包计数及客户端完整 wire。UDP 预热只允许指定上游回答，明确控制父进程首选。

## 实际结果

共 **13 组条件、50 对查询**：每版 37 次 TCP 观察（36 次正常回答、1 次预期的 2 秒超时）和 13 次 UDP 回答。所有对应正常答案的 wire 一致，上游目标顺序和会话复用一致；所有 daemon 存活检查及退出清理通过。

| 条件 | 精确 C | Rust |
| --- | --- | --- |
| IPv4 TCP 立即 RST，冷启动或 UDP 首选 IPv4 | 依次尝试 v4a → v4b → v6a，毫秒级成功 | 相同 |
| IPv4 TCP 黑洞、UDP 首选 v4a、客户端只等 2 秒 | 超时；窗口内只尝试 v4a | 相同 |
| 同样黑洞、客户端允许等 25 秒 | 两次连接等待后经 v6a 成功，10.175–10.573 秒 | 同顺序成功，10.008–10.012 秒 |
| 同样黑洞、UDP 首选 v6a | 直接 v6a，2 秒窗口内成功 | 相同 |
| 已经通过 v6a 成功的同一 TCP 连接再问 AAAA | 复用原上游连接，立即回答 | 相同 |
| 黑洞仍在，再建立新的客户端 TCP 连接 | 重新继承父进程 v4a 首选，再等约 10 秒 | 相同 |
| UDP 重选到 v6a 后，新建客户端 TCP | 直接 v6a | 相同 |
| 首次经 v6a 成功后恢复 IPv4 TCP | 旧会话继续复用 v6a；新会话立即用 v4a | 相同 |
| 建连期间第 2 秒解除 IPv4 黑洞 | 仍在等待的 v4a 连接约 2.071 秒完成 | 约 2.083 秒完成 |

**计时差没有隐藏在“通过”里。** 五次完整跨越两个 IPv4 黑洞的配对观察，最大耗时差为 **0.562 秒**。源码中两版名义连接超时都是每台 5 秒；C 使用 `SO_SNDTIMEO`，Rust 使用非阻塞连接和 `Instant` 期限。实测差异与计时机制、内核粒度及调度相符，但没有把全部差值严格归因于某一个因素。若客户端截止时间恰好落在两者实际完成时刻之间，Rust 可能已回答而 C 仍在等待；**首选 IPv4 且 TCP 黑洞时，2 秒截止两版都失败**。没有发现 Rust 额外卡住、不尝试 IPv6 或恢复更慢。

## 为什么现场成功率会不同

两版都没有独立的“TCP 健康上游排行榜”：新 TCP 会话继承父进程记录的 **UDP 首选**，本轮通过成功 UDP 答复控制该状态。精确 C 的非 REFUSED 回复还可能更新首选，不能将其笼统理解为只记成功解析的上游。IPv4 上游可以一直成功回答 UDP，却一直丢弃 TCP。此时新的 TCP 客户端会重复先等 IPv4；TCP 子会话后来成功用到 IPv6，也不会反写父进程的 UDP 首选。没有另设 TCP 故障冷却或全局恢复定时器。

因此，UDP 首选为 IPv4 时可以复现连续短窗失败，首选为 IPv6 时又可以连续成功；**不能把不同时间、不同父进程首选和缓存状态下的成功率直接当作实现差异。** 立即 RST 与静默丢包也不同：前者两版都迅速转到 IPv6，复制短窗超时的是后者。

这关闭了[真机报告](DEVICE_TRIAL_20261014.md)留下的本项兼容性疑问：给定的运营商 IPv4 TCP 故障在精确 C 上同样发生，Rust 没有新增选路/失败转移缺陷。当天没有保留每个请求的上游连接轨迹，故不能事后断言那 11 次 Rust 查询逐一选中了哪台上游，也不把此次隔离实验冒充当天完整流量重放。此结论不替代真机报告中的 DHCP、长期运行和包级部署资格。

## 修改、验证与范围

仅新增[差分工具](../../tools/dnsmasq/tcp_upstream_parity.py)、[校准测试](../../tools/dnsmasq/test_tcp_upstream_parity.py)和报告收据；在独立分支完成后合入 main，未推送 GitHub。7 项工具单测通过，另基于真实 C 原始记录注入 9 种错误，错选上游、响应变化、额外等待、未复用连接、缺观察、进程退出及清理失败均被拒绝。

首次 DROP 运行因测试工具的 nft 规则格式错误而没有建立故障环境，明确作为 **harness failure** 保留，不计产品失败或通过；修正规则后才执行上述完整矩阵。最终提交仅把工具默认等待/恢复时刻改为与实际命令显式采用的 25/2 秒一致，没有改动已保存的实际记录。

核对 C `forward.c` 的 `tcp_talk/tcp_request`、`dnsmasq.c` 的 fork 路径，与 Rust `dns/tcp_upstream.rs`、`dns/tcp_exchange.rs`、`daemon.rs::tcp_snapshot` 相符。本轮覆盖所列默认选路及 SYN 丢弃/RST；不是全部 DNS 故障类型的穷举，也没有在物理路由器上重跑替换。Oracle 临时进程和宿主挂载已核对无残留。

原始材料保存在本机忽略目录 `private/tcp-upstream-parity-20261014/`，配置和现场地址未入 Git；[SHA 清单](audits/tcp-upstream-20261014/evidence-manifest.json)保留初始工具失败、全部最终结果及源码/运行产物身份。
