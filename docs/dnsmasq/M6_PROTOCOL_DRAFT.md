# M6 性能评估冻结方案草稿

当前只准备方案，没有启动正式性能窗口。M5报告完成并由用户决定最终体积、构建方式后，再冻结同一源码的最终ELF/APK、配置与此协议；若选择opt-level s，必须先完成受影响功能回归，不能复用opt-level 3的性能身份。

比较精确镜像musl C与最终Rust ELF。在Oracle的独立网络namespace运行，服务固定同一CPU、客户端与采样固定其他CPU。每侧记录源码、ELF SHA、工具/配置/种子、CPU/内核及频率策略；窗口内没有构建、其他测试或后台任务。结果只说明该Oracle环境，物理路由器不操作，也不外推为M7真机验收。

| 负载 | 冻结配置与观察 |
| --- | --- |
| UDP缓存命中 | 4096个短名A记录，填满并逐条证明命中；窗口内零上游请求。默认20客户端，另测1客户端。 |
| UDP缓存未命中 | 上游固定有效A响应、TTL和数据；查询序列不重复，核对每次实际上游请求与回复。 |
| 混合DNS | 固定种子，80%命中/20%未命中，A/AAAA/CNAME/TXT固定比例；保持两侧相同成功数与实际上游量。 |
| 故障与恢复 | 同一时刻停止/恢复上游；分别记录故障期间错误、恢复后的正确回复和延迟。故障预期超时与意外超时分别计数。 |
| TCP | 20个保持连接的客户端，固定查询与分帧方式；本地、缓存及真实上游分开，不把fork/单owner不同调度隐藏在总均值里。 |
| DHCP | 20个冻结MAC/CLID，DISCOVER/REQUEST/renew/release固定序列；no-ping常规与实际冲突探测分开，记录每事务正确率与耗时。 |
| Reload并发 | 固定hosts/resolver变更与SIGHUP次数，在固定DNS/TFTP背景量下记录服务间隙、发布边界和完成时间。 |

每个负载先30秒预热，再120秒计量，C/Rust各5轮交替顺序。每轮独立重建规定初态；日志、query-port、0x20、EDNS、缓存与绑定参数相同。仅主负载的配置开启日志，不用生产关闭日志与C开启日志比较。缓存满载RSS另保留整个窗口的样本及live occupancy、FD和退出回收证据。

每轮报告完成QPS、错误/超时、p50/p95/p99、CPU秒/正确查询、RSS/FD/线程数以及上游副作用；汇总给中位数、范围和全部5轮原值。限速试验按相同已完成请求量比较CPU和延迟；吞吐试验逐级提高固定请求率，找零额外错误且不持续积压的最高完成量。

收益标准暂定为：主要DNS负载的中位吞吐提高至少10%，或相同正确请求率下CPU/查询降低至少10%，且5轮中至少4轮方向一致；同时普通负载不增加错误，p99不劣化超过10%，其他主要负载吞吐不回退超过5%。达不到就写“未证明性能收益”，保留功能、体积与RSS结果，不改负载或挑选最好一轮。最终体积/RSS接受标准由用户在M5报告后决定。

若用户选择opt-level s，增加同源码opt3/s的配对轮次，明确其体积收益、CPU和尾延迟代价；这些轮次属于后续正式M6，当前不执行。
