# 审计 C：真机资源与性能

日期：2026-10-14。设备：小米 AX3000T，OpenWrt 25.12.5
`r33051-f5dae5ece4`，Linux 6.12.94，双核 Cortex-A53。

**结论：日常负载的资源预算通过；本审计不支持对当前冻结版本无条件上线。**

在本机实际配置映射的日常负载下，Rust 有充足的内存、CPU 余量，响应增量可以接受：主进程典型 RSS 比 C 多 **1,276 KiB（1.25 MiB，+104.6%）**；20 DNS QPS 加 DHCP 时，额外消耗 **0.171 个整机 CPU 百分比点**；UDP p95 增加 **0.312 ms**。但 1,000 QPS 压力档出现已证实的 `REFUSED` 和约 1.06 秒的客户端计划发送至完成长尾，原因未定位。没有证据证明它们由内存或 CPU 耗尽造成，也不能因平均资源尚有余量就忽略这些上线限制。

每个窗口约 180 秒：20 秒空闲、20 秒预热、120 秒计量、20 秒排空/空闲。日常顺序 C/R、R/C、C/R；较重负载 R/C、C/R。每窗启动全新实例，不运行两种候选实例互相竞争。没有尝试饱和压测，也不把 1,000 QPS 当作吞吐上限。

DNS 查询类型按生成器序列约为 50% A、25% AAAA、15% CNAME→A、10% TXT；80%选择重复名、20%选择唯一名。由于 TXT 默认不缓存、CNAME 共享目标、TCP 冷缓存和缓存容量，**这不是 80% 实测缓存命中率**，实际转发数另外计量。日常重复名 bank=100，较重档 bank=800。固定回环上游返回可通过实际 rebind 策略的地址，TTL=3600 秒；没有访问真实网站或向公网制造查询负载。

主测试 DHCP 不携带主机名。补充配对增加 DHCP option 12 的 `audit-client-N`，并在预热中逐一验证 20 个 `.lan` 名称可解析到租约地址；验证查询不进入 120 秒计量段。FQDN option 81 未覆盖。

每个 DHCP 周期执行 DISCOVER→OFFER→REQUEST→ACK→续租 REQUEST→ACK→RELEASE；验证 xid、MAC、地址、服务器标识、租期/T1/T2，排空后验证租约文件恢复为初始集合。20 个轮换身份不代表同时新增 20 条租约；较重档不是满 150 租约的测试。

两种原始 ELF 的 DHCP 均默认绑定通配地址，仅设置 `interface=lo` 不足以隔离。因此专用启动工具仅在启动系统调用边界将 DHCP 和临时控制 socket 的通配绑定改为 `127.0.0.1`；观察到 DHCP 及 DNS UDP/TCP 成功绑定后立即脱离，计量前检查 `TracerPid=0` 和实际 socket。没有在计量时使用 ptrace。启动工具在 Oracle 上通过了绑定、参数恢复、脱离及拒绝错误地址/端口/提前 fork 等 7 项正负控制。

DHCP 使用 dnsmasq 自带的 `giaddr=255.255.255.255` 本地测试扩展，报文从 `127.0.0.2:15467` 单播到 `127.0.0.1:15467`，回答回到源地址/端口；不使用真实客户端、ARP 注入、广播或 br-lan。该路径跳过真实 LAN 的 ICMP 冲突探测，Rust 还多一次扩展处理的包复制。因此 DHCP 结果覆盖动态分配、解析、租约更新和文件持久化的资源成本，不能称为真实 Wi-Fi 广播事务的端到端延迟。

CPU 取 `/proc` 的 user+system，并纳入存活及已回收子进程。单核 100% 表示用满一个核，整机占比为其一半。实测 `sysconf(_SC_CLK_TCK)=100`，这是 `/proc` CPU 计时刻度，不是对内核 `CONFIG_HZ` 的测量；120 秒窗口单个计数 tick 为约 0.0083 个单核百分比点，这不是整个进程树的误差上限。内核缺少 `/proc/PID/task/PID/children`，工具按 `/proc/*/stat` 的 PPID 识别子进程；另保留全部子进程排空后的首末 CPU 总量，避免漏算 C 的 TCP 工作进程。1 Hz 活跃区间采样不是原子操作，边界附近子进程退出仍可能带来量化偏差。

延迟为本机实际发送至正确响应的时间；同时记录计划发送滞后，避免隐藏生成器排队。TCP 延迟不包含最初建连握手；CPU 则保留测量期内的连接处理。分位数先逐窗计算，再取窗口中位数；不将窗口混成巨大样本宣称统计显著性。日常 DHCP 每窗仅 12 个周期，p95/p99 只能描述本次最慢样本。

### 连续内存观察

初始 Rust 压力窗在缓存周转过程中仍有匿名内存增长，不能直接称为平台。为此保留同一 PID 和堆，补做三个约 180 秒窗口；每段仍有前后空闲、预热、120 秒压力及健康门禁，seed 依次为 1/2/3，让唯一查询名继续更新。各段数据取走后删除已完成段的 tmpfs 文件，daemon 不重启。

| --- | ---: | ---: | ---: |
| 第 1 段 | 3,540 | 1,628 | 3,660 |
| 第 2 段 | 3,516 | 1,604 | 3,684 |
| 第 3 段 | 3,488 | 1,576 | 3,700 |

三段 PID/starttime 均相同；每段初始租约、文件和进程身份均核验，唯一查询名持续更新。首段之后排空后的 RSS 和匿名内存没有继续累积；活跃峰值从 3,660 增至 3,700 KiB（+40 KiB，约 1.1%），不称为严格硬上限。这些数据支持本次短期内存预算通过；不据此断言分配器机制或长期无泄漏。三段仍有 1/14/23 次 UDP `REFUSED`，独立解码确认这 38 包均保持请求 ID/问题且 RCODE=5（356,400 次已发 UDP 的 0.01066%），报文分类另见压力证据，不能因内存稳定就把它们抹掉。详见 [retention-summary.json](audits/20261014/predeploy_resources/retention-summary.json)。

全部正式窗口及连续观察中，Rust 主进程 RSS 峰值 **3,712 KiB（3.625 MiB）**；整机 `MemAvailable` 最低 **102,928 KiB（100.52 MiB，总内存的 43.1%）**，无 swap。这个余量已经包含同时存在的生产服务、测试实例、生成器、上游、监测程序和 tmpfs 文件。仅就已观测的用户态常驻页，即使把整个 Rust RSS 峰值都作为新增预算参照，也只有总内存约 **1.55%**。这是保守预算参照，不是实测物理 RAM 增量或硬上限；内核 socket 缓冲等未单独归因，其总体影响包含在整机可用内存中。各 Rust 窗口的 VmHWM 与采样 RSS 峰值一致。


## 日常影响与上线判断

独立的 181.196 秒生产被动观察中，DNS 转发增加 5、local answered 增加 0、DHCP 各计数未增加，约 0.0276 次 DNS 查询/秒；观察工具没有向生产 DNS 发送测试查询。[passive.json](audits/20261014/predeploy_resources/passive.json) 保留全部计数差值。观察时段较空闲，不代表家庭晚高峰；20 QPS 档本身约为该短观察平均值的 725 倍。

在当前配置和家庭负载下，预计主要变化是常驻内存增加约 **1.3 MiB 的主进程 RSS**、本地 UDP 回答增加约 **0.1–0.3 ms**；这不是实测物理 RAM 增量，也不是网页加载时间。即使把 20 QPS 长时间维持，额外整机 CPU 也只有约 **0.17 个百分点**。因此日常 CPU 开销不明显，短期内存预算有充分余量。

粗略按日常窗口的增量线性缩放，1 QPS 对应约 0.0085 个整机 CPU 百分比点，生产短观察的 0.0276 QPS 对应约 0.00024 个百分点；这是量级估算，低于本次 CPU 计数分辨率，且混合了测试 DHCP 开销，不能当作真实日常精确测量。12 小时租期在补充报文中实测 T1=21,600 秒、T2=37,800 秒；按 4 个活跃租约、持续在线且在 T1 续租的简化模型，约为 16 次续租/日，明显低于本次每 10 秒一个完整周期的日常档，更低于每秒 2 个周期的补充档。开机、新客户端和实际使用高峰不在这个简单估算内。

健康检查和可用资源没有显示生产 DNS/WAN 被本实验破坏。它们不能证明 VPN、满速转发、视频或其他业务 QoS 完全无影响。**可以确认日常资源预算通过；压力档拒答和长尾仍是上线保留项，当前冻结版本不应凭本报告无条件放行。**

## 边界与未覆盖范围

- 这些窗口证明的是当前配置和所测负载下的资源余量，不能证明数天/数周运行没有内存泄漏。
- 未测真实 LAN 广播、ARP/ICMP 冲突、Wi-Fi 空口、真实客户端续租和完整上线包装；没有停止或替换生产 dnsmasq。
- 原机无 `smaps`/`smaps_rollup`，无法提供 PSS/USS；进程树 RSS 会重复计算 C 子进程共享页。Rust 静态 ELF 从 `/tmp` tmpfs 执行，映射页计入 `RssShmem`，不能把上传 ELF 大小和 RSS 再次相加。正式从闪存执行的文件页归类、共享和可回收性会不同。
- 未覆盖 DHCP FQDN option 81、IPv6 DNS 传输（AAAA 回答已测）、公网递归延迟、慢/失效上游、重传风暴、DNS cache TTL 到期、NXDOMAIN 高占比、TCP 大量并发、满 150 租约、生产 UBus 连接、reload、TFTP，以及与 VPN/满速转发等同时争抢 CPU 的情况。
- 固定上游、生成器、监测进程及健康检查也运行在路由器上。整机 CPU 和 `MemAvailable` 是整个实验的实际压力，不能直接当成单独替换服务的资源增量；daemon 进程树 CPU 单独统计。

## 安全与证据

每窗前后及约每 25 秒检查生产 DNS、WAN 状态和公网连通性、内存余量、生产进程身份及二进制/配置 SHA256；低于 64 MiB 可用内存或健康检查失败即中止清理。远程脚本另有 225 秒硬超时，窗口退出按 PID/starttime 核对后清理；总收尾再按独占目录关联的命令行核验测试进程、文件及端口。

正式配对与连续观察共 **15 个约 180 秒窗口、155 次生产健康检查**，DNS、WAN 状态、公网探测、生产进程 starttime 和二进制/配置哈希始终通过。主测试在第一个 C 压力校验失败后按门禁结束，保留 8 窗证据；新增完整错误包记录后补测 2 窗，再加命名 DHCP 2 窗和同 PID 连续观察 3 窗。窗口顺序和中断状态均保留，未挑掉失败数据。

四个正式运行目录均已删除，测试进程为 0、测试端口占用为 0；TCP TIME_WAIT 不当作仍在运行的测试监听器。最后一次运行结束后生产 DNS、WAN、公网探测正常，`MemAvailable=113,428 KiB`。没有停止、信号通知或替换生产 dnsmasq，没有写闪存、装包或修改系统配置。

测量前的短试跑只用于修正工具与隔离：SFTP 不可用改用 SCP 协议；文档示例 IP 被真实 rebind 策略拒绝后改成可通过策略的合成回答；普通 relay 地址会触发回环 ICMP“地址已占用”，改用 dnsmasq 本地测试扩展；补齐无 `/proc/.../children` 时的子进程识别。试跑不进入正式性能统计。启动隔离工具的 7 项正负控制见 [isolation-controls.json](audits/20261014/predeploy_resources/isolation-controls.json)。
