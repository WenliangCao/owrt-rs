# ubusd 持续优化目标与研究状态

2026-09-20 用户明确创建持续目标：把 ubusd 优化到判断已达极限时再停止。
目标处于进行中；不能把一次优化被拒、少数 pilot 波动或尚未定位的开销归因于 Rust/C 的语言极限。

性能和内存同时追求优于镜像匹配 C，尽可能优于正式 R89。正确性、既有修复、失败和背压语义优先。
最终判断来自物理 AX3000T，构建机仅编译和预筛查。生产始终运行 C，候选不部署；每个隔离窗口清理并验证健康。
每个逻辑步骤独立 commit，预先冻结假设与采样，保留全部反向结果。统计与记账规则见
[R95 研究规则](R95_PERFORMANCE_RESEARCH.md)。

## 当前阻断性发现

[R113 FD 帧边界复现](reviews/r113-fd-boundary-discovery.json)已确认 R109/R112 的
跨帧 read-ahead 会把同一 sendmsg 中的 FD 交给错误请求，并错误保留 body 阶段的 FD。
R109 现在仅是历史性能对照，不能称为已完成兼容性验收的可部署版本。生产一直为 C。
先按精确 C 的 prefix/body 消费边界修复，再重建性能基线；R112 的确认采样尚未开始。

## 已有证据与当前起点

- 当前接受源码为 R100+R103 与 R109 方法名存储改动（代码提交 `2fbfd88`），发布 ELF
  `1dfb317c…15259`；
  `d89b8d2` 记录相同源码重建，本轮再次在相同规范路径重建并逐字节核对一致。
  已修复事件 epoch 回绕，并保留早先的方法名、ACL、背压和协议修复。
- [R103 直接事件实测](reviews/R103_UBUSD_EVENT_SEND_BORROW.md)已覆盖原版 libubus 调用者；
  这不等于完整组件、内存或九组件组合验收。后面的 R95–R99 记录是历史实验阶段。
- [R104 接收缓冲即时释放](reviews/R104_UBUSD_RX_RELEASE.md)已因 CPU 退步撤回。
  R105–R108 已检查共享空缓冲、阈值和内联提示：41 条实机单测、协议差分及六组构建机功能/恢复门通过；
  [内存四方对照](reviews/r105-rx-spare-memory-results.json)显示 64 连接 RssAnon 中位数
  当前版/候选/C/R89 为 402/100/118/82 KiB。候选未全面胜 R89，VmData 也仍高于 C。
  [直接事件 CPU](reviews/r105-rx-spare-user-event-results.json)相对当前版增加约 1.5–3.1%，
  [十窗口独立交错复查](reviews/R105_UBUSD_RX_SPARE.md)确认有接收者时 daemon CPU 增加
  1.22%–2.30%、总 CPU 也增加；R106 阈值与 R108 内联复查仍无法同时保住高连接 CPU，候选均已拒绝并移出工作源码，补丁保留。不能只报告内存收益。
- [R110-A 一次初始化栈接收](reviews/R110A_UBUSD_RX_SHARED_EXACT_RESIDUAL.md)也未通过冻结门：
  64 连接增长 44 KiB >38.4 KiB，R103 单监听者 low/loaded CPU 十窗口全增；
  C loaded 单监听者 daemon +3.32%、总 CPU +2.05%。正确性与清理均通过，仍拒绝运行时改动。
  Oracle 旧 perf 计数未同步，不能归因代码布局；先补同步计数，暂不开始借用派发 B。
- [R111 同步计数与消融](reviews/r111-perf-interpretation.json)发现启动路径长度会改变同 ELF 的
  指令计数，已用同 ELF 配对重现并统一路径。去掉重复客户端查询后，用户态指令较 R110-A
  下降约 4.3%，较 R109 下降约 1.5%；Oracle CPU 未显示同等收益，不能替代实机 CPU。
  实验在独立分支，正式源码仍为 R109。
- [客户端表实机请求堆诊断](reviews/r110-client-table-memory-results.json)：64 个 Client 内联
  表与凭据共 41608 字节，其中表本身 41096 字节。Box 容器诊断为 22664 字节；
  尚未证明实际 daemon RSS 或 CPU 优势。下一步独立验证此存储选择，不继续猜接收控制流。
- 保留路径借用遍历、路径共享和方法名字/ACL 兼容性修复。
- [R97 方法存储候选](reviews/R97_UBUSD_METHOD_STORAGE.md)减少请求堆和部分查询 CPU，
  但单方法注册 CPU 八轮全部上升，中位 +1.62%；已撤回实现，补丁和正负数据完整保留。
- R97 阶段的接受运行时为 `5a19517` 方法兼容性修复，ELF `527f8683…`，已被上述 R103 取代。
- R97 当时发现小签名注册慢于 C；后续 R100/R101 已改善这一单方法工作负载。
  [原版 libubus 十窗口](reviews/R101_UBUSD_C_CLIENT.md)中 daemon CPU −5.66%、总 CPU −2.85%，
  caller CPU 区间仍跨零。不能以此代表全部注册、完整内存或组件协同。
- [R98 按需事件编码第一版](reviews/R98_UBUSD_EVENT_LAZY.md)暂缓：注册自身 CPU 下降约 8–16%，
  但有接收者成本上升，独立查询双基线复查也触发 CPU 回退门。补丁和全部数据已保存。
- [第二版单遍借用投递](reviews/R98_UBUSD_BORROWED_EVENTS.md)完成 67 个通过的实机窗口；注册及事件 CPU 改善，
  但事件仍未胜 C，部分查询需继续调查，尚未接受运行时改动。
  首个不完整 block 因外部 HTTPS 健康检查失败已整体保留并排除，完整健康复查后从头重采。
- [R99 注册回复与计量](reviews/R99_UBUSD_REGISTRATION_MEASUREMENT.md)：按用户转来的评议补 CPU affinity、
  长循环和同二进制 A/A 校准。首个 320 万周期 A/A 未达到 ±0.5% 带，约 1% 效应仍无法据此判定；
  改用窗口内交错对照继续校准。独立回复候选的 30 条、组合候选的 32 条实机单测及协议差分均通过。
  当时 scratch 多保留 16 字节，后由 R100 栈回复避免；R99 方案已被接受的 R100/R103 取代。
  交错 A/A 八窗口同样未过 ±0.5% 校准带，不能宣称约 1% 的变化已可稳定分辨。
- [R109 方法名存储](reviews/R109_UBUSD_METHOD_NAME_STORAGE.md)已接受：去掉规范化方法 blob
  之外重复保存的 ACL 名字分配，保留 `Vec<Method>` 布局。十窗口 exact-image C caller
  实测 daemon CPU −7.01%、总 CPU −3.77%；相对 R103 daemon CPU −1.19%。请求堆诊断
  在 128 个单方法对象上下降 17.4%。这些结果只覆盖单方法注册，不能推广到全部负载。

## 按证据推进的队列

1. 事件生成：R100/R103 已实现按需编码并接受。继续补充分辨能力、独立连接的并发与规模证据；
   无接收者不编码，同时验证匹配、多接收对象、
   不匹配订阅、去重、序号回绕、删除、监视器和慢读者；计入完整接收校验成本。
2. 注册回复：R100 已改为固定长度栈编码与借用发送，消除了 ADD/REMOVE DATA 临时构造及复制。
   保留排队时拥有数据、监视器顺序和删除通知边界；不得再把这项记作未开始。
3. 方法存储：R109 已去掉重复方法名字分配并接受；继续验证 16/64 方法、共享类型、
   失败释放和 steady-state 查询，不能重新引入 R97 已修缺陷。
   空签名、坏属性、嵌入 NUL、共享类型和失败释放必须纳入，不能重新引入 R97 已修缺陷。
4. 事件投递本身：已用单遍借用投递消除目标快照，直接发送时借用载荷，排队时拥有数据。
   R103 已去掉用户事件字段的提前复制；继续 profile 剩余编码、遍历、排队及多连接成本。
5. 接收：R105–R110-A 已覆盖小/大帧、成批帧、部分读、SCM_RIGHTS、低/高连接规模、
   精确回复校验和高连接活动流量。共享空缓冲方向在内存上有局部收益但 CPU 退步，当前接收候选全部拒绝。
   仅在提出全新分配/所有权设计并预先区分其成本后再重启实验。
6. 重新 profile 剩余热点，并补原版 libubus 调用者、实际调用链、规模扩展、
   精确内存/峰值和充分独立样本确认。与九组件组合的优势仍需单独验证。

精确 C 与 Rust 的 ID 都调用 `getrandom(..., GRND_INSECURE)`；不把接口相同处猜成性能差异。
队列是待证伪假设，不是承诺每项一定保留，也不穷尽后续 profile 发现的新方向。

## 停止判断所需的证据

停止前必须重新审阅热路径、分配、复制、系统调用、数据结构及失败路径，明确哪些成本来自必要协议工作，
哪些来自实现选择。已知可行改进需要有实验结果或明确排除依据；退步和计量缺口不能删掉。
确认实验、功能覆盖和内存边界必须与声称的适用范围相符。

有限实验不能证明整个 Rust 语言对所有输入的理论极限。最后的判断应明确写成在本硬件、镜像、
兼容性约束和已覆盖工作负载下的可实现极限，并列出未胜出的 C/R89 项、剩余不确定性及停止理由。
在仍有具体可验证方向时，继续工作，不提前结束目标。
