最新状态（2026-09-26）：**性能专项已关闭，R136 冻结为唯一 Rust 运行时基线。**
R142、R144、R146 等候选均未获升级；R146 的正确性通过但固定 monitor 延迟门失败，

[ubusd 最终状态](UBUSD_FINAL_STATUS.md)；本页以下内容保留完整历史研究记录。

[R143 当前 R136 的 monitor 实机覆盖](reviews/R143_MONITOR_RESULT.md)已完成十个性能窗。

内存首个启动尝试因下载后的本地文件缺执行位而失败、零样本，原记录保留；仅修权限后，
同 SHA、同三窗规则的独立系列通过。全部合格窗健康与清理通过，生产仍为 C，独立审计一致。

[R145](reviews/R145_MONITOR_PROFILE_PLAN.md)先补当前 monitor 的函数热点。诊断重建只输出
linker map，控制和诊断 ELF 都必须逐字等于已测 R136，不能套用其他版本地址；固定 C/R136
采样预算，区分用户态、内核、未知符号与 caller 开销，不用 wall−CPU 推断等待。
分散发送原 payload 是尚未实现的机制，需要先看本负载热点，不能把减少复制直接写成延迟收益。

按用户性能九成、开销一成的取舍，R136 继续作为当前工程基线。它不是“所有指标全面胜 C”、

全面排名仍未获本轮证明；四项实机慢尾也未关闭。重开优化应有新的可定位机制或实际负载证据，
不再靠相同控制流的微小变体及追加窗口争取通过。

FD 仍使用 [R134 明确的 read-ahead 契约](reviews/R134_UBUSD_VALIDATION.md)：常规发送方与 C

历史判断，不再代表当前基线或现行 FD 验收契约。

## R113–R131 阶段的阻断与基线判断（历史）

[R113 FD 帧边界复现](reviews/r113-fd-boundary-discovery.json)已确认 R109/R112 的
跨帧 read-ahead 会把同一 sendmsg 中的 FD 交给错误请求，并错误保留 body 阶段的 FD。
R109 现在仅是历史性能对照，不能称为已完成兼容性验收的可部署版本。生产一直为 C。
[R113 修复](reviews/r113-correctness-results.json)已通过 44 条实机单测、七组原协议门、
新增 FD 差分及六组主机功能/恢复门。修复在 `befbb16` 实验分支，尚未接受性能；
现在按精确 C 的 prefix/body 消费边界重建性能基线。R112 的 CPU 确认采样未启动。
[R113 内存基线](reviews/R113_UBUSD_BOUNDED_RX_BASELINE.md)十窗口已完成：64 连接
RssAnon 增长两次均 28 KiB，低于同轮 C 的 48 KiB、R89 的 36 KiB，通过冻结门。
无连接和断连后 VmData 仍比 C 高 4 KiB；十二个 CPU 探索窗口已完成，C 对照六个
lane/规模单元的 daemon CPU 两次均上升（中点约 +3.78% 至 +15.32%），尚无运行时接受结论。
[R114 借用入站派发](reviews/R114_UBUSD_BORROWED_DISPATCH_PLAN.md)独立候选 `579c879`
已通过正确性门；路由器上相对 R113 的总 CPU 局部下降约 0–2%，相对 C 仍慢约 3–12%，内存与 R113 相同，故拒绝运行时接受。
[R115 事件兴趣同步消融](reviews/r115-results-summary.json)去掉了直写成功后的冗余 touched/poller 更新；相对 R114 的 user_8_1 总 CPU 最多下降约 1.84%，但相对 C 六个单元仍全部上升约 2–8%，故拒绝。
[R116 接收 scratch 消融](reviews/r116-results-summary.json)在每个 readiness 回调复用 recvmsg 的 iovec/msghdr/SCM_RIGHTS 状态；45 条单测、Oracle 和路由器正确性门通过，但相对 R115 的路由器 CPU 变化混合且相对 C 仍上升约 4.4–12.9%，故拒绝。

[R117 小帧 owned-body 消融](reviews/R117_UBUSD_SMALL_FRAME.md)保持了 R113 的 prefix/body
FD 边界，45/45 单测通过，并在未安装候选的路由器 pilot 后完成清理和健康复核；但它把 R115
的小帧 `Cow::Borrowed` 改成每帧 `Cow::Owned`，低量 pilot 相对 R115 的 daemon CPU 为
`user_1_1` +3.66%、`user_8_1` −0.28%、`user_1_0` +3.08%，没有同号改善，停止接收路径
实验，不再启动高连接和多窗口验收。

全范围版本选择见 [R89–R116 候选审计](reviews/UBUSD_VERSION_SELECTION_R89_R116.md)。
结论是：R89 仅作历史性能参考；R109 及 R94–R112 的读前缓冲谱系被 FD 差分硬拒；R113
是接收正确性基线；R115 是 R117 阶段的开发基线，当时仍比精确 C 慢。
当前开发候选为其后的 R124，已有门通过不等于证明不存在 bug，也不代表已完成最终全组件验收。生产继续使用 C。

- 保留路径借用遍历、路径共享和方法名字/ACL 兼容性修复。

## R124–R131 阶段的前沿结论（历史）

[R124 当前 ubusd 实用前沿判断](reviews/R124_UBUSD_FINAL_FRONTIER.md)汇总了最新路由器证据。
在性能九成、开销一成的取舍下，R124 是当前 Rust 集成候选基线：查询/调用、单接收者事件和连接驻留已明显优于或不高于 C；
八对象 fanout 约慢 2%，注册结论须受控重测，不能称全面胜 C。恢复审计发现 R128 daemon/caller 未显式钉核且启动 argv0 不同，原先 CPU1/统一 argv0 的描述错误；其单方法 +3.1% 只保留为原条件下的观察，不能归因成已确认的实现退步。R127 的 daemon CPU1/统一 argv0 有证据，但 caller CPU0 的原描述也错误，查询/调用数值只适用于客户端未显式钉核的调度条件。R126 的功能优化因 A/A 校准失败没有合入。
生产继续运行 C；R124 进入九组件协同前，还需以实际组合负载复核这些剩余路径。
后续 R131 共享路径补测已落实 CPU1/CPU0 和统一 argv0，关闭上述注册计量缺口：同轮 R124
单方法 mean/p95 高 C 1.42%/50.93%，16 方法高 2.56%/43.95%；不能再把全部注册差距仅记为未测。
完整原始窗口保留在 [R131 共享路径结果](reviews/R131_SHARED_PATH_RESULT.md)引用的报告中。

R130 对成功 ADD_OBJECT 的 DATA+STATUS 做了一个受限合并：Oracle 机制审计确认每个成功 ADD 少一次
`sendmsg`，R124/R130 为 488/367 次；native、目标 musl 单测和六组功能/恢复门均通过。随后在物理路由器
完成 18 个真正固定 CPU/argv0 的新窗口，但两个注册 mean lane 没有达到预冻的六块全降且中位至少 −3%，
并出现 register-1×8 与 prefix lookup 的 p95 回退门。因此 R130 不接受为 R124 新基线，候选与全部负结果保留。
R130 证明了系统调用减少本身没有转化为稳定的路由器延迟收益；下一步不再为这条合并路径追加窗口或把它
与 R124 拼接。详见 [R130 机制验证](reviews/R130_UBUSD_ADD_REPLY_MECHANISM.md) 与
[R130 路由器结果](reviews/R130_UBUSD_ADD_REPLY_RESULT.md)。

R131 原 18 窗口只记录循环累计 wall/CPU，后已更正为“均值子项有益、完整验收 pending”，
不能删去原计划未测的尾延迟门。随后 [R131 补测](reviews/R131_UBUSD_COMPLETION.md)完成 77 个新实机窗口：
53 条目标单测、协议/FD、owner/monitor/慢读者功能全部通过；同连接八监听对象相对 R124 的
mean/p95/p99 分别下降 16.62%/20.04%/17.25%，相对 C 也有收益。
但注册 1/16 方法的 p95 相对 R124 六对全升，中位 +15.25%/+5.0085%，冻结共享路径门失败；
monitor mean 仍高 C 6.49%。1 KiB 八监听事件多保留 12 KiB RssAnon、28 KiB VmData，
后者触发调查门；1→1000→10000 事件在本负载未继续增长，原 flag 保留。
R131 不提升为通用基线，保留其事件性能实现与全部正负数据。R124 继续作保守基线而非最终完成版，
生产保持 C，测试目录及进程均清理。后续应先定位注册回退和 monitor 开销，而非再换控制流变体。
大载荷 fanout 的延迟/CPU、长时间/饱和/更多活跃连接、完整峰值内存和九组件组合仍不能宣称已验收。

## 停止判断

停止前必须重新审阅热路径、分配、复制、系统调用、数据结构及失败路径，明确哪些成本来自必要协议工作，
哪些来自实现选择。已知可行改进需要有实验结果或明确排除依据；退步和计量缺口不能删掉。
确认实验、功能覆盖和内存边界必须与声称的适用范围相符。

有限实验不能证明整个 Rust 语言对所有输入的理论极限。最后的判断应明确写成在本硬件、镜像、
兼容性约束和已覆盖工作负载下的可实现极限，并列出未胜出的 C/R89 项、剩余不确定性及停止理由。
R117 阶段的停止依据仅适用于当时的接收候选：R110、R116、R117 有负结果，R114/R115 有局部收益但没有达到 C。
R121 profile 后的 R122–R124 已发现并验证新的改进，不能再写成“当前所有低风险方向都失败”。
R126 的提前退出假说已完成功能回归但因计量 A/A 门失败而停止。
[R127 当前 ELF 广覆盖矩阵](reviews/R127_UBUSD_MATRIX_RESULT.md)在路由器上严格校验 lookup/invoke：
单对象耗时低于 C 约 5.7%/6.0%，64/128 全量 lookup 低约 32%–35%，四客户端全量 lookup 低约 59%–61%，
四客户端 invoke 低约 11%。这是当前 ELF 的新证据，不迁移 R109；恢复审计更正 caller 并未显式绑定 CPU0，不能将此组描述为双端分核的受控比较或单独归因于批量发送。
[R128 注册实测](reviews/R128_UBUSD_REGISTRATION_RESULT.md)严格校验 ADD/REMOVE 与完整签名：
1-method/8-byte name 的 R124 中位耗时约高 C 3.1%，16-method 约低 1.3%，但各有异常和反向窗口。恢复审计进一步确认该脚本只 export 归一化标志，自己的 workload 却直接启动 daemon；daemon/caller 无显式绑核，C/Rust 启动 argv0 不同，raw 无 mask/cmdline。保留全部数值与负结果，撤回 CPU1/统一 argv0 及已确认单方法退步的表述，须独立重新测量；[R129 连接规模内存](reviews/R129_UBUSD_MEMORY_RESULT.md)已补齐：64 个空闲连接 R124 的 RssAnon/VmData 增量为 28/28 KiB，C 为 48/52 KiB；
8/32 连接也低于 C，0/1 连接持平。R129 确实使用 `exec-cpu-as 1`，80 份前后 status 的 CPU mask 均为 CPU1，不受 R128 启动缺陷影响。它是驻留快照而非峰值或内核 socket 内存结论。
历史 R109 的查询/注册胜出、R113 的内存数值及现有正确性门都不能替代当前 ELF 的实机性能覆盖；
批次平均 wall 也不能推导 p99。停止判断限于最后实际覆盖的硬件、工作负载和正确性约束。
