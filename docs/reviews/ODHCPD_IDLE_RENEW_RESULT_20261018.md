**空闲 CPU 和 Renew 四个正式配对均改善，全部超过各自校准噪声。**静默窗
内 C 的 CPU 中位数为 **18.859 µs/s**，Rust 未记录到进程 CPU 时间增长；
Renew 中位数 **544.462→288.572 µs**，降低约 **47.0%**。按用户条件授权
继续 v0.3.0 构建、恢复验证、真实客户端试运行、刷机和发布。

这是一次定向修复后的唯一两项复测。没有再次测试 RS、Solicit/Request 性能、
接口更新 CPU、内存或首主动 RA，没有 PGO 或第二轮优化。旧[全项停止结果](ODHCPD_DEVICE_AB_RESULT_20261018.md)
保持原身份，不将用户接受的其它指标重新标成新 ELF 的性能实测。

## 原因和改动

- ubus worker 原先正常连接时每秒醒一次，背压时每 10 ms 重试。现在等待实际
  fd/命令/可用队列槽事件；仅断线重连保留实际重试期限，停止仍主动唤醒。
- 协议循环原先每秒进行完整租约协调，poll 又被限制在一秒。现在取租约、
  offer、Decline、有效源前缀、RA 和失败重试中的实际期限；无任务时无限等。
  非阻塞 self-pipe 保证 HUP/TERM/INT 和 SIGCHLD 能唤醒主循环，不靠周期兜底。
- Rust 原本已先回复再写文件；前一个 Request 的文件同步仍可能挡住后续
  Renew。现在从首次 dirty 起设 1 ms 的一次性导出期限，后续请求不延后它。
  到期以新时钟写完整状态，失败一秒重试，普通退出前刷新待写状态。内存绑定
  与新增 PD 路由 ACK 仍先于成功回复，hosts 原子更新后才执行 leasetrigger。

精确 C 的 ubus 是事件驱动，但 DHCPv6 **仍有每秒轻量到期扫描**；这里没有把
它描述成完全无周期唤醒。文件导出的 1 ms 表示可执行期限，已有同步 I/O 可能
使实际执行更晚，不是硬实时保证。C 在回复前同步写文件；Rust 既有的回复后
导出窗口在本次增加了有界合并，消费者读取完整快照，纯续期不重复触发脚本。

源码提交 `70e0b8aa`、`162d9ba8`。独立定向审查覆盖队列丢醒、重连/停止、
有限期限、内核重试、信号和文件顺序，未发现必修回归。69 项普通测试、严格
Clippy、真实私有 C ubus 检查通过；新 SDK 的 baseline 20＋extended 62＋
Fable 47，**129/129 一次通过**。

## 冻结规则与结果

遵照[事前计划](ODHCPD_IDLE_RENEW_PLAN_20261018.md)，校准 `ABBAAB`、正式
`ABBABAAB`；每侧每实例安静 2 秒，再测零租约的 3 秒空闲 CPU，然后执行
三 NA 客户端轮换的 16 组 Solicit/Request/Renew。前两类仅建立相同状态，
保留原包但不入性能门；Renew 取全部 16 个延迟的中位数。CPU 包含工作线程。

每项 `N=max(C 校准极差, Rust 校准极差, 2×实际量化)`，每对独立比较
Rust−C，任一对大于 N 即停止。以下中位数只展示，未替代逐对判定。
