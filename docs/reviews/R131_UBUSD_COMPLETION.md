# R131 补测完成：收益成立，整体验收未通过

本轮把已冻结的 R131 六类补测全部执行完毕：72 个三方比较窗口、两个正确性窗口、
三个持续事件内存诊断窗口，共 **77 个物理 AX3000T 临时窗口**。
没有更换 R131 release ELF，也没有开始 R132 或拼接新的运行时版本。

结论是：**R131 确实改善连续发往同一连接的事件，但注册尾延迟触发了退步门。
本轮不将它提升为通用 Rust 基线，R124 继续作保守基线，R131 的实现和证据完整保留。**
这不是“性能已经到头”，也不是“所有测试通过”；正确性通过和性能接受是两项不同结论。

## 实际收益与代价

以下为同一轮六个配对变化的中位数，负数更快。不同 caller 的结果各自计算，没有拼接历史窗口。

| 场景、指标 | R131 相对 R124 | R131 相对 C |
| --- | ---: | ---: |
| 八监听对象、同连接：平均耗时 | −16.62% | −12.94% |
| 同上：p95 / p99 | −20.04% / −17.25% | −9.20% / −11.49% |
| 两连接分组监听：平均耗时 | −8.74% | −10.27% |
| 交错监听：平均耗时 | +0.76% | −2.72% |
| monitor：平均耗时 | −1.84% | **+6.49%** |
| 单方法注册周期：平均耗时 | +2.48% | **+4.74%** |
| 单方法注册周期：p95 | **+15.25%** | **+69.93%** |
| 16 方法注册周期：p95 | **+5.0085%** | **+46.75%** |
| exact lookup：平均耗时 | +0.21% | −6.12% |
| all / prefix lookup：平均耗时 | +1.09% / +1.08% | −32.12% / −32.76% |
| invoke：平均耗时 | −0.07% | −6.80% |

同连接八监听对象的 daemon CPU 相对 R124/C 分别低 20.29%/18.42%。
monitor 的 daemon CPU 仍比 C 高 16.43%，平均耗时六对全高于 C。
无匹配事件的 p99 相对 C 中位高 5.43%，六对有正有负；这些反向数据没有删除。

注册 p95 相对 R124 的六对均上升。16 方法的中位数仅略超 5%，不夸大精确幅度，
但单方法中位 +15.25% 是另一条独立的失败项。异常窗口 13 有额外调度干扰迹象，
其余五对仍同向，不能以此撤销整轮结果。没有事后删除窗口、改门槛或追加重测冲淡失败。
注册也不是 R131 才第一次落后 C：本轮 R124 单方法 mean/p95 已高 C 1.42%/50.93%，
16 方法 mean/p95 高 C 2.56%/43.95%。保留 R124 不等于宣称性能目标已经达成。

1 KiB × 八监听对象事件中，R131 比 R124 多保留 **12 KiB 匿名驻留内存、28 KiB 虚拟数据映射**。
VmData 触发原先 +24 KiB 调查门，门仍记为触发。进一步在相同 daemon 上依次完成
1、1000、10000 个事件，1/5 秒快照和 maps 均未继续增长：R131 为 60/84 KiB，
R124 为 48/56 KiB。这里支持固定容量保留的解释，不证明任意负载或长时间无泄漏。
缓冲属于整个 Server，不是每连接一份；16 KiB 是 batch 长度上限，不是 Vec capacity 或 allocator 映射上限。
另以相同 Rust bundled musl 做的[容量核账](R131_UBUSD_BATCH_CAPACITY_ACCOUNTING.md)
复现了 9216 B 缓冲容量对应 28 KiB allocator 映射；这支持解释，但不是对 release 每笔分配的直接追踪。

按性能九成、开销一成的偏好，这十几 KiB 驻留并非拒绝 R131 的主要原因。
主要问题是新证实的注册尾延迟回退，以及仍未胜 C 的注册/monitor 场景。
没有各业务实际占比，不能把不同场景简单平均，造出一个“九比一总分”覆盖失败项。

## 当前版本和下一步边界

R131 release 源提交为 `4e45d2ecc41d8548916c2f92f30c7ac4d2bb65dc`，
ELF SHA256 为 `c5bcf6e7c6f2ed565140e183ba3aa97c1ef60274bbde8398771ac13680da839a`。
测试追加在 `codex/r131-event-batch` 分支，运行时代码没有为补测而更换。
R124 ELF 为 `42435a31e2917186fb353e2c70143f4b3f6d82ec3dd53265bf6d826897b69926`。
主工作树仍含历史 R109 源码，不能把文档基线选择理解成已合入或可部署。

继续研究已有具体对象：先对精确 R124/R131 注册路径做按符号 profile 和同步计数，
查清没有监听者时对象事件调用、编码、分配和调度分别占多少；没有归因证据前不再试分支或内联变体。
本轮仅确认 `dispatch_event` 会被 ADD/REMOVE 调用，尚未证明其中哪一处造成实机退步。
monitor 比 C 慢也是可独立研究的实测缺口。它们均不是已证明不可越过的 Rust/C 语言差异，
也不构成推倒重写的证据。

本轮关闭的是已冻结补测清单，并非任意输入的完全验收。仍不能声称已测：

- 大载荷 fanout 的延迟/CPU：1/8/32 KiB 已测功能与驻留，正常交付性能矩阵仍为小载荷。
  完整帧大于 8 KiB 而不超过 16 KiB 时，batch 只能容下一帧，可能复制却不能合并 syscall；若继续接受候选须覆盖。
- 饱和吞吐、更多活跃连接/并发生产者、长时间运行、PSS/内核 socket/内存峰值。
- 九个最终 Rust 组件共同工作，以及当前精确 ELF 与 R89 的新一轮比较。

共享路径已经未通过，因此本轮没有为该候选追加新的性能矩阵。
所有测试结束后再次只读核验：生产仍是精确 C，PID 869、boot 未变，
本轮 `/tmp/r95-check-*` 目录及其所属进程均不存在，网络健康检查通过；没有部署 R131。
