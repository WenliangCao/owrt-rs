# R61：推进方向审查与纠正指导

日期：2026-09-07。审查基线：`482f8c7`，相对上次 `758df09` 的新增工作。另阅读了工作区中 r49/r57 移除过期 wireless 排除项的两处未提交修改，未改动它们。

本轮是方向审查及高风险路径抽查，不是对新增约 2.4 万行逐行签字。阅读了 R35 调查、决策 0018、核心控制面计划、ubusd/netifd 报告及关键实现和 harness；未重新核验远端原始产物、未操作设备。只新增本文，所有实现修改交给 Opus。

## 总体判断

没有看到需要推倒重来的架构方向错误。继续保留内核、无线认证和 DHCP helper，用精确 rootfs、原版 daemon、namespace 与 VM 作参考，这条路值得继续。ubusd 的包内二进制复测、overlay 撤销实验，以及主动订正测试误判，都有实际价值。

需要纠正的是下一步优先级：从“新增字段/方法与原版一致”转向“本机必要的端到端路径和失败恢复完成”。netifd 目前仍应标为开发中；已有离线用例通过，不等于整个组件离线验收通过。先完成下列缺口，再安排接管或推进下一项组件上线。离线开发无需因为尚无设备窗口而停住。

## 1. P1：无线输出管道会卡住整个无线队列

位置：`components/netifd/src/main.rs:1764` 的 `poll_child_output`、`:3397` 的 `wireless_reap`；`components/netifd/src/process.rs` 的 `Slot::reap`。

协议脚本和 hotplug 在运行中读输出，但 `wslot` 没接进这条路径。无线只调用 `reap()`，而它等子进程退出才 `drain_output()`。handler 输出超过管道容量时，子进程等读取，父进程等退出；`wcur` 一直占用，后续 radio 的 setup/teardown 也无法执行。短小的 r60 桩看不见这个问题。

本地隔离探针直接引用当前 `process.rs`，让子进程写 1 MiB 后退出，按无线当前方式仅轮询 `reap`：1 秒后仍无法退出；探针随后显式杀掉并回收子进程。这是进程层复现，不冒充完整 Linux daemon 差分。

纠正：把无线 stdout/stderr 纳入运行中的输出消费；每轮读取设合理预算，未换行输出也要有内存边界，避免修成另一种事件循环饥饿。不要只增大管道。为 handler 的挂起和启动失败补明确的状态收尾，超时行为先对照精确参考实现。

验收：两 radio；第一个 handler 分别向 stdout/stderr 写超过管道容量的数据，再通知 UP；第二个仍能启动。包含无换行输出，验证 ubus 仍响应、资源有界、down 能收尾。运行在隔离 Linux rootfs。

## 2. P1：本机需要的 DHCPv6 PD 目前不是“只差测试”，而是还没实现入口

位置：`components/netifd/src/main.rs:825` 的 `build_prefixes`、`:1433` 起的 `apply_proto_link`、`:1903` 的 `apply_prefix_assignments`。

当前全局前缀列表只从 ULA 构造，proto 更新没有接收 `ip6prefix` 并插入委派前缀的路径。R45 已明确本机 LAN 的 GUA 来自 WAN6 委派；因此 DHCPv6 获取地址的用例通过，不能证明 LAN IPv6 可用。报告“PD 没测成”应同时明确“动态 PD 路径尚未实现”。

纠正：把 PD 提到下一轮核心工作，不要等一个真实上游环境才开始。先从精确脚本/源码取合法 `notify_proto` 载荷，在 C/Rust 两端通过原有协议入口注入脱敏前缀，补上来源接口、class、更新/撤销和生命周期，再接回现有分配器。不要直接给内部列表塞测试数据绕过入口。

验收至少覆盖：首次 /64 委派给请求 /60 的 LAN（以 C 的实际退让行为为准）、续租、前缀替换、preferred/valid 到期、WAN6 down、与 ULA 共存。比较 LAN 地址/路由、`ipv6-prefix`/`assigned`、事件，以及 odhcpd 消费后的结果；之后再用可控 DHCPv6 服务端覆盖真实 IA_PD 交换。无硬件依赖。

## 3. P1：无线已能报 up，但必要副作用和配置更新尚未闭环

位置：`main.rs:3474–3515`、`:3297`、`:3531`；`wireless.rs:838` 起的 `handler_json`。

当前 UP 主要改状态，SET_DATA 只留 ifname，PROCESS_ADD 直接 OK；handler JSON 的 data 永远是 `{}`。`wireless_load` 只在 main 启动时调用，`network.reload` 不更新无线配置，reconf 又用旧 wconfig 发 setup。因此，当前 r60 证明的是一部分调用协议和状态转换。

r60 的网络配置只有 loopback，没有 LAN bridge；`stub-ap0` 只是上报的字符串，没有真正的网卡。这套用例不能发现无线口未加入 LAN 的缺口，也不能验证注册进程的死亡处理和 teardown 所需数据。

纠正：保留现有桩，扩展它的副作用，不另造框架。按精确 wireless ucode 合同保存和回传 handler data，把 vif 与配置的 network/device 生命周期接起来，实现 PROCESS_ADD 在本机可达路径上的管理语义。补配置差分更新，避免一收到 reload 就无条件重启全部 radio。

验收：在私有 netns 建真实 br-lan 和模拟 AP 的 veth，setup 通知后检查桥成员与跨桥通信，down 后检查清理；注册受控进程后使其退出，比较恢复和重试；修改 SSID/network、删除 radio、禁用/启用以及无变更 reload，比较载荷、实际动作和状态。另让 handler 保存一个设备级 token，确认 teardown 按参考行为拿到它。VLAN/station 字段已做的工作可以保留，下一步优先完成这条本机实际使用路径。

## 4. P1：配置有错误时仍应用部分结果，可能拆掉原来能用的接口

位置：`main.rs:260` 的 `reload` 与 `apply_config_change`；`config.rs` 的 `Config.errors`。

解析器将多类无效/不支持配置记进 errors，却仍返回 Config；reload 立即替换 self.cfg，只打印 errors，之后照常改设备和接口。例如已工作的 static LAN 改成无效地址，解析结果可能变成无地址接口，随后 reload 会拆旧配置并应用这个结果。“有日志”不满足计划要求的“不支持时明确拒绝，不能先拆工作网络”。

纠正：先解析、校验到临时配置，发现本实现无法安全应用的错误就拒绝本次 reload，保留运行态并向调用者报告失败；启动时同样在任何网络副作用前处理致命配置错误。这只是配置预校验，不要求构建通用内核事务回滚框架。若有意偏离原版的部分应用行为，明确记录这一安全取舍。

验收：从可通信 LAN 开始，分别提交错误地址/掩码、不支持的设备类型和段落；确认返回失败且地址、路由、桥成员、helper 和事件没有发生拆网变化，再恢复合法配置验证能应用。

## 5. P2：suite 有明确的假通过路径，也漏掉最新用例

位置：`tools/netifd_suite.sh:14,25–27,40`。

本轮实际运行：给 rootfs、candidate、examples 全部传不存在的路径。输出 13 个 SKIP，最后仍是 `SUITE: all identical`，退出码 0。通配符也只覆盖 r47–r59，r60 不会执行；r46 同样不在列表。

纠正：使用简短的显式用例清单，声明每项所需探针及参数；全量验收缺必需文件立即失败。允许显式选择子集，但汇总必须写清通过/失败/跳过/未执行数量，不能把零执行或部分执行称为全通过。包含 r60 的 up/fail × CMDS yes/no 四种组合；若 r46 属于独立前置检查，明确标出。

r60 还应拒绝无法解析的 status、空 signature，以及双方相同的错误输出；不要把 JSON 解析失败转换成 `__raw__` 后相等就通过。每次运行清空本次输出，命令追加文件不能沿用上次记录。断言预期状态和调用次数，不能只有两边相等。

工作区 r49/r57 去掉过期 wireless 排除是正确方向，但移除后要实跑包含其副作用的回归，不能只凭对象现在注册了就改报告为通过。

## 6. P2：可重复构建与 DAD 的结论需保留证据边界

canonical CI 是合理的阶段策略，不必为这个个人项目修改 Cargo 上游。需要改的是表述：这解决了“规定环境下的发布产物重建”，没有解决异构宿主字节一致。

决策 0018/调查报告用指令条数、助记符直方图和 38 个差分用例证明“行为等价、无运行影响”，结论过强。同样的助记符可有不同操作数和控制流。应写“已定位的差异与 metadata/布局传播一致；已执行用例未观察到行为差异”，保留实测与推断的区别。

workflow 仍是 `ubuntu-latest`，并有浮动 action 引用和在线 apt；不能说整个 runner 环境已被冻结。最小改进是固定 runner OS 版本、记录实际 runner image 与构建工具身份和输入校验值；重要 action 固定 revision。后续工具/runner 升级重新做同 revision clean 对照。无需为了措辞立即引入大型构建平台；若需要严格长期重放，再选可归档的固定环境。

r56 关闭 DAD 可以保留为稳定的协议功能对照，但需标为“DAD 关闭场景”。两边都会抢在 LLA 可用前启动，只能排除已观测的单边时序差异，不能证明真实设备启动、接口重建或链路恢复时没有这个窗口。保留一组 DAD 开启的隔离恢复测试，以最终可用性及有界恢复验证；若参考也失败，如实记录基线问题，不用删状态位或无限等待来消红。
