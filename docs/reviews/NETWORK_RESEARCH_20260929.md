# 九组件之后：网络研究结论与执行顺序

2026-09-29。**下一阶段优先研究现有转发路径如何分工、硬件实际处理了哪些流量，以及满载时请求在哪里排队。DNS 做成本分解，DHCPv6 做协同正确性验证；当前没有值得立即启动的第十个完整 Rust 重写项目。**

本轮完成四份专题报告、精确源码核对、既有性能数据复算和生产只读观察。没有执行新的生产负载、修改配置、安装软件包或刷新固件。研究前后全部 `/etc/config` 文件哈希一致，UCI 没有待提交项，九个 Rust 程序哈希一致；软件卸载 1、硬件卸载 0、WED 关闭。

运行观察覆盖 UTC 19:18:19–19:29:06，各命令不是同一瞬间的原子快照。[脱敏结果与 93 份原始文件哈希](../../reports/ax3000t-stock-openwrt-25.12.5/NETWORK_RESEARCH_20260929.json)保留本轮证据身份；原始地址、配置、租约和源码缓存留在 ignored private 中。

## 1. 投入优先级

| 方向 | 建议优先级 | 能改善什么 | 实际做法 | 暂不做 |
|---|---|---|---|---|
| 网络转发与 CPU 分工 | 高 | 吞吐、相同流量的 CPU 成本、忙时响应 | 查每核/NAPI/RPS，比较现成 packet steering 设置，补受控有线转发基线 | 重写 Linux 网络栈或先固定所有中断绑核 |
| PPE / WED 硬件加速 | 高，但须验证命中 | 减少实际包处理成本，释放 CPU | 分离有线 PPE 和无线 WED；证明指定流的双向 BIND/字节增量 | 把开关打开、规则接受或 HW_OFFLOAD 标记当成功 |
| 排队与限速 | 高，是否部署取决于拥塞位置 | 多人下载时小请求、语音等能否及时获得响应 | 先区分无线/CPU/上游；再用现成 SQM/CAKE 比较吞吐—延迟代价 | 直接抄固定限速数值，或把 SQM 翻译成 Rust |
| DNS | 中 | 打开网站前的解析等待、上游故障时的尾延迟 | 受控上游分解缓存/转发/故障，检查重载与订阅回调 | 没证据就增加缓存、更换完整解析器 |
| DHCPv6 / RA / PD | 对稳定性高，对提速低 | 前缀续租、换号、路由/DNS 更新的一致性 | 补现有 Rust netifd 与 C 协议服务的离线集成测试 | 为持续下载吞吐完整重写 odhcpd/odhcp6c |

“优先研究”不等于“必须把所有候选开启”。最大吞吐、满载低延迟、内存和公平性可能存在取舍，目标是找出适合这台设备与宿舍网络的组合。

## 2. 相比上一轮，多查清了什么

### 上轮只开 HFO，没有覆盖完整的无线硬件路径

精确 mt76 驱动在 WED inactive 时不提供 WDMA 转发路径，PPE 因而不能获得该 Wi-Fi 出口。内核设置连接级 `HW_OFFLOAD` 只要求至少一个方向的驱动回调成功；MediaTek 后续还要将跟踪条目实际绑定到硬件。OpenWrt 本版本也允许一个 flowtable 混合软/硬能力的设备。

所以“规则正确、连接表有硬件标记、CPU 没下降”可以同时成立。上一轮恢复原设置是正确的；剩下值得回答的是**受控有线 PPE 是否有效，以及 WED + HFO 是否能为无线流量带来净收益**。这两项还没有测。[固定 mt76 路径](https://github.com/openwrt/mt76/blob/39c960c3ada558b4c2e7915772483d3731573d09/mt7915/main.c#L1764)、[Linux 回调与标记](https://github.com/gregkh/linux/blob/v6.12.94/net/netfilter/nf_flow_table_offload.c#L955)。

### 整机平均 CPU 掩盖了核间差异

既有 WAN 软件 A₁ 中，CPU0/CPU1 每核忙占比的中位数为 **43.38% / 86.33%**；恢复软件 A₂ 为 **51.71% / 83.82%**。CPU1 更忙，但没有证据证明它始终满载。

当前 Ethernet NAPI 在 CPU0，无线 NAPI/发送线程在 CPU1，并有反向 RPS 分配。这不是“完全没开多核”，也不是会根据即时负载自动平衡。现成 `packet_steering=1→2→1` 比较成本低，值得排在驱动初始化实验之前；threaded NAPI 的 CPU 还要按线程统计，不能只看 softirq。

### 当前已有排队管理，SQM 应针对实际瓶颈

系统默认 qdisc 为 FQ-CoDel，两个 PHY 的 AQL 都开启。默认值不代表各接口实际 qdisc 已全部验证，但足以说明不能把“开启 AQL/FQ-CoDel”当成本轮新发现。

此前 LAN 上传就使本机 TCP 建连 p95 从 **13.65 ms 升到 50.90 ms**，这段流量不经过 WAN。应先查无线与主机处理，WAN 限速不能直接解释或修复这段 LAN 内等待。公网 SQM 的价值，要通过有线客户端的本机探针与固定公网探针分开确认。

精确软件包体系已有 `cake_mq`，但实际 `wan` 仅一个 TX 队列，底层 `eth0` 的 16 队列不能直接拿来当 WAN 多核整形能力。下行多队列 IFB 有研究入口；整形包当前未安装，不能承诺千兆 CAKE。

### DNS 的现成参数已不低，统计也有口径陷阱

当前 dnsmasq 缓存是 **1000**，采样时未过期淘汰为 **0**。没有支持继续加大缓存的证据，也尚未测出 DNS CPU 或解析延迟瓶颈。

两个值得单独核对的小边界是：IPv6 主机名变化经 odhcpd 触发 dnsmasq SIGHUP，会清动态缓存；DNS 结果的 ubus 订阅回调，在确有订阅者时可能等待最多 100 ms。两条源码路径都存在，**本轮没有证明它们正在造成现网性能问题**。普通续租不会无条件触发 hosts 回调，注册了 DNS 对象也不代表已有订阅者。

缓存插入/淘汰计数在 reload 时重置，forwarded/local_answered 不同时重置；后者还包含本地 hosts 等回答。因此当前快照不能计算纯缓存命中率，更不能用不同累计窗口的数字宣布缓存失效。

### DHCPv6 的价值在生命周期，而非逐包速度

当前上游委派一个公网 `/64`，LAN 请求 `/60` 仍只能获得实际可用的 `/64`；ULA `/60` 是另外的本地空间。当前 GUA 在 ULA 前，原先修正的地址选择顺序仍成立。

odhcp6c 获取上游参数，netifd-rs 编排地址/路由，odhcpd 向 LAN 提供 RA/DHCPv6，dnsmasq 读取相应名字。这条链最值得补的是续租期限、前缀撤回、DNS 更新和 ubus 重新订阅的离线测试。两个 C 服务并不搬运日常下载的每个数据包，完整替换的性能收益尚未建立。

## 3. 下一轮分四步，不同时堆开关

| 步骤 | 具体交付 | 进入下一步的依据 | 对用户的操作要求 |
|---|---|---|---|
| 1. 把现有测试工具补完整 | 原/回复五元组与 PPE BIND 差值、每核及 NAPI 线程成本、无线队列增量、两种接入视角的延迟；DNS/IPv6 隔离测试设计 | 原始数据能解释命中和等待位置，观察不会改变 DNS 订阅路径 | 准备阶段无操作 |
| 2. 先做成本较低的 CPU 分工对照 | 固定原无线↔有线路径，steering `1→2→1`，保留全部窗口 | 等交付吞吐的 CPU 成本或稳定吞吐改善，同时延迟不退步 | 届时只需启动一次接收端；每次只给一个操作 |
| 3. 由瓶颈选择分支 | CPU 分支：受控有线 PPE，再 WED/HFO 四组合；排队分支：有线公网基线，再单向/双向 SQM | 某条分支有明确收益才扩大；WED 与 SQM 分开验证 | 先完成具体拓扑与产物准备，再安排需要的接线或配置实验 |
| 4. 固化有收益的组合 | 记录基底/配置/资源代价、验证 IPv4/IPv6 与策略、纳入下一镜像；DNS/IPv6 问题若有复现则做小修 | 所有实际使用路径通过，而不是只看最高测速 | 本轮研究没有执行这一步 |

等速 CPU 对照由**测试端点**控制发送节奏，不在路由器加 CAKE 去测 HFO，避免改变被比较的路径。最大吞吐另测。每项先冻结方法与收益门，专题报告已给出建议值；这些门槛是下一轮的选择标准，不是新的测量结果。

现有 Windows LAN 端点可以复用，但要隔离 PPE 的有线转发收益，还需要独立、受控的 WAN 侧端点。同桥测速和随机公网测速都不能替代这一条件。当前无需重新开 Windows，也不把这项未完成的测试包装成已知性能上限。

DNS 和 IPv6 可以先在隔离 Linux 环境推进，不占用家里的生产网络。DNS 优先把上游等待与本机处理分开；IPv6 优先检查匹配 C 服务与 Rust 编排的协议契约。跨架构模拟只作功能证据，不拿模拟器耗时预测路由器性能。
