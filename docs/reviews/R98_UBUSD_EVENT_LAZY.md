# R98：事件按需编码第一版暂缓，继续研究投递成本

本轮没有接受运行时改动。无接收者时省掉事件编码有明确收益，但有接收者的成本上升，
独立查询复查也触发了事先冻结的暂缓门槛。接受基线仍是 `5a19517`（ELF `527f8683…`）。
这说明本次实现尚不合格，不能推断 Rust/C 存在不可逾越的语言差异。

## 来源、改动与验证

匹配镜像的 ubus 源码 `24864e7840b3a02a9ef76284a373f6b2f00b8a9b` 中，
`ubusd_event.c` 在找到排除发送者、去重后的实际接收对象时才调用 `fill_cb`；
[上游源码导航](https://lxr.openwrt.org/source/ubus/ubusd_event.c)用于交叉阅读，具体合同以匹配版本为准。
原 Rust 在匹配前已构造事件。本候选用一次性构造回调推迟对象、用户和 ACL 事件编码，
保留事件轮次、每客户端序号、监视器和队列所有权；仍有目标 ID 快照和逐接收者复制。

完整补丁：[r98-event-lazy.patch](r98-event-lazy.patch)，SHA `76545973…`；
候选 ELF `1fc485de5261b3090c7bcabe265950fc4071ccf4b8d941cc89f0a232be4a2db1`，
507,880 字节，与基线文件大小相同。构建源路径、SDK、工具链、cwd、release 参数固定。

构建机 31 条单测、clippy 和六组功能/ACL/fuzz/限额/恢复检查通过。
物理 AX3000T 通过 31 条单测，C/基线/候选七组协议差分逐字节一致；
新增对象事件覆盖空订阅、多对象去重、序号回绕、删除和完整有效载荷。
排队单测覆盖 32 KiB 事件、多个接收对象及监视器。计量客户端另有三条实机单测。
这不等于所有可能输入无缺陷；完整身份与验证记录见
[validation](r98-event-lazy-validation.json)。

## 实机结果

全部数据来自物理路由器。每种矩阵四个随机配对 block、四个实现，每 lane 5,000 次；
独立查询复查另用八个随机三联 block，每 lane 20,000 次。
下面为配对变化百分比的中位数，正值表示成本上升；不是混池请求统计或正式优越性结论。
查询、注册、事件接收使用各自冻结且同组完全相同的客户端，不跨客户端混池。

| 注册场景：方法数/名称字节 | 平均延迟 vs 基线 | p99 vs 基线 | 自身 CPU vs 基线 | 自身 CPU vs C |
|---|---:|---:|---:|---:|
| 1/8 | −5.09% | −5.60% | −14.38% | +3.21% |
| 16/8 | −8.08% | −15.06% | −16.16% | +12.14% |
| 64/8 | −4.01% | −0.74% | −7.92% | −11.40% |
| 1/128 | −5.60% | −3.81% | −15.30% | +4.11% |

四场景自身 CPU 均低于 R89，但三个仍高于 C。64 方法场景 p95 +0.64%、客户端 CPU +0.52%，
不能以平均改善掩盖反向指标。完整注册指标见 [结果](r98-event-registration-results.json)。

| 对象事件接收场景 | 平均延迟 vs 基线 | p95 | p99 | 自身 CPU | 自身 CPU vs C |
|---|---:|---:|---:|---:|---:|
| 1 个匹配对象 | +3.03% | +13.78% | +3.60% | +1.95% | +16.16% |
| 8 个匹配对象 | +3.53% | +6.60% | +4.49% | +4.08% | +18.44% |
| 1 个不匹配对象 | −4.17% | +3.69% | −0.23% | −14.16% | +6.11% |

每周期包括注册、完整接收校验、删除、完整接收校验，结束时用请求屏障排除多余事件。
匹配场景客户端 CPU 分别 +1.41%、+1.27%，吞吐 −2.96%、−3.42%；
不匹配场景客户端 CPU +0.47%，吞吐 +4.34%。三个场景自身 CPU 仍高于 C。
详见 [事件接收结果](r98-event-fanout-results.json)。

原十项查询矩阵中，单路精确查询 CPU +1.24%、前缀查询 +1.81%，并发精确查询平均延迟 +4.49%；
也有批量查询 CPU 改善等相反方向。全部 lane/指标/基线保留在
[查询结果](r98-event-matrix-results.json)，不能单挑注册收益接受候选。

## 独立复查与决定

复查加入 `control`：与 `before` 是字节完全相同的基线 ELF。
冻结门槛是 CPU 中位上升超过 1% 或 p99 超过 5%，且相对两个基线都至少 6/8 配对上升；
这是保守工程筛查门，不是统计显著性检验。

| 场景自身 CPU | vs before | 正向配对 | vs 相同 ELF control | 正向配对 |
|---|---:|---:|---:|---:|
| 精确查询 | +1.196% | 7/8 | +1.202% | 8/8 |
| 64 对象前缀查询 | +3.052% | 8/8 | +2.962% | 6/8 |

两者均触发暂缓门。相同基线之间上述 CPU 中位变化分别 +0.062%、−0.954%。
并发精确查询和 invoke 的双基线门未同时触发，不将其记为等价或无退步。
详见 [冻结计划](r98-query-recheck-plan.json)、[原始派生结果](r98-query-recheck-results.json)、
[双基线检查](r98-query-controls.json)。尚未定位非事件查询变化的微架构/代码布局原因，不能猜成语言成本。

## 内存、清理和未完成项

实际注册表七种布局的 ABBA 请求堆诊断精确复现：保留请求字节完全相同；
构造峰值只有部分场景减少 72 或 152 字节，其余不变。
查询矩阵候选 RSS/匿名页中位各高 4 KiB，匿名页也未胜 C/R89。
[堆结果](r98-event-memory-results.json)记录的是成功分配请求，不包含分配器取整、内核缓冲或完整进程峰值，
proc 页计数也不是 PSS；这些内存目标仍开放。

本实验共 79 个隔离实机窗口：72 个性能、4 个堆、3 个功能窗口，
计时查询/invoke 272 万次、注册 32 万周期、事件注册 24 万周期（投递 144 万条计时事件）。
每窗口验证身份、生产 C 和清理；末次全局复查配置匹配恢复备份、boot 未变，
测试目录、进程引用、宿主挂载均为零。没有部署候选。原始文件保留在 Git 外 `private/r98/event-lazy/`。

下一候选保持按需编码，直接借用匹配表遍历，使用已有 `send_borrowed` 在真正排队时才拥有数据，
分别验证目标快照和复制能否省掉。其功能预筛查已通过，性能尚未测量，不能预判接受。
原版 libubus 性能调用者、完整内存/峰值、充分独立确认和九组件组合验收仍未完成；持续目标保持进行中。
