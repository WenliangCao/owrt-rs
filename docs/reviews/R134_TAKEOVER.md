# R134：接手九组件收尾

2026-09-23 接手 Codex 会话 `fea9cc00`。生产路由器始终为精确 C（本日核对 boot
`75a17130…`，`/sbin/ubusd` md5 `ba762b66…`）。

## 1. 前一会话做了什么

R95–R133 共 39 轮，全部在 ubusd 上；其余八个组件自 R94（09-17）后只合入了
R95 审计的四个缺陷修复（reload-config/uci 打包、reload-config 锁等待、UCI 短读）。

- R113 发现 R94 读前缓冲在「一个 sendmsg 里装多帧并附 FD」时与 C 的 FD 归属不同，
  于是把接收改回 C 的逐帧 `recvmsg(前缀)` + `read(正文)` + EAGAIN 探测。
- 之后 R114–R131 在这个 C 形状上做 1–3% 的消融，逐步追回：R131 的 lookup/invoke
  和事件优于 C，但注册 1/16 方法 p95 高 C 70%/47%、daemon CPU 高 6%/11%，monitor 高 6.5%。
- R132 在 Oracle 做了精确 PC 采样与同步计数（见下），R133 冻结了一个
  「无监听者时跳过对象事件查表」的候选，尚未实现即中断。

## 2. R132/R133 收尾

[R132 profile 审计](../../private/r132-registration-attribution/profile-audit-03/results.json)
（12 窗、499 Hz、全部完整性检查通过）的结论：

| 注册周期 | 总样本 C / R124 / R131 | 用户态样本 C / R124 / R131 |
| --- | ---: | ---: |
| 1 方法（各两窗合计） | 5542 / 5443 / 5407 | 837 / 633 / 634 |
| 16 方法 | 5948 / 5921 / — | 1174 / 1062 / — |

- daemon CPU 约 85% 在内核（系统调用与调度）；Rust 用户态已经比 C 少 10–24%。
  实机注册差距不在用户态代码，而在每个请求的系统调用形状：
  C 形状下每个请求固定 `recvmsg` + `read` + EAGAIN `recvmsg`，再加回复 `sendmsg`。
- R133 针对的对象事件族在 R124 中只占全部样本 0.15%（8/5443），
  即使完全消除也达不到它自己冻结的「用户指令降 ≥3%」筛查门。
  **R133 按其冻结规则判定不值得运行，关闭，不实现。**
- R132 的 perf 仪器与数据保留在 `private/r132-registration-attribution/`，不再扩展。

## 3. 为什么「照着 C 翻译」不会自动更快

1. 逻辑可以照抄，照抄的结果就是和 C 做同样多的工作，性能落在 C 附近（±5%）。
   要「全胜」只能让 Rust **做得比 C 少**：更少的系统调用、分配、复制和唤醒。
2. C 用侵入式链表/AVL（节点嵌在结构里，零额外分配）、复用的静态缓冲、直接指向
   接收报文的指针；惯用 Rust 的 Vec/String/HashMap/Box/Rc 每请求多出分配和复制。
   在 1.3 GHz Cortex-A53 上一次 malloc/free 约 0.1–0.2 µs，一个 30 µs 请求多 20 次
   分配就是 5–15%。这是 R94 之前各组件落后 C 的主因，R94 已逐项去掉。
3. 这些守护进程的 CPU 大半在内核。ubusd 的注册周期 85% 在内核，所以真正的收益
   来自 IO 形状（批量读、批量写、少一次唤醒），这不是语言问题，是算法问题。
   前一会话为了逐字复现一个无人使用的 FD 边界放弃了 IO 形状，只剩用户态可调，
   所以在 1–3% 上反复打转。

## 4. 本轮做法

**ubusd（R134）**：以 R131 源码为基础（保留借用派发、系统对象借用、SEND 凭据借用、
事件 scratch、同 owner 事件批量），只把共享栈缓冲上的接收改成读前缓冲：

- 一次 `recvmsg` 读入可用字节，切出完整帧借用派发；只有跨读取的半帧才分配。
  共享缓冲属于事件循环，不按连接常驻，保住 R124/R131 的连接内存优势。
- 读取小于可用空间且未带 FD 即视为排空，不再探测 EAGAIN（epoll 为水平触发）。
- 成功 ADD_OBJECT 的 DATA+STATUS 合并为一次发送（R130 机制已验证帧字节不变）。
- 对象/类型 ID 由启动时随机密钥的 SipHash-1-3 计数器生成，替代每个 ID 一次 `getrandom`；
  碰撞与保留 ID 的重试规则不变。

**FD 契约**：FD 属于携带它的那次 `recvmsg` 最后一个字节所在的帧；同一帧再到的 FD 关闭。
内核在交付 FD 的 skb 之后结束该次读取，而 libubus（含短写时重复附 FD）、C ubusd
和 owrt-ubus 都是一帧一个 sendmsg、FD 附在帧首，所以对它们与 C 逐字一致。
只有把多帧塞进同一个 sendmsg 并附 FD 的手工发送方会不同；镜像里没有这样的客户端，
而且所有候选帧都来自同一发送方，不涉及跨客户端或权限。R113 的 wireprobe 三个手工用例
改为按此契约断言，并在文档中列为已知差异。

机制预测：完整小帧减少正文 `read`、排空时的 `recvmsg` 探测；ADD 再少一次 `sendmsg`
和两次 `getrandom`（对象与类型 ID）。原先写的「每周期 C 14 次 → R134 7 次」
未区分系统调用类别，也没有可靠的 EAGAIN 次数依据，不能作为已证实结果。
Oracle 精确 ELF 的跟踪检查在 100 个计量周期中，四类调用
`recvmsg/read/sendmsg/getrandom` 合计为 C 10.03–10.04 次/周期、R131 10.01–10.02，
R134 5.00；R134 分别为 2/0/3/0。此处不含 epoll 等其他调用，跟踪还会改变调度，
因此只验证减少工作的机制，不推断实机加速比例。

**其余八个组件**：先用当前源码在路由器上与 C 重测（R95 修复改变了 uci 共享库），
只针对实测输掉的负载做算法改动，不追范围重叠内的尾延迟。

## 5. 验收规则

路由器、同一夹具、C 与候选 ABBA 交错四个周期（每侧 8 窗）。每条负载分别看
daemon CPU/op、mean、p50、p95、p99：

- **胜**：候选中位数更低，且 8 对中至少 7 对更低（符号检验单侧 p≈0.035）。
- **负**：候选中位数更高，且至少 7 对更高。其余为**平**。
- 常驻内存看 RssAnon 与 VmRSS；短命命令看整个调用树的峰值。
- 正确性门（单测、协议/FD 差分、各组件历史门）必须先过。

不再使用预冻结 A/A ±0.5% 校准带或 Bonferroni 区间作为继续的前提；
它们让 1–3% 的真实改动无法判定，也不能替代减少工作量的改动。
