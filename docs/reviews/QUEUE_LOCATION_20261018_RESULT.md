# 排队定位：Wi-Fi 延迟与 HFO 路径有关，公网超时另未定位

2026-10-18。**关闭 HFO 后，Wi-Fi 端已完成连接的尾延迟降低，但没有消除公网
超时；有线探针到路由器始终约 1 ms，公网已完成连接约 25 ms。数据支持 Wi-Fi
路径贡献了通常观察到的几十毫秒延迟，不能把全部现象归因于 WED 绕过 AQM，
也不足以认定 WAN CAKE 是直接解法。最终保持 HFO=1、WED=Y，没有配置 CAKE。**

## A：同探针开关对照

保持软件卸载和 WED 开启，仅将 HFO 临时设为 0 并 `fw4 reload`；完成关闭组后
恢复原 firewall 文件并 reload，再取相邻开启组。没有重启或无线重启。
固定原 Apple HTTPS 端点/IP、en0、HTTP/1.1、四连接，每个状态每方向三轮20秒；
使用同一 curl 探针，每个方向10秒空闲。CPU为路由器两核总容量。

p95采用nearest-rank，连接时间不是ICMP RTT。所有未完成连接单独保留；开启上传

记录TCP完成。LAN的480次负载请求全部成功。

下载各窗LAN p95：关44.86/20.57/27.25 ms，开49.24/61.49/71.18 ms；上传：
关74.68/45.42/23.75 ms，开96.41/155.66/45.12 ms。关闭后没有满足「LAN负载
增量均回到20ms内且公网超时归零」的强预测。结果支持HFO转发路径与这部分
延迟有关，但没有直接测量AQL/fq_codel内部队列，不能把相关性写成独占因果。
WED始终为Y，此处也不是WED模块的独立开/关测试。

空闲每批仅20个样本，尾部有波动：下载关/开LAN空闲p95为28.60/9.67 ms，
上传为8.22/31.01 ms；较高空闲尾部会压小计算出的负载增量。两侧实际吞吐也
不完全相同，下载开启中位速率高6.7%、上传低5.5%，不能称严格等吞吐比较。

两组均由en5发探针，分别让en0/en5下载；各三轮20秒、四连接，端点和探针不变。

B的公网超时均在TCP完成前，约一秒。Wi-Fi负载第一、第三窗以及有线负载全部
三窗的全请求p95进入超时区；不能只报表中的成功连接p95。Wi-Fi负载的有线
公网全尝试聚合p95为30.48 ms，而有线负载聚合p95下界约1004 ms。

负载期间有线LAN仍约1ms、有线公网完成连接仅比空闲多约3ms，支持Wi-Fi路径
是此前通常几十毫秒增量的重要来源，不支持把普通延迟全部归因于上游持续排队。
但公网失败尾部在纯有线负载/探针下仍可复现，已知不限于无线探针；尚不能区分
路由器WAN路径、宿舍上游、互联网/端点、丢包或连接限制，不称已定位的上游缓冲膨胀。
有线下载约594Mbps，也没有复现固定「约470Mbps」的上游上限。

两组使用同一Mac，共享系统与调度，不是独立第二客户端；有线下载时en0每窗
仍有约60MB背景接收（约24Mbps），因此不是完全静默的独立链路容量测试。
观测到的一次Mac CPU样本约79%空闲，不据此排除所有单核或调度影响。
B只测下载，没有额外分开测量AP与Mac自身上传队列。没有以两个p95相减估算分段排队。
