# 当前九组件：供电先于 WAN 恢复试验

2026-09-29。用户明确授权部署当前九组件，并亲自执行“拔电源、拔 WAN 网线、先恢复供电、后恢复 WAN”的实际断电试验。只替换控制面和安装本轮诊断/回退工具，保留现有内核、驱动、执行面和配置；不刷固件、不恢复出厂。

运行时源码固定为 `d7bfcf831ca5c73447cb638fdb7253d44ebd32ed`，release-image run `36558448787`。九个 ELF 均核对正式 manifest；八项与上次整栈实测相同，netifd 包含本次前缀顺序修复。部署、备份、完整产物和原始采集数据保存在 ignored `private/power-recovery-20260929/`。

执行顺序如下：

1. 核验当前生产 C、客户端健康、离线配置/overlay/三套保留包、两份恢复镜像和磁盘余量；核验新产物及离线切换、APK 更新和回退测试。
2. 安装独立的 `/root/owrt-power-test/` 采集器、持久回退及 `S01` 启动入口。先在 C 状态验证能采集、落盘、读回。
3. 保留旧活动包，安装七个新 APK，切换九组件并进行一次软件重启；客户端健康连续通过后确认部署，持久回退继续保留。
4. 明确通知用户就绪后，再进行物理操作：拔电源；拔 WAN 网线；等待 20 秒；先插电源，WAN 保持断开 120 秒；再插回同一 WAN 网线。LAN 网线不属于本次拔插对象。
5. 观察插网后 3—5 分钟，读取同一 boot 的采集数据、组件身份和客户端健康；失败现场先保存，再处理恢复。

采集器由独立的静态 C 辅助程序和原版 shell 启动，不依赖九个 Rust 组件正常提供服务。`S01` 早于网络 init；保留启动时 dmesg，并监听此后的路由 netlink。它不覆盖 PID1 到达 init 之前的全部执行过程；该边界仍依靠已核验的离线恢复资料。

每次启动按 boot ID 建目录，保存单调启动时间及设备墙上时间。采集内容包括链路、地址/路由变化，WAN 上的 DHCPv4/DHCPv6、本机相关 ARP、IPv6 邻居发现报文，以及 WAN/进程/协议/路由/日志状态快照。先由内核过滤协议，再排除无关 ARP，不开启混杂模式。包捕获边界为实际 `wan` 的 Ethernet 帧，未解包 VLAN/IPv6 扩展头的任意组合；原始地址和标识仅保存在私有证据。

事件和报文最长每两秒请求刷新并 fsync；快照完成后 sync。突然断电仍可能丢失最后尚未落盘的一段，断电期间设备本身无法记录事件。电脑侧另存阶段时间及可达性。已落盘证据按 boot 分开追加，回退不会删除；不将“杀进程后数据仍在”的离线测试冒充真实掉电持久性证明。

采集文件有每类大小上限、每 boot 约 3.5 MiB 的预留及约 10 MiB 的准入预算；overlay 保留至少 8 MiB 时停止大块采集。达到限制会留标志，不覆盖老证据。快照子进程有 10 秒和 64 KiB 上限，避免 ubus/logread 异常拖住采集；启动前 15 分钟约每 10 秒一份，之后降低为每分钟一份。

持久 guard 独立于原 900 秒首次部署 canary。每次 Rust 启动增加未确认启动计数；三次连续健康观测确认 WAN carrier、默认 IPv4 路由、WAN/LAN ubus 状态及从 WAN 发出的 IPv4 ping 后清零计数，但保留后续启动保护。连续 600 秒未恢复健康，或第三次未确认启动时，先保留快照、核验 `/rom` 身份，再恢复全部 C 启动路径并重启。C 启动只采集，不进入回退循环。

guard 使用的外网 ping 已在当前 C 生产栈验证通过。它是本轮试验保护条件；外部故障也可能触发保守回退。正式验收还包括九组件真实运行哈希、客户端 DHCP、双频 AP、HTTP/HTTPS、DNS、实际联网及配置保持。

SSH 可用时的本轮人工恢复入口为 `/bin/sh /root/owrt-power-test/power_guard.sh restore`，与自动恢复使用同一路径。它保留采集目录、配置和恢复包。执行恢复前仍核验 C 原件，身份不符则拒绝写入。试验结束后先下载、核验各 boot 的证据，再决定组件保留和诊断工具清理；本轮不自动删除记录。
