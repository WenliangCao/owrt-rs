## 这轮比较回答什么

原配置是软件流卸载开启、硬件流卸载关闭、WED 关闭。候选只开启硬件流
卸载，WED 保持关闭。预期 Wi-Fi 继续经过软件路径，有线长连接交给 PPE，
从而保留前者的低延迟和 WED 关闭后的内存，同时减少后者的 CPU 成本。
如果正式 Wi-Fi 流出现任一方向硬件绑定，或 Wi-Fi 延迟、有线 CPU 未过门，
就恢复原配置。这轮不增加 CAKE、不改组件、不再研究已经闭合的公网握手迟延。

使用现有 `http_network_profile.py`，固定相同公网 HTTPS 端点、IPv4 地址和
四条下载连接。Wi-Fi 绑定 en0，扩展坞有线绑定 en5；每种配置、每个接口
各三窗 20 秒，共十二窗，只测这一轮。curl LAN、公网探针均绑定对应接口，
端点与实验 A 相同。48/48 条正式连接由连接表确认直连，所有窗口 utun
字节增量为零，没有更改 Mac VPN。PPE 每约两秒采样，两边使用相同仪器。

## 吞吐、CPU 和 Wi-Fi 延迟

CPU busy 是两核总容量的整机占比，包含内核与现有服务。CPU/GiB 使用负载
内部采样的 CPU 速率，除以整个窗口的 HTTPS 有效数据速率。括号是三窗范围；
LAN p95 合并三窗全部探针计算，不是三窗 p95 的中位数。

| 接口 / 配置 | 下载 Mbps，中位数（范围） | 整机 CPU busy，中位数 | CPU 秒/GiB，中位数（范围） | LAN TCP p95 ms |
| --- | ---: | ---: | ---: | ---: |
| Wi-Fi / 纯软件卸载 | 395.38（366.27–430.72） | 51.37% | 21.855（20.663–22.322） | 27.919 |
| Wi-Fi / 硬件卸载开、WED 关 | 397.04*（356.69–452.38） | 55.26% | 23.910*（21.671–26.482） | 31.096 |
| 有线 / 纯软件卸载 | 505.88（500.74–545.92） | 35.50% | 11.172（11.161–13.418） | 2.601 |
| 有线 / 硬件卸载开、WED 关 | 471.59（277.43–491.51） | 4.55% | 1.649（1.589–4.812） | 0.830 |

`*` 候选 Wi-Fi 第三窗的 wall-clock 总时长未保存，用四条 curl 中最大的
`time_total=20.001227 s` 估计，因此该窗吞吐与 CPU/GiB 是估计值；LAN 延迟
与 CPU busy 有完整原始记录。下文说明恢复过程，没有重复这一窗。

基线 Wi-Fi 三窗 LAN p95 为 19.023/28.627/27.919 ms；候选为
31.096/14.424/18.191 ms。事先冻结的判据是候选单窗 p95 中位数不超过基线
最大值，合并 p95 增量不超过 `max(5 ms, 基线单窗 p95 范围)`，并且 LAN
探针全部成功、候选吞吐区间不能整体低于基线。实际单窗中位数
18.191≤28.627 ms，合并增量 3.177≤9.604 ms，两侧吞吐范围重叠，Wi-Fi
两组共 240/240 个 LAN 探针成功。这是按预定波动范围通过，没有证明统计等价
或 Wi-Fi 延迟改善。Wi-Fi 的 CPU/GiB 中位数增加约 9.4%，没有得到硬件 CPU 收益。

有线 CPU/GiB 预定门槛是中位数至少降低 15%，且候选最大值低于基线最小值。
实际降低 85.2%，候选最大值 4.812 也低于基线最小值 11.161，CPU 收益明确。
有线三窗 LAN 探针 120/120 成功。**有线交付吞吐中位数下降 6.8%，候选
最高 491.51 Mbps 也低于基线最低 500.74 Mbps；不能报告为吞吐提升或相等。**
这是顺序测量的宿舍共享上游与公网端点吞吐，未控制其他用户负载，不能据此
确定下降原因。Wi-Fi 延迟所需的压力可比条件已经满足；有线保留判据是单位
流量 CPU 成本明确下降，未将有线吞吐提升设为门槛。

## 实际流路径

| 配置 / 接口 | 正式流数 | PPE 采样次数 | 匹配正式流的 BND | 计数增长证明 |
| --- | ---: | ---: | --- | --- |
| 纯软件 / Wi-Fi | 12 | 43 | 两个方向均无 | 无硬件绑定 |
| 纯软件 / 有线 | 12 | 43 | 两个方向均无 | 无硬件绑定 |
| 硬件开、WED 关 / Wi-Fi | 12 | 42 | 两个方向均无 | 无硬件绑定 |
| 硬件开、WED 关 / 有线 | 12 | 43 | 12/12 条双方向绑定 | 12/12 条双方向包数、字节数增长 |

逐条以 curl 的本地/远端端口、连接表的 NAT 回复元组、PPE 的 orig/new 元组
关联。候选有线两方向出口均为 GDM1，无 WDMA 信息；采样覆盖的下载方向合计
增加 1,889,775 包、2,858,341,592 字节，上行 ACK 方向增加 480,811 包、
45,508,034 字节。这些计数包含协议开销且只覆盖采样区间，不与应用字节等同。

一个容易误判的现象是：**候选 Wi-Fi 12/12 条连接也带 `HW_OFFLOAD` 标记，
但每条流的 11 个双 PPE 节点快照中，两个方向都没有对应 BND 条目。** 因此
没有将该标记当成硬件路径证明，也未漏掉只绑定 ACK 单方向的可能。同期
249 条 IPv4 背景 BND 观察都属于有线地址，另有 78 条 IPv6 背景观察；
这些都不是固定 IPv4 Wi-Fi 下载流。结论限于本轮持续流与采样覆盖，不声称
每个瞬间、每种协议、每条未来连接都已验证。
