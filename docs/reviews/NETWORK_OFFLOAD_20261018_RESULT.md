# HFO + WED：保留配置；满载延迟需要单独处理

2026-10-18。**启用硬件流卸载和 WED 后，每 GiB 下载的路由器 CPU 成本降低
72.0%，吞吐差异在本轮波动内；185.6 秒客户端健康窗口通过，配置已保留。
上传、下载负载都出现明显延迟恶化，CAKE 值得受控试验，但本轮没有安装或配置。**
固件仍为 v0.3.0，没有重写或替换组件。

## 卸载对照

Mac 经原有 5 GHz Wi-Fi，固定 Apple networkQuality 官方配置返回的 HTTPS
端点及同一 IPv4 地址，HTTP/1.1、四条连接、每种配置三次 20 秒下载。
软件卸载一直开启；候选增加 HFO 和 `mt7915e wed_enable=1`，通过一次正常重启生效。
这是 Wi-Fi＋宿舍上游＋公网端点的交付吞吐，不是纯路由器极限。

| 指标 | 原配置三轮 | HFO + WED 三轮 | 中位数变化 |
| --- | --- | --- | --- |
| 下载 Mbps | 496.92 / 435.75 / 482.05 | 467.61 / 453.98 / 489.78 | 482.05→467.61，−3.0% |
| 路由器整机 CPU busy | 57.12% / 50.28% / 52.65% | 15.04% / 18.15% / 12.44% | 52.65%→15.04%，−71.4% |
| CPU 秒 / GiB 下载 | 19.749 / 19.824 / 18.763 | 5.525 / 6.868 / 4.362 | 19.749→5.525，−72.0% |

CPU 为 `/proc/stat` 的两核总容量，包含内核和现有服务，不是 Rust 进程耗时。
按正式流量内部采样的 CPU 速率除以完整窗口的应用数据速率计算 CPU/GiB。
原配置/候选的轮内 CPU/GiB 范围分别为 1.061/2.506，均远小于 14.224 的
中位数差；收益超过事先规定的 15% 门槛。吞吐差 14.44 Mbps，小于两侧
61.17/35.80 Mbps 的轮内范围，没有证明吞吐提高或可辨的吞吐退步。

启用前，冻结当前 UCI、netifd、设备与文件输入，用实际发货 Rust fw4 和镜像
保留的原版 fw4（ucode）生成规则：软件卸载 5930 B、硬件卸载 5985 B，两侧
均逐字节相同，stderr 为空。当前规则也与冻结夹具一致。硬件候选的完整
`nft -c` 及能力检查通过，前后现网配置与规则没有变化。

候选启动后，WED 参数、WO 固件日志和非空 TX/RX 状态相互吻合。12/12 条正式
下载流逐条匹配 curl 端口、conntrack 和 NAT 元组；下载出口为 WDMA0，上行
ACK 出口为 GDM1，两方向 PPE BND 包/字节计数均增加，每条至少四个快照。
基线 18 个硬件快照没有 BND 条目；结论不只依靠 `HW_OFFLOAD` 标记。

候选负载期间 MemAvailable 中位数比基线少约 29.7 MiB，SUnreclaim 基本不变。
重启年龄、缓存和缓冲池不同，不能把差值称为精确 WED 分配量。随后健康窗口
MemAvailable 在 85.7–94.6 MiB 之间，起止约 89.8/89.9 MiB，没有持续下降。

完整客户端健康 **185.577 秒、19/19 次**通过，覆盖 WAN/WAN6、双频无线、
IPv6 地址/路由、直接 TCP DNS、双栈 HTTPS、LuCI 与组件运行身份。负载延迟
测量后又通过一次完整检查；未观察到匹配的 WED/mt7915 驱动超时、重置、OOM
或内核故障。这是短时验收，不是长期耐久性保证。

## 上传和下载负载延迟

在已保留的 HFO+WED 配置下，两个方向各三次 20 秒、四连接；每个方向先测
10 秒空闲。延迟是从 Mac 发起的新 TCP 建连时间，不是 ICMP RTT。下表 p95
只统计完成握手的连接，包括握手后 HTTP 超时者；失败另列。

| 负载 / 探针目标 | 空闲 TCP p50 / p95 ms | 负载 TCP p50 / p95 ms | 负载 HTTP 总耗时 p95 ms |
| --- | ---: | ---: | ---: |
| 下载 / 路由器 LAN | 3.53 / 8.58 | 8.76 / 86.66 | 155.22 |
| 下载 / 公网端点 | 23.81 / 29.25 | 32.04 / 125.06 | 647.23 |
| 上传 / 路由器 LAN | 3.24 / 8.17 | 21.52 / 78.49 | 141.63 |
| 上传 / 公网端点 | 25.82 / 30.66 | 38.46 / 107.73 | 408.79 |

下载公网尝试 103 次：14 次没有记录到 TCP 完成的超时、1 次握手后 HTTP 超时。
上传公网尝试 114 次：5 次没有记录到 TCP 完成的超时。超时约一秒；下载三窗
及上传前两窗的全请求 p95 已进入超时区，准确值未知，不能用表中的成功连接
p95 代替完整尾延迟。LAN 负载探针 240/240 成功，两个方向的空闲探针均无失败。

公网成功连接的单窗 p95：下载 139.79/125.06/58.81 ms，上传
97.98/212.88/102.91 ms；两方向均 **3/3 窗口**超过预定的空闲增量 20 ms 门槛。
对应吞吐为下载 453.08–481.80 Mbps（中位 466.76），上传 574.59–632.32 Mbps
（中位 622.39）。这是当时交付吞吐，不是稳定接入容量或 CAKE 处理能力。

LAN 延迟同时明显升高，说明等待也发生在 Wi-Fi、Mac 或本机路径，不能把公网
增量全归因于宿舍上游。初始配置的公网 TCP 负载探针也有超时（A/B 各 11/7 次）；
这项问题不是只在开启 HFO 后才首次出现，两个阶段使用不同探针实现，不合并统计。

## CAKE 的下一步取舍

现机没有 SQM/CAKE、tc 或 IFB 组件，WAN 仅有一个 TX 队列。本轮没有安装软件包
或配置整形。若用户确认，可做一次约 **下载 400 / 上传 500 Mbps**的诊断性试验，
分别比本轮中位吞吐低约 14%/20%；不是长期推荐值，也不保证路由器能承载该速率。

硬件 flow offload 必须在该试验中关闭，使被整形流量经过 CPU 的 tc/IFB，
因此会放弃当前主要卸载收益，并增加 CPU 成本。软件 flow offload 在匹配内核
中仍经过 ingress tc 和出口 `dev_queue_xmit()`，不是原则上与 CAKE 不兼容；
保留它必须用实际 tc/IFB 字节计数和限速结果确认整形覆盖。WED 的 DMA 加速
与 PPE 流卸载分别核验，不能只看开关推断所有包都经过 CAKE。

下行整形不能消除数据抵达前已经发生的等待，WAN 上的 CAKE 也不能直接管理
Mac 的 Wi-Fi 发送队列。应把下一轮裁决限定为：实际满载延迟是否显著降低，
以及为此损失多少吞吐、增加多少 CPU；未得到用户决定前保持当前 HFO+WED。
匹配源码和作用路径见[转发研究](NETWORK_FORWARDING_ACCELERATION_20260929.md)与
[排队研究](NETWORK_QUEUEING_20260929.md)。
