# R96 ubusd：共享不可变路径，整体目标仍开放

2026-09-20。恢复供电后重新验证新 boot 的生产 C、健康与离线备份，再运行本轮实验。
保留路径共享改动：减少实际注册表的请求堆存储，功能门通过；没有宣称整体内存或所有性能指标胜出。
[验证身份和范围](r96-ubusd-path-validation.json)。

## 从匹配 C 实现确定存储差异

精确上游 `24864e7840b3a02a9ef76284a373f6b2f00b8a9b` 的 `ubusd_obj.c` 用一次 `strdup`
保存路径，AVL 索引直接引用对象的 `path.key`。Rust 原来在对象表和 BTreeMap 路径键中各有一个
`Vec<u8>`，订阅、对象事件和 ACL 查询还会复制路径。

本次用 `Rc<[u8]>` 让对象与索引拥有同一份不可变字节。单线程服务器无需原子引用计数；
没有循环引用、手动释放或新增 unsafe。结构和树节点也变小，内存收益不只来自路径字节本身。
背压恢复路径继续转为独立 `Vec<u8>`，保留删除/重建时的恢复语义。
标准库行为依据 [Rc 官方文档](https://doc.rust-lang.org/std/rc/struct.Rc.html)。

引用计数、分配大小类别和代码布局都可能带来成本。因此没有仅凭“少复制”推断性能或 RSS 必然改善。
[冻结运行时补丁](r96-ubusd-path.patch)以 `975ab2f` 为基线；生产运行时只改对象路径所有权和恢复路径复制。
候选 `ece562af…`，改动前 `46940829…`；实际固定构建路径、SDK、Rust 1.98.1、cwd 和 flags 保持一致，
两者 release 都是 507,880 字节。

## 功能和路由器验证

- 构建机与物理路由器分别通过 28 条单测，包括原始字节路径、ACL、监视器、部分写入和删除/重建续传。
- 六个构建机历史门通过：root/ubus 用户功能差分、ACL/字节差分、模糊测试、资源边界、恢复。
  它们不冒充实机全功能验收。clippy 门通过；诊断例程仍有共享 sys 模块的 unused-import 警告。
- 四方四 block、每负载每窗口 5,000 次，16 个实机窗口共 **800,000 个计时请求成功**。
- 另有四个实机内存诊断窗口，每窗 12 种对象数/路径长度组合，核对查找、删除、跨索引销毁持有路径以及最终释放。
- 所有窗口结束后清理、生产 C、配置、boot、宿主挂载、客户端健康检查通过。最后扫描零测试目录、零进程引用。
  没有安装或启用 Rust 生产组件。

内存诊断第一次构建遇到旧 `Vec` 类型的 `as_ref` 推导歧义，改为两版本通用的切片索引后通过；
保留该编译失败记录，没有改变运行时来绕过它。

## 内存：注册表减少，RSS 没有证明胜出

先冻结 [内存实验计划](r96-ubusd-memory-plan.json)，用同一 allocator 计数器构建两版本的真实 Registry。
计数成功分配的 Rust layout 大小；realloc 后更新逻辑存活量。它不覆盖 allocator 内部搬迁瞬时双份存储、
分配器元数据/取整、libc 内部分配、客户端、栈、代码、共享库和内核。
所有对象共用一个空类型；这不是完整守护进程的堆布局。

下面是 128 对象的实机字节数。四个窗口按 before/candidate/candidate/before 运行，两个版本各自复现完全一致。

| 路径长度 | 改动前常驻请求堆 | 候选常驻请求堆 | 改动前构造请求堆峰值 | 候选构造请求堆峰值 |
|---|---:|---:|---:|---:|
| 16 | 38,164 | 34,268 | 50,460 | 45,716 |
| 64 | 50,452 | 40,412 | 61,212 | 51,092 |
| 256 | 99,604 | 64,988 | 104,220 | 72,596 |

常驻请求堆分别减少约 10.2%、19.9%、34.8%。全部 12 种组合的请求堆与构造峰值均下降，
包括 1、64、128、512 对象；释放全部持有者后均回到计数基线。
[完整内存记录](r96-ubusd-memory-results.json)、[复算工具](../../tools/r96_registry_memory_report.py)。

但完整性能矩阵结束时，proc 的 VmRSS/RssAnon 中位数（KiB）是：
C 968/144，R89 616/160，改动前 626/170，候选 **628/172**。
候选并没有给出更低的进程计数：三个配对窗口相同，一个窗口各高 4 KiB，导致中位数各高 2 KiB。
这些异步计数既不能证明精确回退，也不能被解释成内存胜出；真实分配器布局与整体峰值仍待量化。

## 性能：新客户端条件下的全部配对方向

[冻结性能计划](r96-ubusd-path-plan.json)采用同一新 CPU 计量客户端 `885ee761…`。
它与旧冻结客户端不同：共享 ubus 库已包含后续预读优化，详见 [计量与版本边界](R96_MEASUREMENT.md)。
不能把 R95 到本轮对 C 优势扩大的幅度归因于路径共享，也不能合并不同客户端、不同 boot 的样本。

下表仅列本轮相对改动前的四个 block 配对变化中位数。正数为增加。CPU 使用新的进程时钟，只含主体所有线程；
旧 tick 指标、依赖、客户端和全部逐轮值仍在 [完整数据](r96-ubusd-path-results.json)。四轮不是正式优越性确认。

并发精确查询 CPU 四轮变化为 +3.97%、−0.33%、+3.57%、−3.25%；并发 64 对象完整列表为
+4.37%、+2.04%、−0.03%、−2.47%。没有将这些反向变化抹掉，也不凭四轮宣布它们等价或稳定回退。

本轮新客户端条件下，十负载的 mean/p50/p95/p99 与主体 CPU 对 C 的配对中位变化均为负；

并发 64 对象列表客户端 **+0.51%**。依赖进程 CPU 的 invoke / invoke_c4 对改动前 **+0.31%/+3.22%**。
这些成本不能被主体 CPU 改善替代；部分空闲依赖零计数不构成胜出。

## 保留理由与未完成项

保留此小改动，是因为真实注册表的存储减少已在实机重复验证、所有权释放与功能门通过，
并且没有依靠缓存或重写队列来换取这项收益。它是一个有已知限制的优化步骤，**不是性能与内存目标的验收**。

仍开放：旧冻结客户端/原版 libubus 调用者下的比较；表中的尾延迟和并发 CPU 反向变化；整体内存和峰值；
充分独立样本的确认实验；九组件组合验证及其余组件的性能目标。
原 C 方法名直接引用保存的签名字节，Rust 方法名仍有独立副本；每客户端接收存储也是下一步可研究的成本，
但尚未实现或验证，不计入本轮收益。

原始结果保存在 `private/r96/ubusd-path/`，备份在 `private/r96/recovery-full/`，均不入 Git。
