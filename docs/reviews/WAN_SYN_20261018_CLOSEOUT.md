# 公网超时关项：楼宇上游握手迟延

2026-10-18。一次正式 20 秒 WAN 抓包中，30 次有线 curl 探针出现 **3 次连接
超时**。三条首个 SYN 都已出现在 WAN 出站方向，超时期限内没有 SYN-ACK；
约一秒发生 SYN 重传，随后约 22–24 ms 收到 SYN-ACK，已经晚于 curl 的一秒
期限。其余 27 条均匹配正常的 WAN SYN/SYN-ACK。

按用户约定将此前“约 5% 公网连接超时”归档为 **楼宇上游：首轮握手迟延／
疑似丢包**，结束路由器侧研究。这是排障分类，不是定位到楼宇内某台设备；
单点软件抓包不能区分楼宇、运营商、互联网、端点或返回路径的具体跳点，
也不等同于物理线路抓包。问题已关项，未声称外部丢包已修复，不再开研究轮。

## 三条超时连接

下表时间差均来自同一 WAN pcap，不依赖 Mac 和路由器时钟同步。

| 探针序号 | 第二个 SYN 距首 SYN | 首个 SYN-ACK 距首 SYN | SYN-ACK 距第二个 SYN |
| --- | ---: | ---: | ---: |
| 8 | 1000.071 ms | 1023.990 ms | 23.919 ms |
| 21 | 1001.618 ms | 1023.739 ms | 22.121 ms |
| 24 | 1001.406 ms | 1025.559 ms | 24.153 ms |

三条重传的序号与原 SYN 相同，返回 SYN-ACK 的 ACK 都是该序号加一。
连接跟踪先显示 `UNREPLIED`、回复包数 0，随后回复包数变为 1。
因此不能写“整个抓包期间没有 SYN-ACK”：确有回复，只是晚到。响应紧随重传，
符合首轮握手丢包或迟延，但无法区分首个 SYN 丢失、首个 SYN-ACK 丢失和延迟响应。
本轮 3/30 为 10%，有限样本不能将历史“约 5%”改成固定的新故障率。

## 测量与证据边界

复用原 Apple HTTPS 端点及固定 IPv4、HTTP/1.1 和四路不限速下载。负载绑定
Wi-Fi en0，探针绑定有线 en5，保持原 0.5 秒节奏和一秒连接／总请求期限。
25 秒下载包围正式 20 秒抓包，交付约 451.21 Mbps；探针安排在抓包内部，
留出末次超时余量。四条下载连接均直连，utun 字节增量为零。

临时静态 tcpdump 4.99.6/libpcap 1.10.6 来自匹配 OpenWrt 配方的官方源码，
在 Oracle 编译，校验静态 AArch64 ELF 后只放入路由器 `/tmp`。禁用混杂模式，
仅捕获目标 TCP 443 的 SYN/RST，snaplen 128；独立计时器在 20 秒结束抓包。
pcap 有 88 帧，libpcap 报告 received 133、kernel dropped 0；两者分别保留，
不将计数差写成零。WAN TX 错误／丢弃、RX 错误增量均为 0，RX 丢弃增量 197，
未能将接口级 RX 丢弃归属到这些握手，也不声称所有网卡接收路径都已排除。

Mac curl 实际未采用请求的固定源端口。成功连接以 curl 报告的实际端口和
conntrack 原始／回复元组关联；失败连接没有返回端口，使用各自时间窗内
唯一的有线源地址 NAT 元组及 WAN SYN 关联，明确记录为时间关联，不冒充
固定端口直接证明。由 27 条成功握手推导路由器减 Mac 的时钟偏移区间
−49.844 至 +1.750 ms；即使取该区间边界，三条 SYN-ACK 都晚于 curl 退出。
它们也都落在完整抓包范围内，末端截断不是“无响应”的来源。

准备阶段发生一次 BusyBox 小数 `sleep` 不兼容：正式探针尚未启动，抓包未按
预期结束，已人工停止。该无效准备记录原样保留；修正为整数计时与独立强制
退出后，才执行上述一次正式窗口。没有因正式结果重测或更换样本。
