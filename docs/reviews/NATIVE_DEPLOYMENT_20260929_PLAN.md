## 刷写前恢复保障

新鲜 sysupgrade 配置备份和 overlay 全量备份保存于电脑，逐项核验配置、密码、SSH 主机密钥和 LED 定时任务；sysupgrade 未备份的原样默认文件与镜像中的默认值核对。官方 OpenWrt 与小米救援镜像重新校验 SHA256。

`native_trial_prepare.py` 生成新的私有配置归档，保留原备份全部 45 个成员，额外加入临时 `S01owrt-native-trial` 服务、guard、状态令牌和既有独立 helper。helper 仅使用有时限的命令执行功能，不启用采集。固件文件保持原哈希，用户配置不进入 Git 或构建机。

| 条件 | 动作 |
|---|---|
| 首次启动十分钟内未获客户端确认 | 验证镜像内 C 原件，调用 `owrt-recover-c`，同步落盘后强制重启 |
| 已确认部署后，LAN/WAN/双频无线及 WAN 探测持续失败五分钟 | 同上 |
| 连续三次启动没有恢复并确认健康 | 提前恢复 C |
| 已确认部署，连续三次本机健康探测成功 | 清零失败启动计数，保留后续启动保护 |
| C 原件或恢复工具身份损坏 | 拒绝替换并保留日志 |
| 已恢复 C 的启动 | guard 退出，不循环重启 |

首次确认必须来自电脑侧连续至少 180 秒的客户端验收。本机健康判定不代替首次客户端确认。恢复保护从原生 PID1 执行 S01 服务时开始；闪存损坏或到达该阶段之前的故障仍需按[救援手册](../RUNBOOK_AX3000T_RECOVERY.md)处理。独立 preinit hotplug 已在上一阶段验证，当前 procd 的 sysupgrade 移交也再次通过隔离 C/Rust 对照。

九项 guard 分支在原镜像 shell 和实际 C 恢复工具上通过，测试只模拟时钟、健康结果和 reboot。原版配置恢复和首次服务迁移保留 guard；原生 Rust PID1、原服务脚本和真实后台 guard 联合启动通过，包含十项原启动断言和 guard 存活检查。首个 selftest 因模拟 `/proc` 缺失 `mountinfo` 被正确拒绝恢复，修正测试环境后重新验收，原失败记录保留。

独立 ARM Linux 构建机的原始证据归档已核验 SHA256、gzip 完整性与工具身份。原始证据、新鲜备份、配置归档、令牌和观察日志仅存在 `private/native-deploy-20260929/`。

## 刷写与确认

1. 核对旧启动身份及配置未变，复制固件和配置归档至路由器 RAM，核验两份 SHA256。
2. 执行原版 `sysupgrade -T -f <配置归档> <固件>`；检查通过才进入刷写。
3. 电脑上的独立进程执行同一 `sysupgrade -f`，跨越 Wi-Fi 断连持续观察。保留普通分区选项，不强制绕过验证。
4. 要求新 boot ID、九个标准路径和 ROM 身份、六个运行进程身份一致；原服务已启用，旧组件开关和三个绑定挂载均消失，fw4 检查通过。
5. 核对原配置，验证客户端 DHCP、双频 AP 桥接、管理 HTTP/HTTPS、DNS、路由器外网 HTTPS 和硬件 watchdog；连续 180 秒通过后才确认。
6. 归档结果和实际空间变化。保留临时 guard，供用户之后进行真实断电与延迟接回 WAN 的复测；完成物理验收后另行清理临时保护。

客户端已有的 VPN 限制使外网 DNS/HTTPS 项沿用路由器侧探测；DHCP、LAN 路由及管理 HTTP/HTTPS 从实际 Mac 客户端验收。普通升级重启与用户拔电复测分别记录。
