# R98：单遍借用事件投递实机结果

第二版已完成 67 个通过的实机窗口，暂不合入运行时。无订阅时的注册收益保留，活动接收者成本较基线下降；
但仍未全面胜 C，部分查询也触发进一步调查门。接受运行时仍为 `5a19517`，没有达到语言极限的证据。

## 机制与覆盖

在按需编码之上，借用已排序的事件匹配表直接遍历，省去目标 ID 快照，
用既有 `send_borrowed` 在实际排队时才复制。单线程 handler 执行期间，发送只改变客户端队列、
监控及 touched 列表，不改变订阅表或对象归属；保持去重、发送者排除、序号、监控和队列限额。
完整[补丁](r98-event-borrow.patch)，候选 ELF `4fe9d5e2…`。

31 条实机单测和 C/基线/候选七组协议差分通过；构建机六组功能/ACL/fuzz/限额/恢复门也通过。
具体身份见[预筛查](r98-borrow-preflight.json)及[完成记录](r98-borrow-validation.json)。
下面都是四个随机配对 block 的探索中位变化，不能当作显著性、等价或全局优越性证明。
每个 block 含 C、R89、接受基线、第一版 lazy、第二版 candidate；各组客户端字节相同。

## 分配与内存

实机请求堆诊断使用相同 fixture，依次 before/lazy/candidate/candidate/lazy/before，16 场景两次结果精确相同。
暖态、16 字节消息、八个匹配对象的成功 alloc 调用从 19 降到 10，realloc 从 6 降到 5；
这支持消除快路径目标数组及逐接收对象复制的解释。
32 KiB 消息强制排队后，八对象 alloc 从 19 到 18，排队仍需拥有完整字节，不能称为所有情况零复制。
无接收者的 32 KiB 消息峰值请求字节从 165,842 到 100,210；有八个排队对象则从 430,238 到 397,390。
所有场景排空后的保留请求字节和发送后未排空占用均与接受基线相同，队列所有权没有被省略。

[完整堆结果](r98-borrow-event-memory-results.json)包含冷态、暖态、小/大消息、无/不匹配/单/八对象。
这些是插桩构建中实际观察到的 Rust 分配请求，不是 malloc 物理占用、PSS、内核缓冲或完整进程峰值。
不由此推导 C/R89 内存优势；查询矩阵 proc 页计数另保留在结果中。

## 失败、清理与后续

首次采集在第一 block 的候选窗口结束后，外部 HTTPS 健康探测返回错误，采集自动停止。
整个四窗口不完整 block 保留并排除，没有按性能数值筛选；健康、配置、boot、生产身份及清理复查通过后，
使用原先冻结的顺序、客户端和二进制从头采集。见[中断记录](r98-borrow-interruption.json)。
最终 60 个性能窗口、6 个堆窗口、1 个正确性窗口全部通过各自的生产 C、配置和挂载不变及清理检查。
没有部署候选；后续 R99 实验按串行队列衔接，不能在它运行时声称整个路由器没有测试进程。

继续验证固定回复分配和 Publish ACL 凭据复制；独立回复候选及与事件改动的组合候选分别保留身份。
先校准串行 CPU 的 A/A 分辨能力，再冻结候选比较。正确性、完整内存、查询反向结果和九组件组合仍是开放项。
