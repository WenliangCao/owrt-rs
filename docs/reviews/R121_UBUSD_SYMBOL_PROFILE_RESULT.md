# R121 符号级热点结果

12 个冻结 Oracle 窗口全部完成：每窗口 500000 个单监听者事件，低连接/64-held、两块反转顺序。
采样 ACK、payload、进程/库身份均验证，无丢样/节流，子进程全部回收。
这是构建机热点诊断，不是路由器性能排名；[派生值与原始文件哈希](r121-symbol-profile-results.json)。

| 精确发布 ELF | 总样本 | 用户态 | 内核态 | 未解析用户态 |
|---|---:|---:|---:|---:|
| C | 11295 | 1762 | 9533 | 829 |
| R109 | 9695 | 1689 | 8006 | 0 |
| R115 | 11583 | 1959 | 9624 | 0 |

R109/R115 的 linker Map 来自完整 ELF 逐字节一致的重建；C 主 ELF 符号伴随的代码字节按加载地址匹配，
共享库采用精确文件的动态符号。C 仍有约 47% 用户态样本没有函数名，不把未知地址算成零开销。
平面样本只能归属于发出的函数，内联代码归在外层符号，不能代替调用次数或因果消融。

## 发现与下一项假设

1. 内核占约 83–84% 样本。R109 同事件数的内核样本较少，C 与 R115 更接近；
   热点包括 socket 唤醒、系统调用入口和 Unix stream 读写。这支持继续检查系统调用工作量，
   不能单凭 Oracle 样本解释路由器上全部差距。
2. R115 的 `__libc_malloc_impl`、`__libc_free`、`alloc_slot`、`nontrivial_free`、
   `__libc_realloc` 合计 641/11583，即 5.53% 样本。客户端表 `get_mut` 为 1.61%；
   这解释为什么继续换表容器不是足够大的方向，但也不是所有相关哈希工作的上界。
3. 回查 R115 `invoke -> system_object`，同步调用前仍有 `method.to_vec()`、`data.to_vec()`；
   所有系统 handler 在调用返回前结束，不停车保存输入。C 将当前消息直接交给对应 handler。
   下一候选只借用这两个输入，验证有无可测收益；event credentials、relay BlobBuf 和 FD 接收边界全部保留。

**不再以“没有低风险方向”收尾。** 现在存在具体代码位置、分配热点和可单独反证的假设，
但尚无新候选路由器结果。R109 仍只作历史参照，FD 兼容性门保持原样。
