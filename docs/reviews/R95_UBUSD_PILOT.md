## 实机结果

AX3000T 六个独立启动的配对 block，每个含随机排序的 C、正式 R89、当前候选；
各轮先预热 100 次，再测 2,000 次全量 lookup。夹具为 128 个对象，完整对象集合在前后核对，
冻结客户端逐次核对 bench.target。全部 36,000 个计时请求成功。
18 个窗口均完成清理，生产 C 身份、配置、boot、主机挂载、客户端健康前后通过，未安装候选。

单位 µs/请求。三侧列为六轮指标的中位数，百分比列为六个**配对变化**的中位数，
因此百分比不等于直接相除相邻两列。

| 指标 | C | R89 | 候选 | 配对比 C | 配对比 R89 |
|---|---:|---:|---:|---:|---:|
| 主体 CPU | 747.50 | 652.50 | 247.50 | -66.67% | -62.21% |
| mean | 1521.15 | 1523.22 | 1449.25 | -4.36% | -4.65% |
| **p50** | **1389.19** | **1418.20** | **1414.70** | **+1.36%** | **-0.46%** |
| p95 | 2201.32 | 2085.33 | 1713.19 | -18.74% | -18.01% |
| p99 | 2531.32 | 2352.35 | 2013.65 | -16.37% | -14.86% |
| 客户端 CPU | 1437.50 | 1445.00 | 1245.00 | -13.26% | -13.84% |

每个 CPU tick 在本轮对应 5 µs/op，不能用它确认小于这一量级的改进。
provider 在采样期间 CPU 计数均为 0，比值留空，不将其算作“性能全胜”。
候选 p50 在六个配对中四次高于 C，两次低于 C；这延续了值得研究的反例，
没有证明稳定退步的效应大小，也没有证明所有尾延迟已解决。六轮依旧只是探索样本。
本轮不作峰值内存或 PSS 结论，新的计量工具尚未补齐。

## 下一条可证伪假设 H1

配套 C 源码 `ubusd_proto.c::ubusd_send_obj/__ubusd_handle_lookup` 逐对象生成和发送。
当前 Rust `Server::try_batch` 先检查整个回复不超过 16 KiB，再全部组装后发送。
这里读的是精确镜像匹配源码，并非把最新 upstream 默认分支当规格。

客户端 CPU 明显大于守护进程 CPU。**推测**：全批次等待可能减少 C 原来允许的生产/消费重叠，
因此虽然减少了大量 syscall，却未改善 p50。仅这些数据还不能把原因唯一归到批处理；
调度、客户端解析和双核上的迁移同样可能影响结果。

拟检验：保持 16 KiB 总回复资格上限和原有 ACL/monitor/背压/队列边界，只把生成过程中
待发送的块限制为约 4 KiB，完整帧不拆分；大于块大小的单帧独立发送。
预期为首批更早到达、常见回复的常驻批缓冲减少，代价可能是 syscall/CPU 上升。
不能以 p50 改善抵消 CPU 退步，需与 C/R89/改动前候选分别实测，且补完整线序和短写回归。

`SOCK_STREAM` 不提供应用消息边界，`sendmsg` 返回已发送字节数，非阻塞写需保留未完成部分，
不允许假设“一次写等于一次完整收”。依据 [unix(7)](https://man7.org/linux/man-pages/man7/unix.7.html)
与 [send(2)](https://man7.org/linux/man-pages/man2/sendmsg.2.html)。
原有 `send_lookup_batch` 的部分写入/队列逻辑必须继续承担这些语义。

H1 当前只是一条试验方向；失败也要记录。未开始更改其他八个组件的算法，
更未关闭“九组件全面胜 C”的目标。
