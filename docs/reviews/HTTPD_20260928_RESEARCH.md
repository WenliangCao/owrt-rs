# httpd 2026-09-28 阶段结果与继续研究

**H1+H2 保留为已验证的阶段候选；研究继续，未部署。** 用户随后明确解除所有时间限制，要求继续深入算法研究寻找最有希望的最佳候选，原定停止决定撤销。下列冻结确认仍是有效证据，不追加或改写其样本。 必要功能门与正式构建门均已通过。小 JSON-RPC 单客户端/四并发主体 CPU 相对精确 C 分别降低 **27.47% / 7.16%**，相对正式 R89 降低 **12.05% / 18.27%**。静态收益保住。大回复四并发相对 C 仍有 **+130.41 µs/请求（+7.77%）主体 CPU** 和 **+597.76 µs（+2.48%）p99**；这两项没有被平均收益抵消。

本轮允许保留已披露的退步和未归因项，不要求每项胜出或全部达到统计显著。这取代 R95/R94 等旧材料冲突的性能收尾要求；功能、身份、恢复与生产隔离门保持有效。ubusd R136、netifd H10 不重开，未测九组件 Rust 组合。

## 为什么保留这两个小改动

先核对 [HTTP 合同](../contracts/httpd.md) 和 [R94](R94_HTTP_FASTPATH.md)。R94 `jsonrpc_c4` 470.2 vs C 462.8 µs 范围重叠，既未证明胜 C，也不能当作当前版本已证实的稳定退步。现有静态/停放代码保持不变。

匹配源码为 uhttpd `7b1bec45826bd78c8afc993435bdc0f1df2fe399`、ubus `24864e7840b3a02a9ef76284a373f6b2f00b8a9b`。确认接口与顺序仍为目标 lookup → session lookup/access →目标 invoke；不缓存权限、不减少鉴权，不改连接池容量或 deadline。

| 机制证据 | 原版当前源码 | H1 | H1+H2 |
|---|---:|---:|---:|
| 完整 RPC allocations | 49 | 41 | 29 |
| 完整 RPC requested bytes | 7748 | 5508 | 4386 |
| 目标 lookup 每请求4096B mmap/munmap | 约1对 | 消失 | 保留H1 |
| 合成32KiB回复转换 allocations | 66 | 66 | 1 |

H1 直接消费匹配的同步 DATA/STATUS 接收缓冲，去掉中间 Message 的 Vec。DATA 仍有独立所有权；乱序帧仍按序入队；FD、状态字段优先级、超时与断连语义不变。profile 把 mmap 定位到目标 lookup，而非 HTTP 正文收集或 JSON 解析。H1 的 Oracle 两侧各两窗，小回复主体 CPU 75–80→62–63 µs，四并发139→103–105 µs。

H2 直接从 Blob 字段序列化回复，复用原字符串/数值编码，省掉中间 JSON 树。每个 batch 元素仍写出并 flush，写失败立即停止后续 RPC。相对 H1，Oracle约31KiB回复主体 CPU 354–358→304–315 µs，四并发454–470→368–374 µs；小回复四并发有波动，全部原样保留。初始分段 profile 与构建并发，时间只作归因；分配计数、syscall trace 和正式未插桩对照严格分开。

每阶段只引入一个机制。缓存权限、移除连接池存活检查、重写事件循环、内存微调均未继续：已有两个低复杂度机制带来实际收益，没有依据扩大兼容风险。实机相对 R89 的改善也包含此前 R94/共享库工作，不能全部归于本轮。候选与未继续方向、逐轮数据及精确 hash 见 [索引](httpd-20260928-candidates.json)。
