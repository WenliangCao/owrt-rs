# HFO 开/关的排队定位计划

2026-10-18。读取用户指定 Fable 会话最后一段 CAKE 分析后，本轮只补排队定位，
不安装 CAKE、不改最终配置、不重启、不碰 Mac VPN。当前 SFO=1、HFO=1、WED=Y。
用户确认没有可用有线客户端，B 本轮不做，也不以路由器自身探针冒充有线客户端。

模型：新增等待可能在 AP/无线发送路径、Mac 自身或公网链路。关闭 HFO 后，
PPE→WDMA 的直接转发路径不再使用；WED 模块保持 Y，因此这是 HFO 路径干预，
不是 WED 模块开/关实验。若 HFO 绕过软件排队管理是主要原因，强预测为关 HFO
后 LAN 满载 TCP p95 相对空闲增量回到 20 ms 内，且公网超时归零。即使符合，
也只支持该转发路径相关，不能凭一次干预直接锁定某个 AQL/fq_codel 内部队列。

固定与前轮相同的 Apple HTTPS 端点、IPv4 地址、en0、HTTP/1.1、四并行连接，
每个状态各三轮下载、三轮上传，每轮20秒。使用同一 curl 探针，记录 TCP 建连、
HTTP 总耗时及1秒超时；每个方向10秒空闲参照。先临时 HFO=0 并 fw4 reload，
完成六窗后立即还原 HFO=1，再取相邻开启六窗；前轮开启数据只作额外参照。
不挑最好轮次、不替换不利轮次。WAN 的60秒租约作为固定输入，不调查上游归属。

报告逐轮和合并 p50/p95、超时及删失下界、吞吐、CPU与实际卸载状态；直接
匹配负载源端口和路由器连接记录，记录 utun 字节。分位数不能相减当作链路
分段时延；吞吐若不同，不能把相同四流设置描述成相同实际链路负载。

现场预检已确认三条 LAN 物理链路均未建立，客户端健康正常，当前完整47成员
配置备份已离机核验。限时守卫在独立会话运行：600秒或显式finish后恢复原
firewall字节/权限并最多三次有超时上限的fw4 reload；核对真实nft硬件标志。
没有接受临时关闭配置的路径，不使用 reboot、网络重启或Wi-Fi命令。
修改前后保护 network、wireless、modules.conf 与启动标识。恢复后做完整
客户端健康检查，再归档并移除临时材料。

本轮只裁决是否有 HFO 相关延迟证据，以及无有线对照时哪些队列位置仍不能区分。
最后保持当前 HFO+WED，不根据结果自动采用新配置。

## 用户接入有线后的补充

A 的相邻开启上传组期间，用户将同一 Mac 的扩展坞接入 LAN4，协商最终为
1 Gbps 全双工。原组第二窗与接线/链路切换重叠，整组三窗保留并标注，
另取完整的稳定开启上传三窗作为主比较，不只替换不利样本。此前开启下载
三窗在接线前已完成。无线负载及探针仍显式绑定 en0，新增记录有线字节。

B 在恢复后的 HFO=1/WED=Y 下做两组，各三轮20秒下载：Wi-Fi en0负载＋
有线en5探针；有线en5负载＋同一有线探针。两组固定端点、四连接、IPv4、
HTTP/1.1及探针实现。核对源地址、接口字节、连接记录、桥FDB和千兆链路。
不关闭Wi-Fi、不改默认服务顺序，也不操作VPN。Mac两接口共享主机，解释时
保留这一限制，不能把它说成独立的第二台客户端。最终路由器配置保持原样。
