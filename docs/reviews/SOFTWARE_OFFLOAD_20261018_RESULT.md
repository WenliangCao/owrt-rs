# 保留软件卸载，关闭 HFO 和 WED；下载一致性未能证实

**后续折中方案：** 用户随后要求测量 HFO 开、WED 关，利用有线硬件卸载并保留
Wi-Fi 软件路径。本文保留此前纯软件卸载阶段的结果；后续决定及现网状态见
[折中方案验收](HFO_WITHOUT_WED_20261018_RESULT.md)。

**同日后续关项：** WAN 抓包确认三次连接超时均先有出站 SYN，约 1.024 秒后
才收到 SYN-ACK，晚于探针期限；按约定归档为楼宇上游握手迟延／疑似丢包，
具体跳点未定位，结束研究。原始测量不改，见[闭合记录](WAN_SYN_20261018_CLOSEOUT.md)。

2026-10-18。按用户决定，最终配置选择软件流卸载开启、硬件流卸载关闭，
WED 恢复试验前设置。**本轮上传 CPU 成本与实验 A 的关闭组相容，LAN 延迟未见
恶化；但下载中位吞吐从 533.02 降至 161.93 Mbps，CPU 秒/GiB 从 18.520 升至
36.173，不能确认下载性能与 A 一致。** 额外一次同端点有线参照也只有
250.00 Mbps，下降原因尚未定位。用户说明公寓共享上游存在时段性网速波动，
接受这一现实条件，维持 SFO=1、HFO=0、WED=N 的决定。共享上游拥塞是合理解释，
本轮尚未证明；不能将这些下载差值直接归因于关闭 WED 或认定路由器性能退化。
本报告保留下载一致性未能证实的边界，不追加优化轮次。

## 配置选择与比较边界

用户选择放弃 HFO 的 CPU 收益，优先降低此前观察到的 Wi-Fi 端尾延迟，并恢复
WED 原设置。前轮 A 中，关闭 HFO 后 LAN 已完成 TCP p95 下载从 69.32 降至
33.18 ms、上传从 99.24 降至 50.76 ms；代价是路由器 CPU busy 中位数从
13.13%/8.08% 升至 60.69%/68.63%。此前启用 HFO+WED 时观察到约 30 MiB 的
可用内存差值，包含重启、缓存和缓冲池差异，不能视为精确 WED 分配量。

本轮 SFO=1、HFO=0，`modules.conf` 恢复原文件，执行一次计划内重启使 WED=N
生效。启动后的实际 flowtable 没有硬件标志。组件、固件和 CAKE 配置均未变。
比较对象 A 的配置是 SFO=1、HFO=0、**WED=Y**，因此本轮还包含 WED 状态变化，
不能把 A 的结论直接当作当前配置已经通过的证明。

两方向各三轮 20 秒，固定与 A 相同的 Apple HTTPS 端点及 IPv4 地址、HTTP/1.1、
四连接；负载和 curl 探针均绑定 Mac Wi-Fi en0。扩展坞 en5 保持连接，默认路由
走有线，使用源地址和连接记录验证实际测试路径。两方向各有 10 秒空闲参照。
所有正式窗口保留，没有替换低吞吐或超时窗口。

## 与实验 A 关闭组对照

CPU busy 为路由器两核总容量。CPU 秒/GiB 用正式负载内部采样的整机 CPU 速率
除以完整窗口的 HTTPS 应用数据速率，包含内核、现有服务和背景流量成本。
表中吞吐及 CPU 为三窗中位数，延迟为合并样本的 nearest-rank p95。

| 指标 | A 下载：WED=Y | 当前下载：WED=N | A 上传：WED=Y | 当前上传：WED=N |
| --- | ---: | ---: | ---: | ---: |
| 吞吐 Mbps | 533.02 | 161.93 | 722.00 | 674.02 |
| CPU busy | 60.69% | 39.38% | 68.63% | 61.69% |
| CPU 秒/GiB | 18.520 | 36.173 | 15.391 | 15.602 |
| LAN 已完成 TCP p95 ms | 33.181 | 26.364 | 50.762 | 32.073 |
| 公网已完成 TCP p95 ms | 52.910 | 60.198 | 90.350 | 67.154 |
| 公网超时/尝试 | 10/110 | 11/107 | 2/118 | 3/117 |
| 完整公网 TCP p95 ms | ≥1005.117 | ≥1005.002 | 99.176 | 96.215 |

下载吞吐下降 **69.62%**，CPU 秒/GiB 增加 **95.32%**。当前三窗吞吐范围
140.18–187.02 Mbps，与 A 的 515.66–573.04 Mbps 完全不重叠；CPU 秒/GiB
34.788–42.157，与 A 的 18.196–20.749 也完全不重叠。整机 CPU busy 较低
发生在交付吞吐大幅降低时，不能写成 CPU 成本改善，也不能将 CPU/GiB 差值
直接解释为每包处理成本增加。

上传 CPU 秒/GiB 中位数仅增加 1.38%，落在 A 的三窗范围内；吞吐下降 6.65%，
两侧范围重叠，当前中位数略低于 A 的最低窗。两方向 LAN 单窗 p95 的新中位数
均落在 A 范围内，240 次 LAN 负载探针全部成功。不过下载实际压力明显降低，
不能称为相同交付速率下的延迟改善，有限三窗也不能证明统计等价。

## 公网超时仍未解决

前轮两组有线探针分别出现 5/115、7/113 次约一秒超时，即此前所说的约 5%。
本轮 Wi-Fi 下载为 **11/107（10.28%）**，上传为 **3/117（2.56%）**；额外有线
参照为 **2/37（5.41%）**。保留各方向的实际分母，不将它们强行归为固定 5%。

当前没有非超时类的公网失败。下载和有线参照的完整请求 p95 已落入超时区，
只能给下界；成功连接的几十毫秒 p95 不能代表它。这项问题仍未定位，关闭
HFO/WED 没有证明修复它，也没有证据将其全部归因于上游缓冲膨胀。本轮未加入 CAKE。
