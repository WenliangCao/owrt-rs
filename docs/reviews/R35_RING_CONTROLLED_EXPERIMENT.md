# R35：ring 跨宿主可重复构建的受控实验指导

本轮仅审阅仓库中的 R34 取证报告及诊断脚本，未重新下载或独立比对两台宿主的二进制证据，也未执行远端实验。本文交给 Opus 实施；不修改发布配方或设备。

## 判断

值得做下一对诊断构建。已经找到一个具体、可干预的差异来源，实验成本有限；但目前还不能承诺映射路径就能修好最终 ELF。

这是发布产物可核验性问题，应安排解决；现有差异本身不证明 TLS、运行性能或稳定性有缺陷。不要因此换掉 ring 或关闭汇编优化。

R34 报告中几处结论需要收紧：

- 两次同宿主 clean 构建相同，只证明这两次相同，不是所有条件下确定性的证明。
- 若干纯 Rust rlib 相同，只证明这些产物相同；zeroize 尚有差异，不能泛称该 target 的 Rust codegen 已证明宿主无关。
- 对象文件名相同排除了“本次由对象文件名不同造成差异”的假设，不排除路径通过其他输入进入对象。
- mem.o 大小相差 104 字节，证明不只是直接替换那一处等长字符串；尚不能证明存在独立于路径的第二个根因。
- 最终 ELF 已无 debug 段，说明不能把最终差异直接归为残留 DWARF 字符串。还需定位实际代码、重定位、布局及上游输入差异；差异字节数本身不能证明修改了这么多代码逻辑，也不能数出独立根因。
- 建议将 R34 的“路径不是唯一原因”改成“已定位一处路径差异，最终 ELF 差异尚未解释”。

## 先修取证，不改变构建语义

以下是对 `tools/repro_diag.sh` 的修改指导，不是发布配方修改：

1. `ringout` 是 `.../build/ring-<hash>/out`，build-script 输出应取 `$(dirname "$ringout")/output`。现有 `/../output` 多退了一层，并通过 `|| true` 静默遗漏。关键证据不存在应显式失败或标为缺失。若找到多个 ring out，分别收集并标明用途，不任取第一个。
2. `cargo rustc -V` 不是查询实际 rustc 版本的有效方式。当前 fallback 只能查询 PATH 中的 rustc，不能证明 Cargo 使用了它。记录实际编译命令、解析后的编译器路径和该编译器的 `-vV`；同时记录相关 Cargo 配置及编译器覆盖变量，避免泄露完整环境。
3. 当前复制出的 `httpd-rs.unstripped` 已按 release 配置 strip；改用准确名称并记录实际 section 列表。第一轮保留现有 profile，不为名字额外关闭 strip。
4. 保存源码 revision/工作区差异、lockfile 哈希、SDK 校验值及实际 CC/AR/LD 身份。构建主机通过 QEMU 执行 SDK 编译器时，记录 SDK 工具文件哈希、调用方式及 QEMU 版本。不要仅凭宿主架构不同就断言用了不同的 GCC 后端。
5. 记录实际 C/汇编命令，而不仅是设置的环境变量；必要时启用 cc crate 的命令诊断并确认其没有改变实际编译参数。保留 build-script output、链接参数及输入顺序。
6. 脚本会删除原 diag 和固定源码目录。先把基线完整归档到构建目录之外；同一宿主不要并发运行。A0/A1 使用相同物理构建路径，归档路径可以不同，避免为区分实验而引入新的 target-dir 路径变量。

## E0：先分析已有产物，不必先重编

将现有 CI/构建主机基线命名为 A0/B0，保存完整哈希清单。缺失证据无法恢复时，再补相应基线；不能把新增参数下的产物当成原基线。

对 mem.o：比较 ELF header、section header、每段的 offset/size/alignment、符号及字符串表、重定位和文件空隙。把多出的 104 字节落实到具体文件区间；“各段大小相同”还不是定位结果。分别记录可装载内容和调试元数据的差异。

对 zeroize rlib：先列出 archive 成员名称、顺序和头信息，再逐成员比哈希。判断分歧位于 `.rmeta`、本机对象、嵌入 bitcode 还是 archive 元数据；然后比较相应 rustc 命令的 features、metadata、target、优化/LTO 参数和路径映射。没有 build.rs 不代表产物不受构建输入影响。暂不把整个 rlib 的不同直接叫作机器码不同。

## E1：只增加一个构建因素，两台宿主各一次

在保持每台宿主原有源码、工具链、SDK、构建路径、profile、链接参数及其他环境不变的前提下，仅给目标 CC 增加 CARGO_HOME 路径映射：

```text
-ffile-prefix-map=<该宿主实际 CARGO_HOME>=/cargo
```

通过目标专用 CFLAGS 传入，保留原有有效参数；先核对 cc crate 的实际变量选择和最终命令，避免覆盖现有 flags。确认 C 文件和预生成 `.S` 都收到参数，并检查对象中的实际映射效果。

源码已经固定在同一 `/tmp/owrt-build/owrt-httpd`，这一轮不要顺手再加源码路径映射、改 OUT_DIR、改 strip/LTO、换 linker 或换容器。若发现其他路径泄漏，记录后单独处理。

保持 clean 构建，得到 A1/B1。保存四组比较：A0↔B0、A0↔A1、B0↔B1、A1↔B1。这样同时知道映射在每台机器改变了什么、跨宿主还剩什么。

比较顺序：ring `.o` → `.a` 成员及 archive 元数据 → 相关 rlib 成员 → 最终 ELF 的 section/符号/重定位/反汇编 → APK。不要只报告“整个文件不同”或逐字节差异总数。zeroize 不直接使用目标 CC；如果仅改 CC 映射后，它在同宿主也变化，应检查是否混入了其他变量或原本存在非确定性。

## 结果如何决定下一步

| 结果 | 下一步 |
| --- | --- |
| ring 对象和最终 ELF 都一致 | 路径映射是本次样本上的有效修复；转正式配方验证，不直接宣布发布闭环。 |
| ring 对象仍不同 | 按 E0 定位剩余字节及输入。先确定映射是否实际生效，别叠加一批猜测性 flags。 |
| ring 对象相同、archive 不同 | 检查成员顺序和 archive 元数据。 |
| ring 对象/archive 相同、最终 ELF 不同 | 继续沿 zeroize、其他链接输入、LTO 和链接布局定位；只能说仍有未解释分歧，不能先断言是另一个独立根因。 |
| 仅中间调试/元数据不同、最终 ELF 相同 | 按最终发布产物目标验收并记录中间差异；无须为所有中间文件强求一致而扩大修改。 |

若最后需要额外链接 map 或未 strip 产物，在两台宿主同步开启独立诊断轮次，并标清其与发布参数的区别。

验收修复时，使用正式发布流程重新完成同宿主两次 clean、跨宿主构建，并比较最终 APK 哈希；执行现有相关回归。保留第一处分歧、最小干预及结果的证据链。诊断通过之前不改发布结论，不接触路由器。
