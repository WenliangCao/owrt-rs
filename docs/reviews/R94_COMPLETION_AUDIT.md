# 九组件攻坚计划成果审计

审计日期：2026-09-20。审计基线：`9db9575ef2879d0acdbe3233f3af1c3f77db9f93`。

**结论：有实质优化成果，但“九组件全部完成”不成立。** 除了性能与覆盖面的尾项，
本次还复现了两个正式打包阻断、一个 reload-config 超时/取消回归，以及一个 UCI 短读丢数据问题。
报告中还存在遗漏尾延迟、混淆 C/R89 比较基线、把阶段候选当成最终代码验收的问题。
这能证明验收结论过宽，不能据此判断作者是否有意隐瞒。

审计仅查看仓库、已有实机数据，并在 Oracle Linux 构建机的临时目录做定向复现；
没有连接、修改、重启或部署物理路由器，没有修改组件实现或替作者补修。

## 1. 先处理的实际缺陷

### A01 / P1：reload-config 的正式包缺少新增的 UCI 源码依赖

- `98c827b` 给 [Cargo.toml](../../components/reload-config/Cargo.toml) 增加了
  `owrt-uci = { path = "../uci" }`。
- [正式 Makefile](../../packaging/openwrt/owrt-reload-config/Makefile) 第 33–57 行仍只复制
  reload-config 自身的 Cargo 文件和 `src/*.rs`，在固定目录下构建时没有相邻 `uci/Cargo.toml`。
- **复现：** 在 Oracle 上按该 Prepare 布局建立独立临时目录，使用相同 SDK/musl 工具链、
  release/locked/offline 构建，退出 **101**，报 `failed to get owrt-uci` / `No such file or directory`。
  仅在临时目录补上 UCI 依赖，构建退出 **0**。
- 私有 `r94-rcb/build.sh` 会复制 `reload-config uci ubus`，因此其成功不能证明正式包可构建。
- **收尾条件：** 修正正式 recipe 的依赖目录布局，跑干净的正式 APK/CI 构建及产物来源验证。

### A02 / P1：UCI 的正式包漏复制必需的 build.rs

- `14c02a6` 让 CLI 采用 `#![no_main]`，并新增
  [build.rs](../../components/uci/build.rs)，为 musl 链接补 `-Wl,-u,getauxval`。
- [正式 Makefile](../../packaging/openwrt/owrt-uci/Makefile) 第 36–43 行只复制 Cargo 文件、
  `src/*.rs`、`src/bin/*.rs`，没有复制 `build.rs`。
- **复现：** 相同 SDK 工具链按正式 Prepare 布局构建，退出 **101**，
  `undefined reference to getauxval`；只补 `build.rs` 后退出 **0**。
- **收尾条件：** 将 build.rs 纳入正式构建输入，并验证干净构建及打包后的 ELF。

以上两项复现的是正式 recipe 的源码布局和对应编译步骤，没有声称执行了完整 SDK make 或 CI workflow。
它们已经足以否定“诊断构建通过，所以正式发布也没问题”。

### A03 / P1：reload-config 进程内规范化丢了超时和取消边界

- [engine.rs](../../components/reload-config/src/engine.rs) 第 108–112 行只在包与包之间检查取消，
  随后同步进入 `show::tuple`；[uci/file.rs](../../components/uci/src/file.rs) 第 42 行取得阻塞共享锁。
  UCI 的锁等待既不接收 `Settings.timeout`，也不检查取消标志。
- **实测对象就是报告验收的静态候选 `e22deec6…`。** 在合成配置 `alpha` 上持有独占锁，
  启动 `--timeout-ms 100 --trace-stderr`：500 ms 后仍存活；发 SIGTERM，再等 500 ms 仍存活，
  最终由探针 SIGKILL 清理。没有 trace，也没有建立基线。
- 同样输入下，改动前 `1f0bb789…` 约 **108 ms** 返回，记录 `normalization: timeout`。
  旧版会按既有策略继续本轮并写基线；这里验证的是它有时间边界，并非赞成其全部失败语义。
- R94 把“uci shim 睡眠”的 f09 改成“shim 未被调用即通过”，没有增加进程内文件锁阻塞的替代用例。
  不再创建子进程，并不意味着原来隔离的阻塞源消失了。
- **收尾条件：** 给实际配置/增量文件加载保留有界、可取消的等待；补配置文件锁及 delta 文件锁的故障门，
  明确取消时退出码、基线与后续投递行为。

### A04 / P2：UCI 将一次正数短读当成 EOF，静默丢掉配置尾部

- 新增的 [file.rs](../../components/uci/src/file.rs) 第 53–77 行在
  `filled < data.len()` 时立即结束读取。这里没有确认文件内容已经读完。
- **Oracle 故障注入复现：** 当前源码的原生 GNU 构建，对一个 60 字节普通配置文件，
  仅把目标文件每次 `read` 限成最多 16 字节。无注入时输出 section 和两个 option；
  注入后只输出 `alpha.s=test`，**exit 0、stderr 为空**。
- 这是受控短读反例，**不是声称路由器的 overlay 已发生短读或数据丢失**。
  旧代码使用持续读取的 BufReader；新假设处于共享库，当前 rpcd/netifd/fw4/reload-config 都会链接它。
- **收尾条件：** 在保留常规文件快路径的同时正确处理短读，补分段读取与提交重读的回归；
  不能用“常规负载 1,000 例无差异”替代这条错误路径。

上述复现的输出、二进制身份、38 个相关源码文件与当前工作树一致的核对结果，见
[定向复现证据](r94-audit-probes.json)。原始探针脚本和输出留在 ignored
`private/r94/audit-20260920/`，没有把设备备份或配置写入 Git。

## 2. “性能全胜”遗漏了哪些结果

[计划](../COMPONENT_PLAN.md) 的准则要求每条负载分别报告 CPU、平均/尾延迟和内存；
标准流程允许对 **R89** 的差值在四轮范围内重叠且已解释。
因此，解释清楚的 R89 持平可以是允许的取舍；它不等于“优于”，也不能用来豁免对 C 的全部胜出要求。
四轮最小–最大范围重叠本身也不是统计等价检验。

本次复算九组最终阶段候选的 **74 条负载、888 个观测**，没有把早期被替换候选混入。
逐项数据和身份见 [机器可读复核](r94-audit-metrics.json)，重算工具为
[r94_audit_metrics.py](../../tools/r94_audit_metrics.py)。下表延迟单位为 µs，数字是四轮指标的中位数。
另用仓库现有分析器从原始采集目录重新派生九组结果，身份与采集检查通过，汇总与已保存 JSON 全部相同，
见 [原始数据重算结果](r94-audit-rederivation.json)。问题在结论的覆盖范围与表述，不是这些汇总数字被本次推翻。

| 组件/负载 | 被略去或弱化的指标 | 基线 → R94 | 四轮范围及结论 |
|---|---|---:|---|
| ubusd / lookup_all_128 | **p50 对 C +2.56%** | 1380.54 → 1415.85 | C 1361.72–1392.81，R94 1402.73–1428.28，**不重叠**。平均延迟改善并未覆盖典型延迟退步 |
| netifd / wireless_status | **p95 对 R89 +11.55%** | 99.56 → 111.07 | R89 98.03–101.80，R94 102.95–141.96，**不重叠** |
| netifd / wireless_status | **p99 对 R89 +4.41%** | 203.28 → 212.24 | R89 199.59–207.44，R94 208.36–221.82，**不重叠**；不能只解释平均延迟 +0.3% |
| httpd / jsonrpc_c4 | CPU 对 C +1.61% | 462.8 → 470.2 | 范围重叠；未证明严格胜出，不能同时写“16 条 CPU 全低于 C” |
| rpcd / uci_configs | p95 对 C +3.89% | 见 JSON | 范围重叠，是需要披露的未胜出项，不据此断言稳定退步 |
| rpcd / session_access_64 | p95 / p99 对 C +0.44% / +0.74% | 见 JSON | 范围重叠 |
| procd / service_list_128_c4 | p99 对 C +2.57% | 见 JSON | 范围重叠 |
| netifd / device_status_c4、interface_named_32 | p99 对 C +1.32% / +0.61% | 见 JSON | 范围重叠 |

对 R89，p95/p99 中位数更高的负载数分别为：httpd **3/2**、rpcd **3/4**、procd **2/3**、
ubusd **2/3**、netifd **2/3**。除上述 netifd 两项外，这些较高尾指标的范围都重叠；
应作为持平/待辨别项披露，而不是一概算作实锤性能回归。完整名单在 JSON 中。

### 内存没有随着 CPU 一起全部下降

下表来自负载结束后的 resident 记录，是四轮中位数，单位 KiB；**不是每条 lane 的峰值内存**。

| 组件 | VmRSS：R89 → R94 | RssAnon：R89 → R94 | 需要收尾的说明 |
|---|---:|---:|---|
| logd | 504 → 516（+12） | 174 → 120（−54） | 匿名内存改善成立；多流 pipe 的内核缓冲不能从 daemon RSS 推断 |
| httpd | 996 → 1134（+138） | 128 → 138（+10） | 报告已披露；文件页解释不能抹掉占用，也不能外推为整机同量增幅 |
| rpcd | 1178 → 1264（+86） | 122 → 140（+18） | 总表没有展开，需补资源取舍 |
| procd | 984 → 932（−52） | 196 → 208（+12） | RSS 降、匿名页升；fd 7 → 8 是常开 meminfo 的固定成本 |
| ubusd | 620 → 628（+8） | 164 → 172（+8） | 需给新增读前缓冲的客户端规模边界 |
| netifd | 1208 → 1352（+144） | 284 → 364（+80） | 明显的常驻缓冲换 CPU；fd 10 → 11，需明确接受预算 |

fw4、uci、reload-config 这三组结果的 `resident` 为空，不能据此给短命进程的峰值内存验收打勾。
它们分别存在整份配置/输出缓冲与配置缓存等改动，应该提供合适的峰值测量。
各组件在独立窗口采样，候选也有 `/tmp` 与原版映射类型差异，**不能把表内差值相加当整机增量**。

## 3. 九个组件逐项收尾清单

以下“可选空间”不当作未修 bug，也不强迫为追求百分之零点几而增加复杂度。
所有组件还共同受下一节的最终源码、正式构建与组合验证缺口约束。

| 组件 | 已有成果可接受的范围 | 仍须处理/补证 | 可保留的优化空间 |
|---|---|---|---|
| **logd** | 两条实机固定输入的 CPU、平均/p95/p99 延迟、匿名内存均改善 | 实机未覆盖多读者 follow、超长 kmsg、真实日志；这些只在 Oracle 覆盖。最终共享 ubus 版本需重新验收；补多流资源边界 | 不要求无限无损慢读；已声明的队列限额是合理边界 |
| **httpd** | 十条静态紧密负载和五档停放明显改善 | JSON-RPC c4 尚未证明 CPU 胜 C；六条 1 MiB/CGI/JSON-RPC 对 R89 持平；RSS 增量与尾指标需并列；明文停放结果不代表 TLS/真实 RTT 终验 | bridge/ubus 路径、CGI/大文件可以另开优化项；维持 50 ms 阈值本身不是 bug |
| **rpcd** | 会话/ACL 优化成立 | 修正 C/R89 基线误写；UCI 64 段两条 CPU +0.75%/+2.10% 仍只支持范围内持平；披露尾指标和 +18 KiB 匿名页；补最终 UCI/ubus 依赖版本回归 | UCI 序列化还有成本，但不是已经证明的稳定退步 |
| **procd** | system_info 有明显收益 | list_128_c4 平均延迟 +1.7% 是重叠项；补尾指标、固定 fd/匿名页成本；设备矩阵只跑 `-S`，空 init/rc，不等于 R94 的 PID 1 冷启动验收 | 编码缓存未采用有合理复杂度理由，不应仅因此判未完成 |
| **ubusd** | 接收及全量 lookup CPU 降幅成立 | **解决/如实接受 lookup_all_128 对 C 的 p50 反例**；补尾指标和客户端数量下的资源曲线 | >16 KiB 或有 monitor 的列表仍逐对象，invoke 仍逐帧 sendmsg；范围外路径应写明 |
| **netifd** | netlink 计数器与 dump CPU 改善成立 | **wireless_status 尾延迟两项不重叠地劣于 R89**；+80 KiB 匿名页需预算；真实无线配置性能未测，当前无线夹具为空 `{}`；最终 UCI 依赖需重验 | wireless 的 JSON→blob 路径仍在，空配置结果不能证明无线管理全面优化 |
| **fw4** | print/check 两条已测负载 CPU、平均/p50/p95/p99 均优于两基线 | 最终 UCI 库更新后需重验；缺短命进程峰值内存；修正 check CPU 归属说明；其他动作未由此性能矩阵覆盖 | 约 1,140 次分配、ubus→JSON、reload-sets 仍调用 nft；删除自定义分配器是合理取舍 |
| **uci** | 三条阶段候选性能指标胜出 | **A02 正式构建阻断、A04 短读丢尾**；后续 `71a9e2e` 已改变 CLI，最终五门跑的是 `2b2e8090…`，性能表仍是 `c3b51560…`；补最终身份和峰值内存 | 不要求继续消除每一次分配 |
| **reload-config** | unchanged_config 的大幅收益成立 | **A01 正式构建阻断、A03 锁等待失去边界**；实机只测无变化路径，没有实际变更投递的性能/资源数据；新加载路径需故障门 | 变更时仍逐包 `ubus call`；可以保留，但不能再无条件宣称“一轮零子进程” |

## 4. 整体尚未闭合的验收

1. **各组件打勾时的源码并不一致。** logd/httpd 测完后，`f1e1f19` 又改了共享 ubus 接收，
   `5ce35b5` 改了 blob 编码；rpcd/netifd/fw4 测完后，`14c02a6` 又改了共享 UCI 读取，
   `71a9e2e` 又移动 show 并改了 UCI CLI。依赖单测或某个组件的门，不能代表所有依赖方的最终组合回归。
   未发现绑定最终 HEAD 全九组件的完整验收清单。应冻结一个源码快照，重建九组件，逐项核对哪些既有证据仍有效，
   对受影响方重跑完整合同门和性能验收。
2. **诊断构建不是正式发布。** R94 各报告明确写了 Oracle SDK 诊断构建、未部署；
   [决策 0018](../decisions/0018-canonical-build-host-ci.md) 固定 canonical builder 为 CI。
   A01/A02 说明这不是形式问题。需要正式 artifact 身份、干净构建、离线包/镜像与回退验证。
3. **单组件 namespace 结果不是九组件整栈结果。** R94 窗口的生产栈为 C，依赖多数固定为 C/R92，
   没有 R94 最终组合的冷启动、mixed 负载、实际 Wi-Fi/IPv6/服务恢复与整机内存证据。
   这些是“可发布/部署完成”的缺口，不应反过来否认已经证明的局部收益。
   物理部署/重启仍需另行明确授权及恢复门；本次审计不执行。
4. **三侧与四侧要求未对齐。** 计划标准流程写实机 C/R89/source05/候选四侧，最终报告普遍是
   C/R89/候选三侧。三侧足够直接回答对 C/R89 的比较，但没有严格执行书面四侧流程。
   应明确是否接受省略 source05，不能声称原流程全部完成。
5. **内存和尾延迟需要进入判定。** 不能再只靠平均延迟+CPU给组件打勾；
   补齐已经采到却没解释的分位数/内存，再决定哪些是需修复的回归、哪些是明确接受的取舍。

## 5. 这些“开放问题”实际已关闭，别重新列为 bug

计划的历史缺陷段存在过时信息。对照
[R92 逐项处置](../../reports/ax3000t-stock-openwrt-25.12.5/R92_COVERAGE.md) 和当前合同：

- **UCI U1 非 UTF-8 rename：** R92 已按“原子拒绝”合同关闭，计划仍写“开放”过时。
- **reload-config F2 4096 上限待写合同：** [合同 §11](../contracts/config-change-dispatch.md) 已写，且已有边界测试。
- **logd 非 UTF-8 有损转换：** 那是 R88 的中间状态；R92 已改成保留原始字节。应更新描述。
- README 的顶部现状仍指向 R92 在运行；R94 记录则是回退到 C 后的诊断测试。
  这说明现状说明过时，不是本次已核实今天路由器实际运行哪一栈。

建议收尾顺序：先修 **A01–A04** 并补针对性门；再冻结最终九组件来源并做正式构建；
随后处理上表性能反例、披露资源取舍并完成受影响方验收；最后单列发布/部署状态。
计划勾选应区分“局部优化完成”“最终候选验收完成”“正式发布/部署完成”，避免再次混为一个 ✅。
