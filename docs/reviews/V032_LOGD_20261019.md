# v0.3.2 logd：ID 回绕与日志容量

2026-10-19。ID 回绕修复完成：旧 Rust 四轮均有 10 个窗口与 C 不同，修后四轮
20 个窗口全部一致；正常对照始终一致。Oracle logd 完整测试 **20 passed / 0 failed**。
尚未部署；2 MiB 容量及全量读取的四轮 C/Rust 对照也已完成。

## ID 回绕

精确参考为 ubox `6f78fa496bf36c55864a41e353df7d13f04b1077` 的 `log/syslog.c`
（SHA256 `da58ab3c4c384942b42d00c1778c1ed68f914cc7d3957f8abdb2715c2fb30da9`）。
C 按物理顺序逐条筛选 `id >= min`；原 Rust 从 `current_id - retained_count` 推导
一个连续后缀，ID 回到 0 时把仍在环内的高 ID 历史跳过。修复改为对实际记录 ID
逐条过滤，不调整记录保存、淘汰或 wire 格式。

`tools/logd_id_wrap_check.py` 从精确 C 源码提取 `log_next`/`log_list`，沿用先前
审查的近回绕种子并加入正常、回绕两侧、正/负 count 对照。例如
`[MAX-1, MAX, 0, 1]`、`current_id=2`、`count=1` 时，C 与修后均返回
`[MAX-1, MAX, 1]`，不能以遇到第一条匹配记录后全部保留代替逐条过滤。
两项单测覆盖回绕历史及其最终被物理淘汰后恢复普通窗口。

这是注入近回绕状态的模型复现，没有实际写入 40 亿条记录。C 的 `current_id` 是
signed int；本轮所有枚举状态的 current_id 均非负，不执行 C signed overflow，
不宣称修复其他高位计数或算术溢出边界。

原始证据在 `oracle:/home/ubuntu/v032-logd-20261019/`：
`wrap-red-4x/`、`wrap-green-final-4x/`、`logd-tests-id-wrap-fixed.log`。
早期 harness 的局部存储警告、SSH PATH 缺 rustc 和新增单测的借用编译错误均保留，
未计入产品红例。所有编译、测试在 Oracle，使用独立 target 目录。

## 容量与全量读取

只读 logread 快照保留 1267 条，覆盖本地时间 20:15:09–22:23:21。完整
21:00–22:00 小时共 619 条、消息内容 42127 B；按真实 arena 开销
`32 + align4(message_bytes + 1)` 合计 **63568 B**，不是显示文本的 66303 B。
原始日志只存 ignored `private/v032-logd-20261019/` 和 Oracle 同任务 private 目录。

选择 **2048 KiB**。受控重放包含该完整小时的 24 份、实际设备 dmesg 前 60 秒
266 条、此前精确镜像 native_boot_check 的用户态启动 48 条及标记，共 15173 条，
实际 ring 占用 **1557884 B**、stream 编码 **2468264 B**。原设备用户态开机窗口
已被覆盖，因此明确使用离线启动夹具；这不是连续 24 小时物理观察。

旧 Rust 的固定 1 MiB stream 上限四轮均拒绝全量读取，原版 logread 等待至 5 秒
超时，输出 0 条；同容量 C 四轮都完整读取。修复按配置 arena 的三倍确定单流
上限，aggregate 上限取旧 4 MiB 与该上限的大者。最短记录是 36 B arena、96 B
frame，长消息的比率更低，因此足以容纳任何完整历史；小 ring 保留原限制。
慢读者仍受单流/总量限制和最多 64 个客户端约束，没有移除资源上界。

同一输入的 1024 KiB 容量对照四轮 C/Rust 均只保留 10205 条，启动标记全部丢失，
见 `capacity-1024-control-4x/result.json`。这直接支持本轮选择 2048 KiB。

耗时包含启动原版 logread 与管道传输，RSS 读数分辨率为 4 KiB；不把 Oracle
的耗时差异宣传为路由器性能收益。额外最短消息案例明确到达大于 4 MiB 的编码
积压边界。完整 logd 单测 21/21 通过，包括完整 ring 最坏编码开销与既有慢读者恢复。

独立 stream 故障回归 **5/5** 通过（`stream-recovery-capacity.json`）：读者隔离、
总线重连/FD 回收、重试间隔、64 流限制与容量回收、总积压限制。2 MiB ring 的
总积压上限已从 4 MiB 变为 6 MiB，因此压力输入从 850 增为 1100 条，确保仍实际
触发淘汰；健康读者完整收到 1100 条，2 个慢读者被淘汰。工具本地/远端 SHA256
一致，结束后没有遗留测试进程。

可重放工具 `tools/logd_capacity_check.py` 在私有 mount namespace/chroot 中使用
原版 ubusd、logread 与 C logd；启动前把 `/proc/kmsg` 遮盖为空普通文件，未读取真实
内核日志。原始记录：同一 Oracle 目录 `capacity-red-normalized-4x/`、
`capacity-green-4x/`、`capacity-short-green-4x/`、`logd-tests-capacity.log`，以及
private 内语料和摘要。候选 main.rs/ring.rs/tool 的本地、远端 SHA256 全部相同；
musl ELF 为 `3866cab2f04dbd8bc278a1b9cd951779f852bc670bef14e66fd4437c6fc9b937`。
此前夹具的 rootfs 权限、启动 readiness、时间戳/尾空白规范化失败均保留，未算作产品红例。

容量成本模型仍是 arena、每条 4 B 索引与临时编码积压。下一步是迁移旧 UCI 值，
并在最终精确镜像和获准部署后核对实际开机窗口、设备 RSS；当前结果不能替代它们。
