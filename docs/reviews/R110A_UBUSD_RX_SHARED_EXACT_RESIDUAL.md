# R110-A：事件循环共享接收暂存与精确残帧

R109 是当前接受的 Rust 基线：源代码提交 `8e716db`，规范 release ELF
`1dfb317c4baa50b94b17cffd21a098322be0591174f1f50c067dc5fc00315259`。
生产路由器继续运行镜像匹配的 C `ubusd`，本候选只在隔离窗口验证，不安装、不替换生产进程。

## 为什么重新做这一项

路由器只读盘点于 2026-09-21T21:26:50Z 完成：`/var/run/ubus/ubus.sock`
有 17 条长连接，C `ubusd` 的 `RssAnon` 为 160 KiB、`VmData` 为 144 KiB。
这证明每连接固定 4 KiB 接收缓冲不是纯粹的 64 连接合成场景，但实际收益仍须在路由器上测量。
盘点原文保存在被 Git 忽略的 `private/r110-rx-stack/inventory/router-long-connections.txt`，
SHA-256 为 `dca1382c682c2c23aa0f0b8ad16524bb8a6dffddd08e805fcebda921a3e943c7`。

R105 的共享 spare 候选已经证明“内存下降、活跃 CPU 上升”，R106–R108 的阈值和内联变体也没有解决这个冲突。
R110-A 改变所有权边界，而不是再换一个条件分支：共享缓冲只在一次事件循环服务调用期间存在，
客户端只在读不完整时留下精确大小的残帧 Vec；借用派发另行做 R110-B。

## 冻结假设

1. 事件循环在 `while` 外只创建一个 `Vec<u8>`，长度为 `RX_SIZE=4096`。不得在
   `service_client` 的栈帧或每条消息中创建 4 KiB 暂存区。
2. `Client` 的接收状态不再长期持有完整 4096 字节容量。服务一个客户端时，暂存区可以
   暂时归它使用；该服务调用返回前，完整帧已经处理完，或剩余字节被复制到精确大小 Vec，
   暂存区归还事件循环。
3. 一次服务调用内的合并帧继续使用同一个共享缓冲，不在每帧之间复制。只有服务调用结束时
   才压缩未完成残帧；因此热路径不引入 R105 的每次调用交换/检查组合。
4. `LargeFrame` 保持独立拥有型存储。超过 `RX_SIZE` 的帧、跨 readiness 的大帧和其 FD
   所有权不借用共享缓冲。
5. `rx_fds` 的标记在残帧压缩时减去残帧起点；完整帧消费时沿用现有边界规则。任何
   `SCM_RIGHTS` 转移错误都直接拒绝候选。
6. `InMsg`、`Server::receive`、排队 LOOKUP 和发送 API 在 R110-A 保持拥有型语义不变；
   这一阶段不测借用派发收益。

Linux `recvmsg` 在非阻塞 UNIX socket 上可能只返回当前可用字节，并通过 ancillary data
携带 `SCM_RIGHTS`；因此残帧和 FD 标记必须一起迁移，不能只释放字节缓冲。实现依据
[recvmsg(2)](https://www.man7.org/linux/man-pages/man2/recvmsg.2.html) 和
[unix(7)](https://man7.org/linux/man-pages/man7/unix.7.html) 的接口语义。

## 实现边界

先新增共享暂存读取路径并由事件循环调用。读取完整帧时仍构造当前的拥有型 `InMsg`；
如果一轮中还有完整合并帧，暂存区留在当前客户端直到它们全部派发；返回 `None` 时：

- 无残帧：把 4096 字节 Vec 归还事件循环；
- 有残帧：将 `[rx_start, rx_end)` 复制成精确长度 Vec，重排 FD 标记，再归还 4096 字节 Vec；
- `LargeFrame` 活跃：共享暂存区直接归还，继续由 `LargeFrame` 接收后续字节。

不得修改 wire bytes、消息顺序、FD 边界、半关闭、背压、监控和错误关闭行为。

## 预检与物理判定

代码提交前完成主机单测和 clippy，覆盖：单帧、合并帧、每种残帧边界、跨事件循环的残帧、
大帧、`SCM_RIGHTS` 在首帧/后续帧/残帧上的转移、EAGAIN、背压、EOF、畸形长度和
客户端间共享缓冲复用。随后在路由器以 C 生产状态完成相同的功能/恢复/清理门。

性能窗口只比较 R110-A 与 R109，采用既有物理路由器配对方法：daemon 固定 CPU、
C 调用者固定另一 CPU，十个独立窗口，ABBA/BAAB，`user_1_1`、`user_8_1`、`user_1_0`
三条 lane。每个窗口结束都必须验证候选未进入生产、同一 boot/config/mount、健康和清理。
R89/C 只作为已保存的上下文，不把旧窗口与本轮样本池化。

内存主判定预先写死：64 个持有连接的 `RssAnon` 增长除以 64，必须不超过 R89
实测 `36 KiB / 64` 加 `0.6 KiB`，即 `1.1625 KiB/连接`；同时保存 VmRSS/VmData，
但不把它们冒充 PSS。CPU 只接受“不是三条 lane 全部相对 R109 同号上升”；任何约 1–2%
的上升先用可用的硬件计数器/指令与分支统计定位，禁止继续猜测控制流变体。

功能失败、清理失败、内存门失败或三条 CPU lane 全部上升，均拒绝 R110-A 并保留证据。
R110-B（借用 `receive`、直接借用回复、仅 LOOKUP 停车时拥有）只有 R110-A 通过后才单独冻结，
不与本候选合并。若 R110-A 通过而 R110-B 的 CPU 效应无法分辨，则保留 A 的内存改进，
不再把接收路径的剩余差距包装成语言极限。
