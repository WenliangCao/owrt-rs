# R135：实机定位到 ADD 回复合并的尾部代价

四个预冻结窗口已完成，C/R134/drain/separate ADD × 两种 caller 亲和性 × 三条负载，共 96 case。每 case 10,000 周期。四窗所有健康、身份、归档、功能和清理断言通过；九个生产组件仍为 C，实验文件和进程均已清理。

这一步是诊断，不替代 R134 的既有八对结论，也不构成正式晋级。以下为相同窗口的变化百分比中位数。

| 相对 R134 的变化 | reg1 mean | reg1 p95 | reg1 p99 | reg1 CPU |
| --- | ---: | ---: | ---: | ---: |
| separate ADD，caller CPU 0 | -2.76%（4/4 低） | -30.83%（4/4 低） | -14.06%（4/4 低） | +7.21%（4/4 高） |
| separate ADD，caller 允许 0–1 | -1.52%（3/4 低） | -25.58%（4/4 低） | -12.67%（3/4 低） | +6.15%（4/4 高） |

相应 p50 增加 2.12%/3.10%，不能省略这个代价。注册 16 和对象事件也有改善方向，但并非所有窗口一致：固定 caller 时，separate ADD 的 event_1 mean +1.43%、p99 +3.65%，各两窗退步；允许 0–1 时该负载 mean -1.39%、p99 -5.13%，仍各两窗退步。不能只摘单方法注册的胜项。

继续读取至 EAGAIN（drain）没有同样一致的结果：固定 caller 时 reg16 mean +1.01%、p99 +12.98%，event_1 p99 四窗都高于 R134；允许双核时又有改善。因此只推进 separate ADD。

R134/C 的 reg1 p95 在 caller 固定 CPU 0 时仍为 +41.50%，四窗均高。禁止 caller 迁移没有消除问题。部分窗口 separate ADD 的非主动切换次数更多，而 p95 更低；不能把根因直接写成“抢占更多”。当前只证实回复发送方式参与了这次实机尾部变化，未证明完整内核时序原因。

Oracle 初筛和串行复核中 separate ADD 不占优，实机却出现上述改善；服务器能快速筛代码和结构，但在本任务上不能当尾延迟方向的否决器。

## 功能和精确产物

两个旧诊断 ELF 各通过 55 项 Oracle 单测、事件和 FD 契约、五项 ubusd 功能、两项 ubusd 恢复。drain 的通用恢复套件全过；separate ADD 所在通用套件整体仍失败，唯一失败是 **original/C netifd_overflow subsequent_events=false**。该独立案例未执行实验 ubusd；失败保留，未重试，也不归因于并发。

工作树提交 `fa3ed5a` 采用独立发送 ADD，保留查询合并、short-read 与 keyed ID。修正三行 doc comment 后，正式构建 `c6f002dad50f4cc7fbe6e19738246a4c55e20aa82285272ec81f0b133f403615` 与旧 separate ADD `df483ee2116acd910fac614220e061b08858c710a138e60b9bd0eb4cd05321e0` 的实际 .text 不同，不能借旧 ELF 的结果直接晋级。源码差异仅文档注释、区段大小相同、.rodata 相同，但代码布局变化已记录。后续正式窗统一使用新 ELF，另补其功能检查。

新一轮只确认这一组合：八个独立三方窗口、全部五条注册/对象事件负载。每项 ±1% 分辨带加至少 7/8 同向描述胜负；主项要求 reg1 p95 相对 R134 配对中位数严格低于 -5%、至少 7/8 低。C 比较和全部其他指标同时公开，不作多重比较校正后的全局优势声明。
