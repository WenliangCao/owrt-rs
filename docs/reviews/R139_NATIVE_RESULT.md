# R139：原镜像 libubus 注册诊断，p95 四窗降低

**独立 native libubus caller 的四窗八例全部通过，R136/C 的注册 p95 配对变化中位数为 −8.34%，4/4 窗降低，达到预冻结的 lower 描述门。** 本轮使用现有精确 C/R136 ELF，没有修改 daemon，没有部署。

每例 10,000 次单方法 ADD＋REMOVE、20 次预热，caller CPU 0、daemon CPU 1。两个 daemon 使用相同新 caller 和镜像原版动态库；八个逐周期数组共 80,000 条样本全部保留。

| 窗口 | C p95（µs） | R136 p95（µs） | R136/C 变化 |
| --- | ---: | ---: | ---: |
| 0 | 96.871 | 88.253 | −8.90% |
| 1 | 101.871 | 89.945 | −11.71% |
| 2 | 96.947 | 89.407 | −7.78% |
| 3 | 97.409 | 92.331 | −5.21% |

所有指标的同窗变化如下。只有 p95 是冻结的主诊断；四窗不是正式全局优势或等效性结论。

| 指标 | 配对变化中位数 | R136 更低窗口 |
| --- | ---: | ---: |
| mean | −9.34% | 4/4 |
| p50 | −10.03% | 4/4 |
| p95 | −8.34% | 4/4 |
| p99 | −5.10% | 3/4 |
| daemon CPU／周期 | −20.64% | 4/4 |
| caller CPU／周期 | −2.47% | 4/4 |
| 整窗 wall／周期 | −9.34% | 4/4 |

不利项保留：窗口 2 的 p99 从 C 188.123 µs 增为 R136 195.587 µs，**+3.97%**。完整八例、全部指标的四个有符号百分比／绝对差值及证据哈希见 [脱敏结果](r139-native-results.json)。没有删例、重测或追加窗口。

这补足了 R101 没有注册逐周期尾延迟、且只测旧 R100 ELF 的覆盖缺口。它只支持 **本次 native caller、CPU 放置和负载下**的方向。native libubus 与 Rust `Connection` 的接收、编码、分配和计时形状不同；不能比较跨 caller 的绝对延迟，不能据此证明旧 Rust caller 的慢尾是假象，也不能撤销 R136 已确认的四项尾部负判。

验证覆盖四窗六项保护器健康／清理门、相同 boot 与九个 stock 组件身份、固定工具／daemon／caller ELF、四个原镜像动态库的前后哈希、daemon PID/starttime/线程／亲和性／argv、完整签名前后检查、每周期对象／类型 ID 清零、最终空对象表，以及 **220 个原始文件与归档逐文件一致**。mean 和分位数从原始样本重算；daemon/caller CPU 和整窗 wall 从边界时钟独立重算。分析器另有原始数据损坏、身份／时钟错误、严格 ±5% 边界与方向数的拒绝测试。

没有采集 caller 的外部 live maps、每周期 CPU 迁移或调度轨迹。CPU 包含取时与循环开销，未扣探针成本，也没有用 wall 减 CPU 推断等待原因。
