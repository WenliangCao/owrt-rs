# R133：无监听者的命名对象事件

这是基于 R131 的一个独立、受限实验，不宣称已找到其注册 p95 回退的根因。
R132 的正式计数显示 R131 每注册周期仅比 R124 多约 19 条用户指令；
正式 profile 也没有显示 `send_obj_event` 自身有足以解释路由器尾延迟差距的增量。
但源码和精确汇编证明：Rust 在没有事件 patterns 时仍为每次对象事件查 registry、
增加并减少路径 Rc 引用；C 只在找到接收者后读取现成的对象路径。

候选只在两个已经确认存在合法命名对象的位置处理空 patterns：成功设置路径的 ADD，
以及删除时已经确认有 path 的对象。空 patterns 时推进事件轮次，并保留回绕清 stamp；
不查第二次对象表、不复制路径引用、不进入完整投递函数。
非空 patterns（包括完全不匹配者）仍走原路径，避免新预扫描。
原私有 `send_obj_event` 对不存在或匿名对象的提前返回行为保留。
正常请求、DATA/STATUS 的 monitor 镜像和顺序不变；没有监听者时不产生事件 INVOKE，
不增加 outgoing event_seq，不改变 scratch，batch 长度仍清零而保留容量。

先补真实 ADD/REMOVE 的 epoch、两种回绕位置、monitor 六帧顺序、匿名及拒绝请求回归。
这组新测试预期在原 R131 上也通过：它们约束优化，不被描述为修复旧 Bug。
独立分支以 R131 的已补测试源码为基础；规范路径重建的 R131 控制必须逐字匹配原 release ELF。

第一阶段只做 Oracle 正确性和同步计数预筛查，复用 R132 的原 register-cycle caller：
1/16 方法分别采用 R131/R133/R133/R131，n=100000、warmup=5000，共八窗。
单方法的两个配对用户指令数都必须下降，配对中位至少下降 3%；
16 方法不能有用户指令数超过 +0.5% 的配对退步。±1% 的 CPU/cycle 变化不描述为确定收益。
不支持或 multiplex 的计数拒绝，所有结果保留，不追加窗口凑通过。
这只是是否值得继续投入实机测试的筛查，不是性能接受门，也不是语言极限判定。

若预筛查不通过，就停止这个候选，不再换 inline、阈值或控制流变体。
若通过，再独立冻结物理路由器的注册/查询/调用、事件和正确性计划，
同时检查注册回退是否消失、R131 的 fanout 收益是否保留；不把 Oracle 数据当最终结论。
生产继续运行 C，候选不部署，每个路由器窗口后清理和核验健康。
