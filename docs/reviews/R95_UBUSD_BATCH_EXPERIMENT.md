# R95 ubusd 分批发送实验：未采用

2026-09-20。承接 [128 对象 pilot](R95_UBUSD_PILOT.md) 的 H1。
**4 KiB 分批发送没有进入运行时代码。** 单项 p50 改善没有覆盖完整矩阵的新未胜出项，
内存也没有证明全面胜 C/R89。保留新的背压回归测试和全部实验记录。

## 可重现的实验

试验候选 `469080f6…`，改动前 `0eea3291…`，另含精确 C、正式 R89。
[实验补丁](r95-ubusd-4k.patch) 以 `ad97260` 为基线，SHA 与冻结计划一致；
补丁只供重现实验，不表示当前实现采用了它。
实验使用同一 SDK，但 Cargo 构建根与改动前不同，即使使用 remap，也不能把所有差异
唯一归因于算法。恢复原算法后，在原固定路径重建得到与 `0eea3291…` 完全相同的 release 字节；
在实验目录构建则身份不同。后续算法归因试验应固定实际构建路径后再改变算法。

该补丁维持 16 KiB 总回复资格上限，把符合资格的回复按约 4 KiB 的完整帧块发送，
单帧过大时预留其实际上界，沿用原来的部分写入与队列处理。
Linux 6.12.94 的 `unix_stream_sendmsg` 在加入接收队列后调用 `sk_data_ready`，
支持“更早发送可能产生处理重叠”的机制推测，但不能单凭源码断言更快。
见 [匹配版本内核源码](https://github.com/gregkh/linux/blob/v6.12.94/net/unix/af_unix.c)。

- 128 对象：采样前提交 [四侧六 block 计划](r95-ubusd-blocks-plan.json)，
  24 个实机窗口，每侧每轮预热 100 次、计时 2,000 次。
- 完整矩阵：采样前提交 [四侧四 block、十负载计划](r95-ubusd-matrix-plan.json)，
  16 个实机窗口、160 条负载观测、每条计时 2,000 次。
- 两轮共 368,000 个计时请求成功。40 个窗口的生产 C、配置、boot、挂载、客户端健康和清理均通过。
  候选从未安装或启用为生产组件。
- 28 条单测与 clippy 在构建机通过；SDK 构建的 28 条单测在路由器全部通过，
  包括新补的两条连续查询、强制背压、覆盖组装缓冲后保持完整 DATA/STATUS、超批次大小单帧。
  另有路由器基本调用验证。首次测试交叉构建误带了缺少相邻 profile_support 的 example，
  改为明确构建 `--bin ubusd-rs` 的测试程序后通过；没有为此改动运行时。

原始记录：`private/r95/ubusd-blocks/`、`private/r95/ubusd-matrix/`。
派生值分别见 [128 对象全部值](r95-ubusd-blocks-results.json) 和
[完整矩阵全部值](r95-ubusd-matrix-results.json)。复算工具为
[r95_ubusd_pilot_report.py](../../tools/r95_ubusd_pilot_report.py)。全部为探索结果，未作确认实验。

## 单项改善，完整矩阵仍有缺口

以下百分比均为各 block **配对变化的中位数**，正数表示更慢/CPU 更高。
不以范围重叠证明等价，也不以四轮点估计宣称稳定回归。

128 对象独立试验：p50 对 C **-3.10%**、对 R89 **-5.28%**、对改动前 **-4.82%**。
主体 CPU 对 C/R89 仍较低，但对改动前 **+5.32%**；p99 对改动前 **+0.14%**。
这已说明“减少等待”可能伴随其他成本，不能只取 p50。

扩大到十负载后：

| 负载/指标 | 对 C | 对 R89 | 对改动前 |
|---|---:|---:|---:|
| lookup_all_128 / p50 | -0.72% | -4.68% | -4.98% |
| lookup_all_128 / CPU | -64.61% | -60.54% | +8.42% |
| **lookup_prefix_64 / mean** | **+1.20%** | **+4.47%** | **+4.48%** |
| lookup_prefix_64 / p95 | -0.25% | +9.06% | +8.79% |
| lookup_prefix_64 / CPU | -67.77% | +4.35% | +14.29% |
| lookup_prefix_64_c4 / mean | -41.51% | +5.00% | +3.86% |
| lookup_prefix_64_c4 / p50 | -41.23% | +7.21% | +5.37% |
| lookup_all_128_c4 / mean | -41.19% | -37.25% | +3.36% |

其余未胜出项：lookup p99 对 R89 +2.97%；invoke mean/p95/p99 对 R89
+0.15%/+1.58%/+3.28%；invoke_c4 p50 对 R89 +2.54%；lookup_prefix_64 p50/p99
对 R89 +2.82%/+5.98%。lookup、lookup_c4 的 CPU 对 R89 配对中位变化为 0，
也不记为胜出。完整正负项都在 JSON。
低成本 lookup 的 CPU 变化受约 5 µs/op 的计数粒度影响，对改动前的 +50% 不能脱离
绝对计数解释，更不能为了好看从表里删掉。并发 CPU 使用同一外层时间窗，不重复累加客户端窗口。

第 4 个 block 的候选 128 对象 p50 为 1589.241 µs，明显高于其余候选轮的约 1334–1351 µs。
该轮功能、身份和健康检查通过，按预先规则保留；没有证据将其归因为某一种系统噪声并删除。

## 内存没有因此验收通过

独立 128 对象试验结束时，候选的 VmRSS/RssAnon 中位数较改动前各低 12 KiB。
但完整矩阵结束时，观测为：

| proc 诊断计数（KiB） | C | R89 | 改动前 | 4 KiB 候选 |
|---|---:|---:|---:|---:|
| VmRSS | 956 | 618 | 626 | 624 |
| RssAnon | 144 | 162 | 170 | 168 |

差额缩为 2 KiB，且匿名页仍高于两基线；不能把独立轻负载的 12 KiB 改善外推为全场景收益。
这些计数有精度限制，C 的文件映射与 `/tmp` 中静态候选的映射类别也不同；它们不是 PSS，
更不是整个调用树/内核 socket 缓冲的峰值。本实验没有关闭内存验收缺口。

## 处置与下一步

撤下这版运行时改动，保留回归测试。恢复原有算法后，SDK 构建的 28 条单测已在路由器全部通过，
并再次验证 `0eea3291…` 的基本调用与清理；新保留代码仅在 `cfg(test)` 内。
[保留测试的实机身份与结果](r95-ubusd-kept-test.json)记录该最终窗口。
未运行的候选扩展构建机合同队列已取消，不把计划执行的门计作通过。

下一次试验先区分编码等待、客户端解析、调度和 socket 缓冲成本，再考虑批次大小或减少复制；
新方案重新冻结计划，不能将本轮改称“通过”，也不能仅重新挑选有利负载。
精确内存/峰值测量、独立确认实验、其他组件及整栈协同的目标均仍开放。
