## 重启前计划

用户明确批准一次普通重启，要求只调查、不改组件或配置，并在开机五分钟内保留
毫秒日志、按客户端健康验收。控制器只提交一次 `reboot`，提前持久化防重复标记，
连接失败不会重试重启。原始记录留在 `private/dhcp-event-reboot-20261017/`（0600）。

已重新验证 14 个离线恢复原件；重新通过 `sysupgrade -b -` 取得配置备份，46 个
成员、SHA256 `3e19b84765b5276cdc35a2d178627d527a9999a73d63f9f6a97d7a0bc34d6666`，
与此前干净配置完全相同。现役 v0.2.2、v0.2.1 回滚和 TFTP 镜像身份见
[上一轮材料表](DHCP_EVENT_BOOT_20261017.md)。十组件安装/ROM/运行身份、两频 AP、
WAN/WAN6、DHCP、DNS、watchdog、本地 HTTP/HTTPS 全通过；本次还从 Mac 的 en0
直接完成 IPv4、IPv6 外部 HTTPS 200 和向路由器的 DNS 查询，不依赖路由器代测。
没有部署新固件或安装自动回退守卫，已有手动恢复与回滚材料可用。

仪器：精确 ubox `6f78fa496bf36c55864a41e353df7d13f04b1077` 的 `logread -t`
直接输出原始 `time` u64 的 `[epoch_seconds.mmm]`，已在现役设备核验。
`logread -t -f -l 100000` 在首次 SSH 可达后读取全部 backlog 并跟随；同时只读
`ubus monitor` 观察现存客户端的 `notify_proto` 与接口更新，不设置日志级别或探针。
以客户端单调时钟及首次 `/proc/uptime` 的读取区间约束 boot 零点，检查 NTP 跳变。
客户端每秒尝试一次绑定 en0 的外部 HTTPS，失败/成功时间保留完整，不强制续租。

成本模型：总启动时间由硬件/服务启动、租约等待、事件脚本、netifd 处理及后续重载
组成，并发时间不能直接相加。此前最终 dnsmasq 进程起点约 29.26 s，只能作为联网
时间量级参考；脚本总成本仍未知。本轮预测 WAN 获租→up 小于 100 ms，且 60 s
上游租期导致约 30 s 的标准半租期续租。WAN6 地址或 data 是否实际改变是未知数；
若没变却产生 ADDRESS/DATA 更新标志，推翻“重载由上游输入驱动”的假设。

1 ms 日志量化满足 100 ms 门槛所需分辨率，但日志接收/调度及缺少脚本起止仍会
限制归因。首次租约→up 只能作为包含 netifd 的事件区间估计，不冒充脚本 CPU。
运行期续租不一定产生新的 up 边沿，不能与旧 up 配对。防火墙触发间隔不是执行耗时。
本轮选择同一次启动的被动日志+通知观察，不做第二次重启、离线性能代理或候选实现。
结果先汇报，再判断 `<2 s && <100 ms`；信息不足不当作满足条件。

防火墙条目是 stock `20-firewall` 的执行前日志，没有配对完成记录；以上是**触发次数**，
不是成功应用次数或执行耗时。首次三个触发的间隔为 1.181、2.142 s；跨校时的一个
间隔不直接相减。WAN6 后续 22 个间隔原值保存在派生 JSON。

dnsmasq 两次 `started` 在日志第 233、398 行，SIGTERM 在 397 行；重启后的
`/etc/hosts` 批次分别为初始化（422）、额外两批（424、433）。结合当前源码
`reload_hosts_data/reload_data` 与 init 的 `reload_service`，后二者符合 HUP 型重载。
两次运行期 resolver 文件读取不计为 HUP。dnsmasq 自报丢失 **3 条**日志，且不直接
打印每次 SIGHUP 投递，所以不声称完整 HUP 信号总数或 init reload 调用总数。

初次 DHCPv4 从 setting-up→up 为 1.071 s，DHCPv6 为 3.286 s；两段相加
**4.357 s**、墙钟并集 **3.297 s**。这是包含网络等待、客户端、脚本及 netifd 的
**协议建链包络**，既不是脚本估计值，也不覆盖脚本尾部及所有 hotplug；不能据此
宣称脚本总计超过 2 s。直接观测到的 IPv4 获租→up 317 ms 约为客户端联网时间的
0.96%，其中脚本与 netifd/调度仍未分离，不能把 317 ms 全算成 Rust 替换收益。

## 路由器侧的多余工作

用户已说明 WAN 接学生公寓墙口，上游不可改；**60 s 租期作为固定输入**。
stock udhcpc 按半租期续租，本次没有改变这个行为，也不再调查上游身份。

### WAN6：有效规则没有变化，却反复重建

完整 monitor（983,412 B）捕获 25 次 WAN6 `notify_proto`：20 次逻辑接口更新，
其中 19 次 ADDRESS、1 次仅 PREFIX；5 次请求没有产生接口更新。共享/独立对象
通知及订阅者转发已去重。PREFIX-only 没有触发防火墙，ubus 副本也没有各跑一遍
hotplug。地址变化已经存在于 stock 客户端提交的 `/64` 集合中，当前 netifd
ADDRESS 判定符合精确 C 参考；不把它误报成 Rust 错误置位。

监控覆盖段对应 **18 次 fw4 重建会话**，另外 5 次 WAN6 触发早于恢复后的 monitor。
其中有一对特别明确的重复：21:15:33.956 和 21:15:34.194，间隔 **238 ms**。
两次 fw4 读到的整个接口 dump 完全相同（monitor 353、396 行），service firewall
data 也均为 `{}`。其间接口短暂变化又恢复，队列留下后续一次重建。该队列策略与
精确 C 一致，是可改进的合并不足，不是 ubus 广播重复调用。

进一步在 **Oracle** 用现役 SHA 匹配的 fw4 ELF、现网 firewall 配置和捕获状态做
一次只读 `print` 差分，固定其他接口/服务输入：基线加 20 个 WAN6 更新，共 **21 份**。
全部退出 0、stderr 空；有 8 种完整文本，变化全在 **未引用的 `define wan_subnets`**。
删去该定义后 21 份输出逐字节相同，SHA256：
`310395b2cbbdbe38bfafa481e5c085c5ef2f10c3d93b9470fd5b91179ece2f1a`。

现网规则按 `wan` 设备、协议及固定端口匹配，没有 NAT reflection 或动态子网引用。
唯一自动 include `10-custom-filter-chains.nft` 全为注释，已纳入边界核验。
因此这些状态变化没有改变**当前有效防火墙规则**，整份规则重建存在可避免工作。
这不是可直接跨配置跳过 reload 的证明：flowtable/其他副作用、失败重试和真实配置
变更必须保留，本轮没有测试 nft 安装或擅自加入节流。

### IPv4 续租：没有多余重载，但重复写内核地址和路由

monitor 覆盖到 **7 次内容完全相同的续租通知**，每次 1 个地址、1 条默认路由。
结果是 **0 次 WAN interface.update、0 次 WAN ifupdate 防火墙触发**。
`write_resolv_conf` 在内容不变时返回，没有重复发布 resolver 文件。

但当前 Rust [netifd 实现](../../components/netifd/src/main.rs) 在每次通知仍无条件
`add_address`（2056）及 `add_iface_route`→`add_route`（2347）；
[sys 实现](../../components/netifd/src/sys.rs) 将它们作为 CREATE|REPLACE 发给内核。
按这 7 份实际输入和代码路径，产生 **7 次 RTM_NEWADDR + 7 次 RTM_NEWROUTE**。
这是代码与输入推导，未用系统调用跟踪认领其耗时。精确 C `interface-ip.c` 的
keep/replace 分支会跳过已成功安装且属性完全不变的地址与路由。

因此可省的是 **netifd 内部重复工作**，不是把固定 30 s 续租取消，也不是为此
单独替换 jshn/jsonfilter/ubus CLI。对 IPv6 lifetime、地址撤回、真实路由变化及
之前失败的内核操作，不能套用“地址字符串相同就跳过”。

## 续租补充观察计划

用户补充 WAN 接学生公寓墙口；上游不可改，60 s 租约是固定输入，不再调查上游
身份。只查本机重复工作。计划用一次 35 s 只读窗口比较既有 udhcpc 进程的已回收
子进程 CPU ticks，并以日志确认实际跨过几次续租；不强制续租、不安装工具。
模型预测每次旧脚本及后代 CPU 为约 80 ms（此前稳定续租间隔超出 30 s 约 79 ms
只是线索，包含 RTT/调度，不能直接作为脚本耗时）；100 Hz 的 10 ms ticks 仅用于
这个量级估算。与进程自身 CPU 分开，保留采样边界/子进程未回收的不确定性。
源码已显示相同 IPv4 续租不发 ifupdate，但仍重复提交地址与路由；这次观察不为
这些 netlink 请求单独认领耗时，也不把稳态 CPU 换算成开机墙钟耗时。

实际窗口 **35.29 s**，同一 udhcpc PID/start/boot，跨过 **1 次续租**；已回收
子进程 user+system CPU 增加 **4 ticks≈40 ms**，udhcpc 自身为 0 tick 增量。
这是一次 10 ms 刻度的 CPU 观察，不是零 CPU 证明或延迟分位数。起止均距离该次
租约日志十余秒，不是脚本尚未回收的边界。预测 80 ms CPU 比实测高一倍：模型
修正为“周期多出的约 79 ms 还包含 IPC/等待/调度/网络 RTT”，不把它全当脚本 CPU。

## 决定

首次 WAN 事件 **317 ms ≥100 ms**，所以本轮**不满足直接放弃条件**；脚本总计
是否小于 2 s 仍未知，不能宣布已达门槛或把稳态 40 ms CPU 外推为全部开机成本。
现有证据支持优先评估本机的无效防火墙重建与 netifd 重复内核写。这些收益并不要求
先把 DHCP 两个脚本整体改成 Rust。测量及调查到此汇报，未开始脚本替换、odhcpd-rs
或任何生产修复，三天实现期限尚未启动。
