# v0.2.2：一次授权重启的 DHCP 事件测量

## 重启前计划

用户明确批准一次普通重启，要求只调查、不改组件或配置，并在开机五分钟内保留
毫秒日志、按客户端健康验收。控制器只提交一次 `reboot`，提前持久化防重复标记，
连接失败不会重试重启。原始记录留在 `private/dhcp-event-reboot-20261017/`（0600）。

已重新验证 14 个离线恢复原件；重新通过 `sysupgrade -b -` 取得配置备份，46 个
成员、SHA256 `3e19b84765b5276cdc35a2d178627d527a9999a73d63f9f6a97d7a0bc34d6666`，
与此前干净配置完全相同。现役 v0.2.2、v0.2.1 回滚和 TFTP 镜像身份见
[上一轮材料表](DHCP_EVENT_BOOT_20261017.md)。十组件安装/ROM/运行身份、两频 AP、
WAN/WAN6、DHCP、DNS、watchdog、本地 HTTP/HTTPS 全通过；本次还从 Mac 的 en0
直接完成 IPv4、IPv6 外部 HTTPS 200 和向路由器的 DNS 查询，不依赖路由器代测。
没有部署新固件或安装自动回退守卫，已有手动恢复与回滚材料可用。

仪器：精确 ubox `6f78fa496bf36c55864a41e353df7d13f04b1077` 的 `logread -t`
直接输出原始 `time` u64 的 `[epoch_seconds.mmm]`，已在现役设备核验。
`logread -t -f -l 100000` 在首次 SSH 可达后读取全部 backlog 并跟随；同时只读
`ubus monitor` 观察现存客户端的 `notify_proto` 与接口更新，不设置日志级别或探针。
以客户端单调时钟及首次 `/proc/uptime` 的读取区间约束 boot 零点，检查 NTP 跳变。
客户端每秒尝试一次绑定 en0 的外部 HTTPS，失败/成功时间保留完整，不强制续租。

成本模型：总启动时间由硬件/服务启动、租约等待、事件脚本、netifd 处理及后续重载
组成，并发时间不能直接相加。此前最终 dnsmasq 进程起点约 29.26 s，只能作为联网
时间量级参考；脚本总成本仍未知。本轮预测 WAN 获租→up 小于 100 ms，且 60 s
上游租期导致约 30 s 的标准半租期续租。WAN6 地址或 data 是否实际改变是未知数；
若没变却产生 ADDRESS/DATA 更新标志，推翻“重载由上游输入驱动”的假设。

1 ms 日志量化满足 100 ms 门槛所需分辨率，但日志接收/调度及缺少脚本起止仍会
限制归因。首次租约→up 只能作为包含 netifd 的事件区间估计，不冒充脚本 CPU。
运行期续租不一定产生新的 up 边沿，不能与旧 up 配对。防火墙触发间隔不是执行耗时。
本轮选择同一次启动的被动日志+通知观察，不做第二次重启、离线性能代理或候选实现。
结果先汇报，再判断 `<2 s && <100 ms`；信息不足不当作满足条件。
