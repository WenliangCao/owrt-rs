# 硬件流卸载 / WED 与负载延迟：本轮计划

2026-10-18。现网 v0.3.0，软件卸载开启、硬件卸载关闭、WED=N。用户授权配置
试验与重启；不重写组件。CAKE 仅测量和评估，是否配置留待结果汇报后决定。

当前模型：吞吐由无线、宿舍上游及远端共同限制；CPU 成本包括包转发、无线 DMA
和现有服务。9 月 29 日 HFO 单开、WED 关闭未达到 CPU 收益门。此次预测是
HFO+WED 令同类下载的 CPU/GiB 至少降低 15%，或在 CPU 受限时吞吐增加至少
10%；若不超过同配置噪声，不保留候选。不会将内核接收 offload 配置当成实际命中。

先做小流量端点检查：Cloudflare 小请求成功、大请求返回 403，故不采用；
采用 macOS networkQuality 官方配置返回的 Apple large/slurp HTTPS 端点，
冻结同一 IPv4 地址、HTTP/1.1、en0 和四条并行流。两个配置各三次 20 秒下载，
不挑最好轮次，不因结果不利替换轮次。上游路径仍有时间变化，这不是实验室
纯路由器上限。完整端点、原始输出、IP/MAC、配置和证据放 ignored private。

记录每秒路由器总量/每核 busy、softirq、接口字节；CPU/GiB 使用正式流量期间
CPU 速率除以下载速率，同时报告吞吐和 CPU%，不以 softirq 代替整机 CPU。
100 Hz 的 20 秒计数分辨率足够判断 15% 效应；同配置三轮范围作为测量噪声。
固定 curl 的接口、地址和不使用代理，并要求每条负载流源端口出现在路由器
Mac→固定端点的 conntrack 中；记录 Mac en0/utun 字节，避免混入 VPN 路径。

接受候选须同时满足：

- fw4-rs 与精确原版 fw4 在同一冻结输入的 HFO 规则逐字节一致；完整候选 nft
  检查通过且无现网副作用。此门已通过。
- WED 启动 attach/WO 与匹配负载流的 PPE 状态有直接证据；不能只看开关或
  HW_OFFLOAD 标记。低频只读 txinfo/rxinfo/PPE BIND，不写调试寄存器。
- CPU/GiB 中位数降低至少 15%，且差值大于两侧轮内范围；或有 CPU 瓶颈证据
  且吞吐增加至少 10%、超过范围。吞吐下降超过 5% 且超过噪声则拒绝。
- 完整三分钟真实客户端健康窗口通过；没有驱动超时/reset、网络不稳定。

候选只改 firewall 的 hardware offload 和 modules.conf 的 mt7915e wed_enable，
SFO 保持开启。先验证离机配置备份及现役固件恢复镜像，独立 S01 守卫在模块
初始化之前启动；首次启动等待最多 1200 秒。未确认或明确拒绝时精确恢复原
文件并仅请求一次回滚重启。另有 13 个使用实际镜像 BusyBox 的离线守卫用例。
确认必须在收益与三分钟健康通过后进行，随后清理临时守卫。

第二阶段在最终保留的配置下分别测三次 20 秒上传/下载，复用同一端点与客户端。
并发测 Mac→路由器与公网端点的 TCP 建连时间，失败单列，空闲 10 秒为参照。
这是 TCP 建连延迟，不称 ICMP RTT。公网 p95 增量至少 20 ms 且至少两轮同向
作为明显负载延迟恶化的工程门；同时看 LAN 探针以区分无线/客户端与外网。
如有明显恶化，报告 CAKE 带宽/CPU 代价及硬件卸载绕过 tc/IFB 的取舍，不安装。

每阶段只保留本计划和一份结果报告；原始失败保留。软件与硬件协议、基线和
当前唯一输入的规则验证依据见此前转发、排队报告及本轮私有收据。
