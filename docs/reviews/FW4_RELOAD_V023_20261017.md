# v0.2.3：跳过有效规则未变化的 fw4 reload

**Oracle 真实 nft 内核对照中，3 次 WAN6 地址变化、1 次普通重复 reload、
1 次计数器增长后的 reload、4 个并发 reload，候选共 0 次下发，原版共 9 次。**
规则变化、外部内核改写、include 和故障恢复仍下发；40 个场景 × 两实现全部通过。
这里验证功能与下发次数，不把 Oracle 时延当作路由器收益。真机部署验收另报。

## 决策与边界

成本模型仍是“输入读取/渲染 + nft 解析和事务应用”；本次省去已证实无效的后者。
新增成本是只读的静态 nft 表快照与短 netfilter generation 查询，未取消 hotplug
触发或接口状态刷新。预测是：首次认证后，未引用的 WAN6 subnet 定义变化不下发；
一条实际规则变化必须下发并可在内核查询到。实验直接计数 nft `-f` 调用和检查内核
规则、handles、实际增长的计数器，分辨率为一次事务，不设微秒性能门槛。

仅去掉渲染器生成、全文不存在 `$name` 引用的 zone device/subnet 定义；其余生成
文本逐字节比较。不会重排规则或推测不同表达式语义相同。持有现有 `fw4.lock` 时，
只有候选有效文本和上一次成功应用后记录的 `nft -s list table inet fw4` 都完全
相同时，reload 才跳过下发。没有使用 hash 代替相等比较，也不只信旧 render 缓存。

- 成功应用前读 generation G；应用后、快照后都要求 G+1，排除其他 nft 事务混入。
  检查当前表时也要求读取前后 generation 不变。外部规则增删、表被清空/删除、查询
  失败都会回到普通 reload。最后一次检查之后，仍无法阻止不遵守 fw4 锁的外部写者。
- 有用户 script include、非纯注释 nft include、named ipset 或无法确认的输入时，
  普通 reload。支持当前纯注释 include 和 software flowtable。
- 纯注释 include 与父目录/通配目录记录 dev、ino、ctime、mtime（纳秒）及 size，
  同时检查 symlink 与目标。读取前后和认证/skip 前重核，防止 include 在 nft 应用
  窗口改变又恢复后，旧候选与不同内核规则被长期错误配对。
- 失败 apply、stop、flush、reload-sets、独立 includes 调用失效缓存；restart 强制
  检查和应用。状态文件或内核快照不可认证时只损失优化。缓存是 `/var/run` 中的一个
  原子替换文件，不保存到固件或持久配置。

## 与原版 firewall4 的明确差异

参考原版是镜像 shell/ucode firewall4，匹配上游
`b6e5157527d361f99ad52eaa6da273cb0f2dfd59`，并非独立 C fw4 程序。
原版每次 reload 都下发；候选在以上可证明条件下保留已有表，因此也保留 packet/byte
计数器、software flowtable 中已有流及其他规则运行状态。`-v reload` 被跳过时没有
nft echo。`fw4.state` 及接口输入仍刷新，`print` 的原版字节契约不变。

初始没有 flowtable 时生成文本不含 `delete flowtable`，下一次 reload 出现该前导命令，
因此需要额外一次普通 reload 才进入稳定认证状态。保留该保守热化；不扩大语义归一化。
原版 apply 失败后 CLI 通常仍取 includes 阶段的退出码，此兼容行为保留，但失败不能
产生或沿用本次认证。restart/check/stop/flush 的显式操作没有被自动去重。

## 授权的单次定向修正：start 不建立 reload 证书

[首次真机 A/B](V023_DEVICE_AB_20261017.md) 已推翻“额外认证开销可忽略”的预测：
start CPU 23.273→37.404 ms，变化 reload 23.682→38.333 ms。用户随后仅授权一次
定向小修。本次产品 diff 只在 `lib.rs`：仅 reload 准备有效规则/输入戳，start 与
restart 保留原状态写入、缓存失效、nft apply 和 includes，不做额外 GETGEN、实时
规则快照或证书保存。`reload.rs`、缓存格式和全部认证边界保持原样。

首个后续 reload 正常 apply 后建立证书，再后续相同事件可以跳过。现网 software
flowtable 原本就因 `delete flowtable` 前导变化需要这次热化，故不增加本机的首个
reload 下发；无 flowtable 配置的首个 reload 则可能比此前候选多一次 apply。
变化 reload 保留成功应用后的必要快照，使紧接着的相同事件立即可 skip；删除该
快照会把认证及额外 apply 移到后续 WAN 事件，因此本次不把这种成本转移当作优化。

模型预测 start 可以省去此前新增认证的大部分成本；没有分段 profile，不把约
14 ms 增量全部归因于一个命令。下一步由正式 SDK 产物在用户授权的 start/changed
两项真机复测中裁决；Oracle 不作性能比较，不运行优化轮次或 PGO。

Oracle 单次功能回归 **41 场景 × 两实现**、19 单测及 Clippy 通过。新增的实际 nft
调用断言确认：start/restart **0 次**证书快照；首 reload **1 次**快照并建证；后续
相同 reload **0 次 apply**；变化 reload **1 次 apply + 1 次快照**，下一次相同
reload 立即 **0 次 apply**。原有外部改表、失败、并发、include 与 generation
竞态负控同时保留。原始结果在 `private/fw4-v023-20261017/results-start-fix-1/`，
独立 Oracle ELF SHA256 `ce664a477ece5ca663d8ebf8c2df3ebb7ac3753f122c7b3c2771b96af8202359`；
它只用于功能检查，正式 SDK/镜像产物需重新构建与核验，不能沿用旧候选性能结论。
