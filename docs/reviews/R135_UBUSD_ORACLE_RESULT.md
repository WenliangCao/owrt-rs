# R135 Oracle 预筛：八组合已测，未复现实机慢尾

三项因素的八种组合已经完成，不是只写了计划。Oracle 实际有 4 个可用 CPU、无 CPU quota，本轮以两组不重叠的 CPU 对并行初筛；没有独占 cpuset，因此仍需串行复核。没有在路由器部署候选。

初筛含精确 C、R131 和八个 R134 组合：每 CPU 对四块、两种 caller 亲和性、三条负载，每条 10,000 次，共 480 个测量，收集约 96 秒。2082 个原始文件的哈希、80 个 daemon 清理和所有样本统计均复核。未混合两个 CPU 对冒充八次同核心重复。

随后仅在 CPU 0/1 串行复核 C、R134、drain、separate ADD，另外 96 个测量、450 个文件通过核验。初筛的 C/R131 argv0/路径长度没有统一；后续串行启动已归一。初筛八个因子候选路径同长，但跨 C/R131 的初筛比较只能作为探索参考。所有原始记录和不利结果均保留。

## 结果和下一步

Oracle 没有复现“R134 常见请求更快，但注册 p95 明显高于 C”的路由器现象。串行时 R134 的三条负载 p95 都低于 C；因此同为 Linux/aarch64 不能保证这项慢尾在两个平台间具有一致方向。

继续读取至 EAGAIN（`s0b1k1`）的注册 mean 相对 R134 约降低 0.77%–1.38%，CPU 增加 2.59%–3.48%；多数延迟变化接近 ±1% 的探索分辨带，事件路径没有整体改善。撤销 ADD 合并（`s1b0k1`）注册 mean 增加 1.49%–1.88%，CPU 增加 5.15%–5.33%。恢复逐 ID getrandom 的组合没有提供明确优选方向。这里的范围跨两种亲和性和两条注册负载，是逐块百分比中位数，不是置信区间。

没有据此修改生产运行时，也没有宣称“服务器上没问题所以路由器退步作废”。保留 drain 作为主要接收时序探针、separate ADD 作为回复唤醒时序反证；两者通过功能门后，在路由器做四窗定向诊断。它们不是已经获胜的正式候选。原 R134 的五项实机尾部负判保持。

## 结构计数

18 个 C/八组合 × 1/16 方法 trace 完成，167 文件匹配。所有侧每 100 周期成功 recvmsg 都为 200；R134 组合的 read 为 0，C 为 200。ADD 合并使 sendmsg 从 400 减为 300，keyed ID 使逐 ID getrandom 从 200 减为 0。

在 **ptrace 改变时序的条件下**，短读即返回的 s1 组合有 200 次 epoll_pwait；读至 EAGAIN 的 s0 只有 1–3 次，C 为 2 次。该结果证实因素改变了能否在同一处理轮次接住下一请求的机会，不能把这些 trace 次数当未跟踪负载的调用率，更不能当实机慢尾的因果证明。所有 trace 时间排除于性能统计。
