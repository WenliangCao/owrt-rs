# 九组件整栈实测与收尾（2026-09-29）

**九组件整栈的性能收益成立：本次真机软件重启后，混合负载控制面 CPU 降低约 31%，吞吐提高约 31%。复核撤回“内存退步”和“AES p99 稳定退步”的判断，并补出一个真实的 netifd IPv6 选址兼容差异。该差异和 fw4 校验工具已修正；断电恢复留待下一阶段。路由器已恢复测试前的 C 状态。**

## 复核后的内存、TLS 与资源结论

- **原 MemAvailable 差额主要反映文件缓存与可用内存估算，不成立为 Rust 内存退步证据。** 全部 726 个快照都精确满足下述 4 KiB 页取整模型：`MemAvailable = MemFree − 24576 + L − 4×floor(L/8) + S − 4×floor(S/8)`，单位 KiB，L 为 Active(file)+Inactive(file)，S 为 SReclaimable。按这个分支，空闲页变成 1 MiB 文件缓存会使 MemAvailable 降约 0.5 MiB。Rust 测前多 14.81 MiB 文件LRU，其中 12.10 MiB 为 Inactive(file)。大量身份校验读取是合理来源推测，逐页来源未记录。
- **扣除空闲、文件LRU和可回收slab后的整机占用更低。** 测前 Rust 为 65,176 KiB，三次 C 分别为 66,300 / 70,460 / 67,208 KiB；主负载后 Rust 为 66,404 KiB，C₁ 为 67,400 KiB。这个余额包括多类内存，不称为“永久不可回收”或单个组件的独占占用。Mapped 的确增加约 2.9 MiB，与静态 ELF 工作集增大相符；没有逐页归因，暂不把增量全部算给静态链接。
- **撤回 AES p99 的稳定退步判断。** Rust 的默认静态 c1 与指定套件 c1 实际都是 AES256-GCM，三轮 p99 的中位数却为 8.80 / 13.89 ms。同套件每窗 1200 请求中，C₁、Rust、两次 C₂ 超过 12 ms 的次数为 11 / 16 / 14 / 9，Rust 默认 AES 负载为 10；所有静态 c1 负载合看为 9～17 次。每轮仅 400 次时，p99 对少数离群请求敏感。Rust 同 AES 的合并中位延迟为 5.85 ms，C 约 7.5～7.6 ms。样本支持链路/调度噪声解释，具体是否 Wi-Fi 重传未记录；12 ms 是事后诊断阈值。
- **HTTPD 的部分资源增加。** 主负载后的匿名页为 492 vs 332 KiB，fd 为 23 vs 11，线程为 4 vs 1。其 RSS 仅略低（1,932 vs 1,944 KiB），不能套用其余组件的内存降幅。
- **空闲时六守护进程 CPU 很低。** 以两核整机容量为分母，全部六段空闲采样均低于 0.1%（若按单核分母，C 的最高段约 0.13%）。整机忙占比约 1.6%～4.0%，主要未落在这六个进程的自身 CPU 计数内；三次 C 启动也有波动。它包含每秒采样、内核及其他活动，不是静息功耗。
- **默认 TLS 比较包含套件选择差异。** 双方固定 TLS 1.2，但 C 默认使用 CHACHA20-POLY1305，Rust 使用 AES256-GCM。相同 AES 的独立负载已列出；不能把默认协商的全部差额归因于 HTTP 处理。
- **Wi-Fi 慢尾有明显窗口波动。** C₁ 的四并发静态 HTTPS p99 为 73.69 ms，两次失败 C₂ 的已完成负载仅 16.12 / 15.41 ms；因此 Rust 相对 C₁ 的 −85.41% 不能当作稳定可重复的改善幅度。
- **运行文件和存储也有代价。** 九个 Rust 静态 ELF 合计 7,741,878 B。原版九个入口合计 520,451 B，但大量实现位于共享库、ucode 和 shell 工具中，这不是完整安装体积的公平比值。实验期间 overlay 已用空间增加约 1,320 KiB，包含旧包、恢复副本和文件系统分配变化；未测最小固件体积、功耗或 flash 寿命。

Rust 采样时两个回退计时器共有四个存活进程，测前 RSS 合计 4,016 KiB、匿名页合计 356 KiB；共享页会重复计入 RSS，不能直接从整机内存差额扣除。原启动计时器虽已解除，其休眠进程在本次 Rust 窗口内仍存活，直到回到 C 的重启清除；独立试运行计时器在第一次 C₂ 采样前已解除并回收。

软件重启后首次观测 SSH 可达为 C₁ 74.34 秒、Rust 50.30 秒；轮询间隔为 10 秒，含 Wi-Fi 恢复和客户端连接，只有一次 Rust 启动。健康验证包括客户端 DHCP、双频 AP、WAN/WAN6 up、DNS A/AAAA、HTTP/HTTPS 和 watchdog 运行状态；外部 HTTPS 由路由器发起。**五次启动全部由 SSH 执行 reboot，实际断电恢复为零次。** 原冻结计划中的“冷启动”在这里更正为软件重启，原计划文件保持原样。确认后取消的启动计时器不提供跨断电的持久回退保障；该保障和 R92 断电后无网络问题下一阶段单独处理。

## C₂ 为什么没有完成

实际经历五次软件重启：C₁、Rust、第一次 C₂、失败后的 C 恢复启动、第二次 C₂。没有再次部署 Rust，也没有刷固件。

| 阶段（UTC） | 结果 |
|---|---|
| 08:08–08:21 C₁ | 全部负载、身份、配置及健康检查完成 |
| 08:21–08:33 Rust | 最终九组件共同运行，全部负载及恢复前检查完成 |
| 08:33–08:41 第一次 C₂ | 三轮 LAN 和首轮部分本机负载完成；第一次 fw4 测量字节校验失败 |
| 08:41–08:42 自动恢复 | 原包、原 C、原启动状态和原保留包恢复并核验 |
| 08:51–08:53 只读诊断 | 13 次采样中 WAN IPv6 地址数由 4 变 6，fw4 只有 wan_subnets 定义相应变化 |
| 08:54–09:03 第二次 C₂ | 沿用全部冻结工具与负载；同一处校验再次失败，随后恢复 |
| 后续收尾 | 已校验下载失败材料、清除设备上的测试残留，完成最终只读审计 |

失败是 `benchmark INVALID: child stdout failed byte validation`。旧工具有两个设计缺口：fw4 参考输出来自被测栈本身；该参考又在窗口开始时生成，后续网络状态变化会被判为字节错误。只读诊断直接捕捉到 WAN 地址集合变化，失败后的输出也只在 `wan_subnets` 上不同。四个窗口保存的初始参考输出，在仅对子网集合成员排序后完全相同。两次失败瞬间的实际 stdout 未保存，精确差异仍缺失；现有证据指向过期参照与上游状态漂移，而非 C 版退步。

补采前明确限定最多一次重试，未依据性能选窗。两次失败窗口各保留 15,600 次有完整结果的成功操作，单列展示。已完成的本机负载均保持 Rust 更快的排序；C 相对 C₁ 的平均延迟变化为 −3.95%～+10.52%，所以“全部在 ±7% 内”稍有夸大。缺少完整 C₂ 主要留下混合、fw4 和重载负载的后置对照缺口，并不推翻已测窗口的显著收益。

新 fw4 工具每轮以 `/rom/sbin/fw4 print` 前后夹取 C 参考，参考调用在被测 CPU/延迟区间之外。只归一化 `*_subnets` 中普通 IP/CIDR 成员的顺序，保留成员增删、重复成员、规则顺序和其他文本差异；所有实际 stdout/stderr 均留存。前后 C 输出变化标记为 `INVALID_ENV`。夹取是相近时段的观察，并非网络状态的原子快照。

## 已修正的 IPv6 前缀顺序差异

四个 `network.json` 均显示 LAN 没有显式 `ipv6-address`。三次 C 的 `ipv6-prefix-assignment` 顺序都是 GUA/64 → ULA/60，Rust 为 ULA/60 → GUA/64；`network_get_ipaddr6` 因而分别选中 GUA 与 ULA。防火墙集合成员相同，使用首地址的其他调用者则受影响。

匹配镜像的 netifd 源码 revision `cbb83a1857407a28a63dc09412a1f209195914ef` 在 `interface-ip.c:1340` 对新建及更新的前缀执行头插；ULA 变化也走该路径。Rust 原先尾部追加。修复统一了 ULA 和协议前缀的替换顺序，并测试了实际状态编码后的首个地址、续租、ULA 替换、撤销及多个 PD 更新。这里遵循“最新更新在前”，不是固定把 GUA 排在 ULA 前面。

WAN 的 `ipv6-prefix` 则遵循 C vlist 的地址/掩码顺序；修复保留这个独立顺序，避免全局头插连带改变另一项接口行为。Linux netifd 全部 170 项测试通过，包括四项新增顺序回归；fw4 归一化单测、真实 CLI 的成功/失败字节留存测试，以及 `make check-tools check-harnesses check-benchmark` 全部通过。[复核验证清单](STACK_20260929_REVIEW_VALIDATION.json)记录输入身份与检查结果。
