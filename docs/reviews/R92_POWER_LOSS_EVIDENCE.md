# R92 断电后 WAN 故障：历史证据复核

2026-09-29。复核当日对话、原始截图、部署身份、离线归档及已部署版本源码；本次未连接或改动路由器。

**2026-09-16 那次故障的准确描述是：断电恢复后系统已启动，LAN、Wi-Fi、后台和 SSH 可用，WAN 未恢复正常联网。用户当时报告，在路由器上执行 `ping 1.1.1.1` 立即返回 `Network is unreachable`。现存材料尚不能确定 WAN 启动链在哪一步失败。**

这比后来记忆文件里的“冷启动后没有网络”更具体。排查应优先追踪 WAN 设备、链路、DHCP 和路由安装；早期 PID1 卡死、总线未启动、无线完全没起来，都不是当日已报告的现象。`ping` 的报错来自当日用户陈述，未找到那次命令的独立输出或抓包。

R92 运行时是 `ca1a9121df0380448a19d474e29796066b6734e8`，正式构建 `34874442503`。已将 09-16 断电前记录的九个生产哈希逐项与 R92 发布证明比对，全部相同。故障 boot 的回退前状态还记录着六个 Rust 接管开关开启，以及 logd/httpd/rpcd 的 PID；故障 boot 本身没有留下九组件完整的 `/proc/PID/exe` 哈希。

**备份实际证明了什么。** 对照 09-15 R93 overlay、故障 boot 的回退前配置包、09-16 恢复 C 后的 R94 overlay，三份材料中的 `/etc/config/` 文件集合及内容完全一致，共 19 个普通文件，包括历史 `.bak` 文件。WAN 配置为设备 `wan` 上的 DHCP，WAN6 为同一设备上的 DHCPv6。因此“回退顺手修好了持久网络配置”没有证据支持。

回退前包仅有 45 个持久文件，属于 `sysupgrade -b` 配置备份。它不含故障时的 `/proc`、`/sys`、`/tmp`、DHCP 租约、地址/路由表或完整运行日志。`.state.txt` 额外保留了 boot 标识及六个开关状态，也没有 WAN 故障详情。该包 SHA256 与当时状态文件的记录一致：`40eb2a45551c2a2ff0a42ae0ef83df123cd915e2b0bf8a17ea30aadf8be56d10`。

设备记录的备份时间为 `2026-09-14T23:38:28+02:00`，与 09-16 的对话、执行过程及前后归档顺序冲突，应视为滞后的设备时钟。故障前、回退前、恢复后的三个 boot 标识互不相同；不能按文件名把这次回退排到 R92 最终验收之前，也不能把时钟滞后直接当作断网根因。

**两处历史判断需要纠正。**

- 当时助手将 `missing executable recovery switch` 解释为“`/root/r84` 已丢失”。截图只证明 `-x` 失败。前后两份 overlay 都保留着同一份 `stack-switch.sh`，权限都是 `0644`，SHA256 都是 `454212dd5219856e31dd74c7b1257fb19a05cf0bcd761230760d8ef32be4a3d7`，与 R92 源码及部署包一致。原工具通过 `/bin/sh script` 使用它，不需要执行位。新回退工具却先要求 `-x`，构成误检；本地仅做 `test -x` 和 `sh -n` 即分别得到失败和成功。现有证据不支持“断电导致回退包丢失”或由此推断 overlay 损坏。
- 当时读到的 `mt7530-mdio ... error -110`、AN8855 链路起来等日志，都是恢复后的 C boot。它们不属于故障 boot。原记忆中泛指 procd/ubusd 早期启动失败、P6 旧 DNS 缺陷的猜测，也没有失败现场支持。数字 IPv4 目标的不可达首先要求检查路由和 WAN 状态，单独缺少 DNS 上游文件不足以解释它。

**自动恢复为什么没有发生，已经有明确证据。** R92 的 `stage rust` 安装 900 秒计时器；`confirm` 将 pending 改为 confirmed，并删除 canary init 文件和启动链接。R93 故障前归档中，confirmed 存在，pending/reverting/canary 均不存在。后来再上电仍会启用 Rust，却不会重新启动这个回退计时器。[E6]

这解释了“为何需要人工回退”，不是“WAN 为何失败”的根因。机器当时能提供 SSH，后续保护机制的健康条件必须覆盖 WAN 实际可用性；仅以系统启动、SSH 可达或 PID 存在来判成功，会漏掉同类故障。仅记录启动次数也不足以处理一次启动后长期停留在 WAN 不通的情况。

**目前的排查优先级如下；这是依据症状的技术推断，不是已证实的故障归因。**

R92 源码已经包含设备晚出现、carrier 状态变化及 DNS 文件写出的处理。存在这些代码和已有软重启通过的事实，只说明不能直接套用 P6 旧故障；实际断电启动时的时序仍需单独验证。对 R92 归因必须使用上述发布提交，当前 HEAD 或 09-29 九组件产物不能代替历史版本。

**恢复 C 的结果应怎样解释。** 用户在本次复核中明确确认：恢复 C 后上网正常时，宿舍网线已重新直连 AX3000T WAN。[E8] 结合配置逐字节一致的证据，可以确认：同一台设备、相同持久配置、相同最终接线，R92 断电启动后 WAN 失败，切回 C 并重启后恢复。这进一步支持调查 Rust 栈的 WAN 启动恢复路径。仍同时改变了九个实现、重新启动了设备，也经过了等待；现有证据尚未把实现差异与重启、上游恢复时序分离，更不能锁定某个组件。

09-20 宿舍再次停电、恢复供电后核验生产 C 的 R95→R96 记录是另一件事，不混入本次时间线。[E7]

下一步最有价值的证据，是在任何重启或回退之前，同时保存同一 boot 的 WAN 设备/carrier、`network.interface.wan/wan6`、协议进程、IPv4/IPv6 地址、全部路由表与规则、netifd/udhcpc 日志；若接口已启动但仍无租约，再记录 DHCP 报文。每份记录同时带电脑时间、设备 uptime 与 boot 标识，避免再次被设备时钟误导。随后才能区分“协议没启动”“请求未获回复”“获租却未装路由”。真正断电复现及持久回退的设计另行安排，本次只完成历史取证。
