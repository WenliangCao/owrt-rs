## 为什么 R136 可以收手

R136 在已有的 18 条实机负载中，daemon CPU 相对 C 全部下降；平均延迟有 11 项下降，
7 项处于未分辨范围。它已经解决了主要的 lookup、invoke、事件编码和请求分配成本，
不是一次失败的翻译工程。

剩余问题集中在少数生命周期和对象事件慢尾，而不是所有路径都落后。正式记录的四项
明确负项是单方法注册 p95、单监听对象事件 p95、不匹配对象事件 p95 和 p99；完整数字
见 [R136 实机结果](reviews/R136_UBUSD_COMPLETION_RESULT.md)。

R142 和 R146 都验证了相同的事实：monitor 局部成本可以降低，但小消息端到端收益很小。
R146 候选通过 62 项单元测试及协议、FD、恢复和功能检查，但固定 54 例性能筛选中，
monitor 平均延迟相对 R136 只下降 0.82%，只有 4/6 组下降；冻结门要求下降超过 3%，
且至少 5/6 组下降。daemon CPU 下降 11.20%，caller CPU 上升 5.26%，两者合计 CPU
下降 1.94%，都不能替代延迟门。候选因此拒绝，原始证据保存在
`archive/ubusd/r146-closeout` 的 `7539c22` 及 ignored `private` 归档中。

这不是 Rust 天生慢于 C 的结论。R136 的主要收益来自减少系统调用、分配和复制；当这些
工作已经被消除后，剩余时间更多落在内核调度、socket 读写和调用端校验，继续改动局部
Rust 表达方式很难稳定改变端到端结果。

## 保留的边界

- R136 不是“所有指标全面胜 C”，四项实机慢尾负项仍然存在。
- Oracle aarch64 的结果不能替代 AX3000T Cortex-A53 的性能验收。
- monitor 的手工多帧 FD 场景保留既有 read-ahead 契约差异，不能写成对 C 的全输入等价。
- 正确性测试覆盖了已知合同和故障边界，但不能证明没有任何未知 bug。
- R146 的 VmHWM 诊断改善是单次描述性观察，不能替代延迟验收。

## 后续工作边界

性能专项关闭后，只接受有明确交付价值的工作：

1. 修复或验证实际兼容性、错误恢复、打包和集成阻断。
2. 为 R136 写部署前的身份、回滚、健康检查和全栈验收计划；没有单独授权不接触物理设备。
3. 只有出现新的实际负载证据，或能证明某个既有缺陷会阻断交付时，才重新开实验。

“再减少一次复制”“再换一种容器”“再跑一轮窗口”本身不构成立项理由。任何未来候选
都必须先写清它解决的具体交付问题、预期省掉的工作、失败后的停止条件和唯一验收门。
