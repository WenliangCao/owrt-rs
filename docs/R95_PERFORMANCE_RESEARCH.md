# R95 后续性能研究与实机验收规则

2026-09-20。用户要求：先关闭实际缺陷，再逐个优化九组件，最后验证协同运行；
性能、内存全面胜过精确 C，并尽可能胜过正式 R89。遵循 [审计](reviews/R94_COMPLETION_AUDIT.md)
与 [修复记录](reviews/R95_DEFECT_FIXES.md)。本文件规定研究方法，**不宣称任何新性能结论**。

## 1. 不降低目标，也不提前宣布达到目标

- 正确性、功能和既有错误恢复合同是前置条件；更快地返回错误结果不计收益。
- C、正式 R89、候选三侧是必测对象。紧邻改动前的候选作为第四侧用于定位本次改动；
  它不能替代 C 或 R89。历史 source05 只在复核其特定回归时加入，不再机械沿用旧四侧要求。
- 每个组件、每条预先确定的负载、每个主要指标分别验收。平均数、加权总分或几何平均
  不得抵消某条尾延迟或内存退步。持平、测不准、未测均不是“优于”。
- “全面”必须附硬件、镜像、二进制、负载及规模范围。有限实验不能证明所有可能输入，
  扩大功能或规模范围后需重新验证，不把缺乏覆盖说成无需覆盖。
- 每一步单独 commit，包含改动理由、实际验证范围和剩余问题。研究中的候选可以保留，
  但存在未胜出项就不能标记组件/整栈性能目标完成；对 R89 的未胜出项同样全部列出。

## 2. 物理路由器上的试验边界

最终正确性、CPU、延迟、吞吐、内存结论来自 AX3000T 本机。构建机只做编译、预筛查、
差分和采集工具验证，不混入实机样本。每次记录精确镜像、内核、工具链、源码与二进制 SHA。

当前生产始终为 C：不安装 APK、不切换 init/overlay、不替换生产进程、不重启或刷机。
候选只在唯一临时目录和隔离 mount/PID/network namespace 中运行；配置、ubus socket、
网络设备、nft 表和服务均为测试专用。隔离 kmsg 和硬件 watchdog。使用路由器端 guard
约束整个 namespace 生命周期，不仅靠 SSH 客户端超时。

每个窗口先核对恢复备份与 C 身份，结束后清除所属进程、挂载和目录，再核对配置、boot、
生产二进制、挂载表及客户端网络健康。异常窗口保留原始记录并停止后续采样。
不通过重启、全局 drop_caches、修改生产 CPU affinity/频率或移动生产 cgroup 来制造安静环境。

单组件先固定其余依赖为镜像 C；之后在同一隔离系统内接入全部九个最终候选，测真实调用链
和 mixed 负载。实际硬件无线、生产 PID 1 冷启动及部署态的全栈验收仍须单列，
在当前禁止部署的阶段不能用 namespace 结果冒充已完成。

## 3. 指标与记账边界

| 范围 | 必须覆盖的指标/状态 | 不允许的代替方式 |
|---|---|---|
| 每条请求负载 | 主体与必要子进程 CPU/op、端到端 mean/p50/p95/p99、错误/超时数 | 只报 CPU 或 mean；删除慢请求 |
| 并发负载 | 固定同一并发/到达方式下吞吐及尾延迟、相同外层时间窗内 CPU | 累加互相重叠的各客户端 CPU 差分 |
| 守护进程资源 | 启动、空闲、活动、峰值、连接/对象扩容、关闭后回收 | 用运行结束的一次 RSS 代表峰值 |
| 短命命令 | 整个调用树的累计 CPU、同时存在的内存峰值、返回码和输出 | 只读父进程；把各进程各自峰值相加 |
| 九组件组合 | mixed 与各主调用链、启动/恢复、整体 CPU 和同时段内存 | 累加不同窗口的单组件收益 |

CPU 必须同时披露主体、依赖和客户端开销，明确子进程归属。fw4 的 child_cpu 包含 nft，
不能标成纯 fw4 自身成本；单组件压低自己的开销却把成本转移到依赖也不算系统收益。
记录 CPU 计时分辨率，先用 pilot 确定足够长的测量窗口；量化误差覆盖收益时结论为待定。

吞吐不能靠增加失败率或放松超时提高。并发数、到达模式、请求校验、返回大小、预热、
冷/热状态均在采样前固定。现有紧密请求只代表一种负载，需补实际 RTT、TLS、长连接、
慢读者、并发变更、恢复等功能相关场景。用于 profiling 的插桩、strace 和内存采样
独立运行，不能把其耗时混入正式延迟比较。

## 4. 内存测量的现实缺口

当前镜像 kernel 6.12.94 没有 `/proc/1/smaps` 和 `smaps_rollup`，尚不能报告实测 PSS。
Linux 说明 `/proc/PID/status` 的 RSS/HWM/匿名页等计数存在精度限制；因此旧报告的这些值
保留为诊断观测，不能通过增加重复次数消除系统性的计数误差。
见 [proc 文档](https://docs.kernel.org/filesystems/proc.html) 与
[proc_pid_status(5)](https://man7.org/linux/man-pages/man5/proc_pid_status.5.html)。

只读检查确认 cgroup v2 提供 memory controller，但根的 subtree_control 当前为空。
下一步应先验证独立测试 cgroup 的可恢复建立/删除流程和记账精度，再采集 memory.current、
memory.peak、memory.stat，覆盖完整调用树。尚未启用该测量，也尚无新的峰值数据。
6.12.94 的 memory.peak 重置针对同一个打开的 FD；不能写一次后另开 FD 读取并假定已重置。
具体依据是 [匹配内核版本的 cgroup v2 文档](https://github.com/gregkh/linux/blob/v6.12.94/Documentation/admin-guide/cgroup-v2.rst)。

新的工具必须用已知分配/释放、fork、短命子进程、共享文件页和 socket/pipe 负载验证记账范围。
cgroup 的 file 包含 tmpfs；页缓存的归属、共享库复用、候选从 `/tmp` 执行而 C 从 squashfs
执行的差异须另设控制。不能把 cgroup 数字称为 PSS，也不能把 RSS 差值当整机实际增量。
分别报告匿名内存、文件/共享页、内核资源、整体实测峰值及回收行为；不重复累加分类中重叠字段。
保持生产 C 的隔离试验天然共享 C 库缓存，这一部署方式偏差在全栈验收前仍需明确披露。

## 5. 先试验设计，再运行确认实验

依据系统基准研究，把重复放在主要变异来源上，报告效应量与不确定性，
不能将同一守护进程内的一万条请求当成一万个独立实验。
参见 Kalibera/Jones 的 [Rigorous Benchmarking in Reasonable Time](https://kar.kent.ac.uk/33611/45/p63-kaliber.pdf)。

工作分为三段：

1. **校准与 pilot**：相同二进制 A/A、空工具成本、计时/内存分辨率、预热、运行间变异、
   请求数与尾分位数稳定性、顺序/温度/负载影响。用于选择规模和独立重复次数，不计入胜出证据。
2. **冻结**：提交假设、负载矩阵、指标和方向、独立实验单位、样本数、随机种子、全部侧的身份、
   有效样本规则、分辨率/实际收益门槛及完整命令。记录 Cargo 实际固定构建目录、链接参数和
   strip 步骤；remap 不保证不同构建目录产生完全相同的二进制布局。
   没有通用的“四轮就够”，样本量由 pilot 决定。
3. **确认**：按冻结方案采集全量结果。不得看见领先就提前停止，也不得一直补轮次直到显著。
   改算法、改负载、改样本量都形成新实验，旧实验及失败样本保留。

一个配对 block 含同一负载下 C/R89/候选（及改动前侧）的独立进程运行，各侧使用同一夹具。
block 内顺序独立均匀随机，记录顺序、时刻与可用环境观测，避免先跑完 C 再跑 Rust。
若采用六种顺序强制平衡的设计，应将完整平衡周期作为外层实验单位分析，
不能假装受约束的每个子块都独立。随机化不自动消除热状态或前一次试验遗留影响；
发现持续漂移、顺序依赖或强相关时，先修正设计，不套用独立样本置信区间。
参见 [NIST 随机区组设计](https://www.itl.nist.gov/div898/handbook/pri/section3/pri332.htm) 和
[Avoiding the Ordering Trap](https://www.usenix.org/system/files/atc23-duplyakin.pdf)。

## 6. “优于”的初始统计判定

选用易复核、无需正态假设的**配对运行比值中位数**作为确认实验的初始效应量。
这是“典型独立运行的相对变化”，不是所有请求混池后的均值或 p99；每轮请求的 mean、p50、
p95、p99 各自先算，再分别形成配对序列。同时完整披露每轮原始值、范围、异常和失败。
偶发大停顿不能被中位数掩盖，压力/长时错误恢复门仍是独立必需条件。

对越小越好的正值指标，令每个独立 block 的 `z_i = log(candidate_i / baseline_i)`；
吞吐取反向比值。排序为 `z_(1)..z_(n)`。计划预先冻结比较总数 `m`，包含所有声称要比较的
负载 × 指标 × 基线；总错误率 α = 0.05。选择最大的整数 `k ≥ 1` 满足：

```text
sum(j=0..k-1, choose(n,j)) / 2^n <= alpha / (2*m)
CI = [exp(z_(k)), exp(z_(n-k+1))]
```

这是二项分布秩区间配合 Bonferroni 校正；在独立同分布/明确中位数等假设成立时，
整个预定比较集合的区间同时覆盖率至少为 95%。依据
[Penn State 的中位数秩区间推导](https://online.stat.psu.edu/stat415/lesson/19/19.1)。
实现需以小样本穷举覆盖率验证，不能只用模拟“看起来正常”。

- 区间上界严格低于 1，且达到预先冻结的分辨率/实际收益门槛，才记“已证优于”。
- 区间下界高于 1，记“已证退步”；跨 1、样本不足得不到有限区间，记“证据不足”。
- 恰好相等不是胜出。基线为 0 的计数不能强行除法，改用预先声明的配对绝对差；
  两侧都为 0 只能说相同。缺测、失败、身份/清理不通过均不能记胜出。
- 全部必需指标胜 C 且正确性门通过，才关闭该组件的 C 性能目标；九组件组合另外验收。
  对 R89 使用相同规则，列明未胜出的每一项。统计不显著不能用作等价或非劣证明。

此方法是研究起点；若 pilot 显示它不能回答实际目标，可以在确认实验前选用并论证另一方法。
不得在结果出来后挑选最容易得到胜出的检验。四轮历史 R94 结果继续作为探索证据，不追溯升级。

## 7. 算法研究队列与证据要求

| 次序/组件 | 已知问题或尚未覆盖的成本 | 下一步要回答的问题 |
|---|---|---|
| 1 ubusd | lookup_all_128 对 C 的 p50 反例；读前缓冲成本 | 接收、批量写入、队列或客户端校验分别占多少？怎样同时改善延迟和每客户端占用？ |
| 2 netifd | wireless_status 对 R89 尾延迟；常驻匿名页增加 | 空无线夹具与实际配置分别走哪里？常驻 netlink 缓冲可否缩小/复用且保持溢出恢复？ |
| 3 httpd | JSON-RPC c4 CPU 未胜 C；内存上升 | HTTP→ubus 的编码、复制、调度和依赖成本各多少？TLS/真实 RTT 下是否仍成立？ |
| 4 rpcd | 大 UCI 回复、尾延迟、匿名页 | 是否重复解析/遍历/编码？减少中间对象是否同时降低峰值和 CPU？ |
| 5 procd | 大服务列表尾延迟、固定 fd/匿名页 | 能否减少重复工作且保持动态状态正确？缓存失效成本是否超过收益？ |
| 6 logd | 多读者、慢读、内核 pipe 缓冲证据不足 | 零/单/多读者的总资源曲线、背压与队列限额是否可同时改善？ |
| 7 fw4 | 短命峰值、配置/输出中间结构 | 是否可减少复制/分配，同时保留输出顺序、nft 错误与 reload 合同？ |
| 8 uci | 已修短读后的真实成本、短命峰值 | CLI/共享库各自的解析和分配热点是什么？不省略 EOF/错误检查能节省哪里？ |
| 9 reload-config | 实际变更投递、峰值、锁预算成本 | 无变化/少量/批量变更的加载、哈希、投递成本分别多少？取消与超时边界是否保持？ |

每项按“现有接口/调用者/失败边界 → 实机 profile → 可证伪假设 → 匹配上游/论文研究 →
小改动 → 历史回归 → 实机确认 → 记录正负结果”推进。逐项只是研究顺序，任何共享库修改
都重新标记其调用方证据是否失效；不能逐项打勾后忽略最终组合。
不凭算法名称或 Rust 语言本身推断更快，不为微小收益引入难以维护的多套路径。
