# R93 暂停交接：仍未解决的现象

**暂停时间：2026-09-15。用户因额度要求暂停；所有构建、测试和实机采集已经停止。**

这份文档主要记录现象。这里的“未解决”指目前没有通过证据确认解决，
不等于证明 Rust 天生做不到，也不等于所有尝试都失败。没有异常证据的组件会直接写“尚未发现”，不编造问题。

## 先看结论

- 最确定的未解决问题是 **HTTP 停放后请求开销**：当前 Rust 与 R89 基本相当，明显高于 C。
- **整机日志、HTTP、混合负载曾比历史 R89 退步**，但固定输入/同机控制未完整复现差额；原因仍未分清。
- ubusd、rpcd、netifd 有部分延迟指标未赢 C；不能用 CPU 更低代表所有指标都赢。
- 目前没有证据支持“九组件全面优于 R89”，也没有证明“绝对无 bug”。

## 1. HTTPD：请求间隔跨过 50 ms，Rust 的 CPU 突然升高，C 基本不变

这是**本轮最新路由器实测**，不是构建机模拟：AX3000T，16 KiB 静态响应，4 客户端，
每侧每档四轮交错；共 60 组、168,000 个请求，响应状态和正文全部正确。
生产 R92 栈保持运行，三侧被测 HTTPD 各在私有 namespace 内运行。

| 请求间隔 | 原版 C CPU µs/请求 | 正式 R89 | 当前 source05 修复版 |
|---|---:|---:|---:|
| 0 ms | 259 | 204 | 203 |
| 20 ms | 290 | 210 | 210 |
| 40 ms | 290 | 210 | 210 |
| 60 ms | 290 | 625 | 630 |
| 80 ms | 290 | 685 | 685 |

**C 的表现：** 20/40/60/80 ms 四档 CPU 中位数均为 290 µs；各轮并非每次都精确相同。

**Rust 的表现：** 0/20/40 ms 仍比 C 省 CPU；60/80 ms 上升到 C 的约 **2.17/2.36 倍**。
60/80 ms 的平均响应延迟中位数也更高：C 为 **456/468 µs**，当前 Rust 为 **753/779 µs**。
与 R89 相比，当前修复没有消除这一现象；630 对 625 的小差值不能单独认定为新的显著退步。

**目前没搞定的地方：** 如何同时保持紧密请求优势、低空闲连接内存，又消除停放后请求的高成本。
临时线程复用实验在构建机上降低了开销，仍未赢 C；立即停放的另一实验反而显著拖慢紧密请求，已否决。
新的安全线程复用补丁只通过原生单测，**还没有同 SDK 或路由器收益证据**。

另一个尚未解释完的现象：历史实机中，**同一 R92 二进制的活动 HTTPD 比临时新启 HTTPD 更贵**。
`configs/get network` 两方法，自身 CPU 高约 **28.34%/15.95%**；进程历史、监听端点和其他活动请求同时不同，
尚不能唯一归因于线程、分配器或代码。不能靠重启活动服务挑选好分数。

证据：[本轮四轮实机结果](reviews/R93_HTTP_DEVICE_BASELINE.md)、
[逐项范围与身份](reviews/r93-http-device-baseline.json)、
[历史活动/临时实例比较](../reports/ax3000t-stock-openwrt-25.12.5/R92_PERFORMANCE.md)。

## 2. logd：整机时比历史 R89 贵很多，固定语料却没有相同退化

以下是已有 R92 实机观察，**不是本轮 source05 的整机成绩**：

| 场景 | C CPU µs/操作 | R89 | R92 |
|---|---:|---:|---:|
| 整机日志 lane，总服务端 CPU | 827.5 | 437.5 | 566.5 |
| 隔离组件，固定 128-byte syslog，logd 自身 CPU | 31.90 | 8.35 | 7.30 |
| 隔离组件，读取 100 条，logd 自身 CPU | 805.50 | 417.00 | 386.50 |

**C 的表现：** 上述固定输入场景均比 Rust 更贵。

**Rust 的表现：** 整机日志 lane 相对历史 R89 增加 **29.49%**；固定语料里 R92 却更省 CPU。
两种计数范围不同，不能横向相减。整机读取真实最近 100 条日志；历史正文和进程历史没有完整冻结。

**目前没搞定的地方：** 还无法将整机增幅准确拆成日志内容、必要日志恢复、进程状态和实现开销各自的贡献。
不能将“固定语料更快”解释成整机退化不存在，也不能将 29.49% 全算到新代码上。

另一个边界：Rust 的 4 MiB 待发数据预算**不等于 4 MiB RSS 硬上限**；缓冲清空后可能保留容量。
尚无本轮实机压力数据证明所有读者轮流积压后的内存会回到理想水平。

本轮旧 poll 下标误断健康流、断总线后积压和 oneshot 等问题已修，相关专项通过。
新固定语料工具在 C/R89/候选五场景共 15/15 smoke 通过，但明确不是性能结果。
正文单次分配/消除 clone 的私有补丁已构建，尚未跑该二进制的完整运行门和性能对照。

证据：[历史日志数据](../reports/ax3000t-stock-openwrt-25.12.5/R92_PERFORMANCE.md)、
[固定语料工具说明](../tools/r93_logd_fixed_corpus.md)。

## 3. ubusd：CPU 更低并不保证查询延迟更低；慢读大表还有未验证的成本

**C 与 Rust 的已有实机差别：** R92 同批比较中，`lookup_all_64/128` 平均延迟比 C 高
**3.77%/3.23%**，但自身 CPU 分别低 **10.50%/13.52%**；四客户端 invoke 平均延迟高 **3.40%**，CPU 持平。
这些是逐项中位差，不能把每个小差值都当确定性回退。

**目前没搞定的地方：** 尚未同时改善这些延迟和 CPU 指标；绑单核有时减少轮间波动，却会明显增加尾延迟，不能算解决。

本轮另发现：**不带 OBJPATH 的慢读全表查询，Rust 每次续传会复制剩余 ID 表**。
单次分配探针中，64→1024 对象时，旧实现恢复一次查询申请的字节 **33347→41027**；
私有直接遍历候选为 **32851→32851**。这证明了一项分配成本，**尚未证明设备上的延迟/CPU改善**。
C 直接遍历树，但它的删除续传点缺陷不能带回 Rust。
原 74 项矩阵里名为 `lookup_all` 的负载实际传 `"*"`，没有覆盖这个无路径分支。

accept 错误后不恢复的已确认问题已修；不要把这个旧 bug 当成当前仍未解决。

证据：[核心算法审计](reviews/R93_CORE_PERFORMANCE_AUDIT.md)、
[历史组件数据](../reports/ax3000t-stock-openwrt-25.12.5/R92_PERFORMANCE.md)。

## 4. rpcd：原版偶发漏功能字段，Rust 返回完整，导致差分报红

**本轮现象：** 733 步原版/候选差分中有一次 `luci.getFeatures`：C 返回有效 JSON，但没有 `dnsmasq` 字段；
Rust 有完整字段，其他字段相同。相邻原版调用又能返回该字段。

独立真实 helper 测试：无信号干扰时两侧各 8/8 完整；SIGCHLD burst 下，原版 **7/8 漏 dnsmasq、8/8 漏 odhcpd**，
候选 8/8 完整。不是“Rust 怎么改都失败”，这里反而是原版不稳定。
当次差分没有 syscall trace，不能断言唯一根因已经证明。

测试夹具还用了镜像不支持的小数 `sleep`，其预期的 EOF/退出间隔实际不存在。
修正为相同的精确 helper 输出字节和有效间隔后，**733 步零差异**；真实 helper 故障测试另行保留，未屏蔽字段。

**尚未赢 C 的性能项：** 历史 `session_access_granted_c4` 平均延迟高 **7.29%**，自身 CPU 低 **14.58%**。
现阶段没有新的实机证据证明该延迟项已消失。

断连时会话/回滚保留及离线配置恢复已有修复和专项证据，不能与此夹具差异混为一个未修 bug。

证据：ignored `private/r93/rpcd-features-diagnostic-final.tar.gz`；
[历史组件性能](../reports/ax3000t-stock-openwrt-25.12.5/R92_PERFORMANCE.md)。

## 5. netifd：少数延迟没赢 C；复杂 IPv6 状态还没有性能实测

**已有实机差别：** R92 的 `lan_status` 平均延迟比 C 高 **0.87%**、CPU 低 **12.50%**；
`interface_named_32` 平均延迟高 **0.10%**、CPU 低 **8.85%**。差值很小，尚不能证明稳定的大倒退。

**目前未知：** 带实际 delegated prefixes/assignments 的 IPv6 状态查询是否明显低效。
源码中存在重复扫描、字符串复制和排序；现有 32 接口矩阵是静态配置，没有覆盖这个非空路径。
这只是待验证的疑点，**没有 C/R89/Rust 三侧数字，不能写成 Rust 必然慢**。

本轮 SDK 产物的 31/31 netifd 历史用例通过；部分注册失败后错误宣告恢复的问题已修。
当前没有另一个已经复现、仍无法修复的 netifd 功能故障。

证据：[核心算法审计](reviews/R93_CORE_PERFORMANCE_AUDIT.md)。

## 6. procd：通知时序曾修坏，已经恢复；大规模 watch 成本尚未测清

修复中确实出现过：R89 在 `set` 返回后立即通知为 **12/12**，最初队列版 **0/12**；
仅推迟回复的中间版在 `service.start` 驱动通知时为 **2/12**，R89 仍为 **12/12**。
最终 source05 两项都恢复 **12/12**，83 项 Linux 单测、11 项业务检查和历史 procd 门通过。
**这些是已解决的中间回归，不是暂停时仍然失败的现象。**

仍未知的是大量 watch 的队列去重/所有者检查成本。新队列存在二次扫描可能，旧矩阵的 list/info 服务没有 watch。
目前无大规模 C/R89/候选实机数据，不能宣称全面优于 R89，也不能宣称已发生大倒退。

现阶段未找到另一个可复现而修不掉的 procd 功能问题。
证据：[最终时序复核](reviews/R93_PROCD_FINAL_REVIEW.md)、[核心审计](reviews/R93_CORE_PERFORMANCE_AUDIT.md)。

## 7. UCI、fw4、reload-config：不要为了列满而编造异常

- **UCI：** 当前历史字节、rename、模糊用例通过。没有本轮已确认而未解决的异常；新实机全矩阵尚未采集。
- **fw4：** 当前精确上游、模糊、defaults、镜像及 R92 专项通过。没有本轮已确认而未解决的异常；没有证明每个负载都优于 R89。
- **reload-config：** 默认构建曾为 528544 B，超过 512 KiB 门；按项目 SDK 链接/裁剪后为 498415 B，原功能/体积门通过。
  正式 R89 为 494319 B，当前还大 4096 B，**体积没有赢 R89**。这是构建体积差，不是“功能始终修不好”。

## 8. 整机：进程 RSS 更小，系统可用内存却更少

历史 C/R92 冷启动比较：daemon RSS 中位数之和 **9606→5320 KiB**，
整机 MemAvailable 却 **137296→130830 KiB**，少 **6466 KiB**。
它们衡量不同东西，不能互相抵消。文件页、保留副本、预热和内核缓存都有影响；
已有副本页干预也没有把 MemAvailable 变化唯一解释完。**目前不能保证 Rust 全机内存各项均优于 C。**

另有历史 R89→R92：mixed 吞吐 **−3.73%**、CPU/操作 **+4.35%**；
R92 仍胜同批 C，但没实现用户要求的双基线全面胜出。历史输入/进程状态未完全冻结，
本轮尚未完成新的 C/R89/候选三侧冷启动整机比较。

证据：[整机、内存及局限](../reports/ax3000t-stock-openwrt-25.12.5/R92_PERFORMANCE.md)。
