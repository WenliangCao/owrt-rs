## 已定的取舍

1. **perf**：只保留 `153c4589`（rpcd iwinfo 查询去重，真机快约 36%）。其余 39 个 perf 全部放弃，
   包括归档 ref 里的 DNS stack 和 HTTP slice 两组。这一轮不再做任何性能优化工作。
2. **补丁质量**：采纳的修复必须是一个优良的补丁：
   - 改动最小、可读，风格与周围代码一致，符合 `docs/RUST_GUIDELINES.md`；
   - 自带回归测试，而且这个测试在 v0.3.3 上会失败。
   原补丁写得乱的，就按正确行为重写，不要硬移植。
3. **19 个待定**：这一轮必须全部结案，结束时不允许再有「无法判定」。规则如下：
   - 只有证明了以下两种情况之一，才算采纳：
     - v0.3.3 在可达输入下出现与 C 不同、客户端或配置结果能看到的行为；
     - v0.3.3 在可达输入下会 panic、abort、挂起或无界增长。
   - 用一个聚焦的实验证明不了的，一律拒绝并丢弃，在台账里写一行理由。
   - 已经证明原版 C 也这样、只是「更标准」或「更安全」的，同样拒绝。
4. **9 条「值得另立的任务」**：
   - **要做，共 4 条**：
     - netifd 遇到非有限数值在 teardown 时 abort（`ada4f5ef`）：改为不 abort，编码与 ucode 往返一致；
     - odhcpd PD 前缀（`ef2402a6`）：同一输入下 C 返回 3 个前缀、v0.3.3 返回 2 个，修到与 C 完全一致，并且不引入移位 panic；
     - logd ring 写满最大尺寸记录时 abort（`3f0f2e0c`）：改为不 abort，行为按 C；
     - DNS TCP 65536 和 DHCP 重复选项：只有当 v0.3.3 在这些输入下会 panic/abort，或者会把不合规的包发给客户端时才修，否则不做。
   - **不做，共 5 条**：RA 零 lifetime、`-S` docroot、HEAD 错误正文、CLOEXEC 和 rpcd 信号顺序、netifd 强杀旧 helper。
     理由是 C 本身也这样，也没有观察到问题。在报告里记为「决定不做」。
5. **Rust 与依赖**：Rust 1.100 已于 2026-11-12 发布。项目当前固定在 1.98.1，这一轮升到 1.100.x 的最新补丁版本，
   依赖也一起升级（细节见下文）。

## 工作顺序

### A. 工具链和依赖：从 `0cbc328d` 开独立分支，先只做这一件事

- 把所有固定版本的地方都改到 1.100.x：
  - `rust-toolchain.toml`；
  - 13 个 crate 的 `rust-version`；
  - workflow 里写死的版本（例如 `dnsmasq-target-check.yml` 里的 `"1.98.1"`）；
  - `tools/` 里的 `RUSTUP_TOOLCHAIN` / `V1_CARGO`；
  - packaging 和 `docs/RELEASE.md`。
  改完全仓 grep 一遍 `1.98`，确认没有遗漏。
- oracle 的 `~/.cargo/bin` 装上 1.100.x 和 `aarch64-unknown-linux-musl` target。
- 依赖：
  - 13 个 lockfile 都做 semver 兼容范围内的 `cargo update`；
  - 主版本升级只做两类：改动很小的，或者有安全公告的。不做的列出原因；
  - 跑一遍 `cargo audit` 或等价检查。
  - 不借升级之名做无关重构。
- 新版 clippy 报出的问题要逐个修，不要整片 `allow`。
  never-type fallback 的变化会影响 2024 之前 edition 的代码，要检查各 crate 的 edition 和受影响的代码。
- 这一步完成后，在 oracle 上跑一遍完整门禁，单独提交。

- 主代理把子代理的结论和前两轮的结论对照。凡是不一致的，用实验裁决；

### E. 正式构建与 PGO（这是上一轮遗留的坑）

上一轮发现，用现有方法重建的 dnsmasq 比线上发布的 ELF 慢约 20%（低速 +23%、饱和 +20%、DHCP +14%），
原因是冻结的 PGO profile 与代码不匹配。这次要按正式流程来：

- 授权你把**一个名为 `ci/audit110-r3` 的分支** push 到 origin，用来运行 `ci.yml`、`core-safe-check.yml`、
  `dnsmasq-target-check.yml`、`dnsmasq-pgo-candidate.yml` 和 `release-image.yml`。
  不 push main，不打标签，不创建 GitHub Release。
- 先过构建配方的 A/A：用这条正式流水线重建 v0.3.3（`1e25d61d`），在真机上与线上发布的 ELF 对比，
  必须在噪声范围内。过不了，就先查清根因并修好流水线或 PGO 输入
  （参考 `docs/releases/dnsmasq-k-pgo-inputs-20261017.md`、`private/v033-pgo`、decision 0018）。
  不允许绕过 A/A 直接比候选。
- A/A 通过后，按同一流程为「仅工具链和依赖」和「最终候选」两版分别重新生成 PGO profile 并构建。
  最终要产出 CI 构建的固件镜像，并记录它的 SHA256。

- 流水线重建的 v0.3.3（即 A/A 那一版）；
