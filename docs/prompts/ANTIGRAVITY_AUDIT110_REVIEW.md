## 怎么裁决

**fix 提交**：每个都要回答以下四个问题。
1. 它声称的缺陷在 v0.3.3 上是否真实存在？要拿可复现的输入或场景证明，不能只读 diff 推测。
2. 修完以后，行为是否与上游 C 一致？以 C 源码和 C 对照实测为准，不以它的提交信息或测试名为准。
3. 有没有引入新问题？重点看 panic/abort、无界增长、阻塞或忙等、权限和 ACL，以及 procd respawn 的交互。
4. 它附带的测试，在 v0.3.3 上会失败、在修复后会通过吗？会，才算真回归测试。

**perf 提交**：默认拒绝，除非满足以下全部条件：
- 在与线上同形态的构建里（release profile、musl、aarch64、strip 后）测出改善，
  多次运行后区间与基线不重叠；
- 同时没有 RSS、匿名内存、二进制体积或空闲唤醒方面的代价，reload-config 的 512 KiB 体积约定也不能破；
- 改善能落到用户可感知的量级上。

CPU 敏感的结论以设备为准，oracle 只能做筛选。

**test 提交**：判断它们测的是真实契约还是实现细节，以及是否确定性（flaky 的断言比没有断言更糟）。

每个提交给一个结论：`采纳`、`修改后采纳`（写明怎么改）、`拒绝`、`无法判定`（写明还缺什么证据）。
相互依赖、或互相抵消的一串提交，按组裁决。
