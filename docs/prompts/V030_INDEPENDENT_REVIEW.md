## 优先级（按真实影响，不按数量）

已知事实：路由器整体瓶颈在楼宇上游和 Wi-Fi 空口，控制面不在转发热路径上。所以**性能不是主目标**，除非你能证明某处可被用户感知（启动时间、配置应用延迟、内存长期增长、空闲 CPU 唤醒）。按以下顺序投入：

1. **可用性与恢复**：冷启动/断电后能否稳定起网；进程崩溃、重启、依赖（ubusd、netifd）先后到达或消失时的行为；无限等待、死锁、忙循环、退出码与 procd respawn 的交互；看门狗。
2. **长期运行**：连续数周运行下的 fd、内存、定时器、租约表、日志缓冲、netlink 订阅泄漏或无界增长；时钟跳变（无 RTC，NTP 前后时间回拨）；60 秒 DHCPv4 租约和 WAN6 频繁抖动这种真实上游下的状态机正确性。
3. **安全边界**：LAN 侧暴露面（httpd、rpcd/ubus ACL、session、dnsmasq/odhcpd 报文解析）；对恶意或畸形输入的 panic、越界、整数溢出、放大；`unsafe` 块与 FFI 的每一处前提是否真的成立。
4. **与 C 原版的行为分歧**：仅限会影响客户端或配置结果的分歧（UCI 解析、防火墙规则生成、DHCP/RA 报文字段、ubus 返回格式）。
5. **可删减的复杂度**：死代码、重复实现、过度抽象、只为测试存在的分支；能删就删，删了要证明行为不变。
6. 最后才是性能，而且必须给出用户能感知的量级。

在每个组件上先花少量时间找“爆炸半径最大的路径”，不要追求逐行覆盖。

## 验证纪律

- 每个发现都要有可复现证据：失败输入、测试用例、或在 Oracle 上的运行记录。没复现的只能标为“疑似”，单列，不计入结论。
- 差分测试红了要重跑 3–4 次再相信；绿了要确认它确实比较了东西。
- 发现分级：P0（会断网/无法恢复/远程可利用）、P1（特定条件下功能错误或资源泄漏）、P2（分歧或健壮性问题）、P3（清理与简化）。
